# 営業KPI: HubSpot 直読み化と GitHub Actions 削減の計画(調査と設計)

作成: 2026-10-05 / 状態: 調査と設計のみ(コードは書いていない)/ 対象: HR_HR の `/sales-kpi` と `/app/sales-kpi`

表記: **【確認済】** は実ログ・実コード・実 API 応答で確かめた事実。**【推測】** は根拠はあるが確かめていないもの。**【未確認】** は私の側から見えず、ユーザー側の確認が要るもの。

## 0. 結論(先に読む)

1. **営業KPI を全部アプリに移しても、Actions の削減は月およそ 270 分(Hubspot リポ内の営業KPI ぶん)が上限**。これは 2026-10 の全体の使用量に対して小さい(後述 2.2)。10/1〜10/5 の Actions 使用量は **アカウント全体で 1,883 分**で、内訳は HR_HR リポ 1,289 分(68%)、Hubspot リポ 62 分(3%)。**枠(Free の private 2,000 分/月と見られる)を食っているのは営業KPI ではない。** 移行は無駄ではない(朝の更新が 3 時間遅れる問題、枠切れで止まる問題、`classify()` の二重管理が消える)が、「Actions の分を減らす」という目的の主役にはならない。
2. **現在の Python は 1 回およそ 8 分 15 秒(課金 9 分)のうち HubSpot 取得が 97%**(実測 4-1 の表)。Zoom は 5 秒程度。つまり Zoom より HubSpot を移すほうが効く。
3. **段階 1(画面だけ HubSpot 直読み)では Actions はほとんど減らない**(担当者別を Python から外した場合の月およそ 50 分のみ)。理由は、週次(Python)が `KPI営業_商談` などのシートを読んで計算するため、Python は HubSpot からそれらのシートを書き続けるしかないから。**分が減るのは、週次・決定者の履歴・リスト在庫の保存先をアプリが持った時点(段階 2a)**。
4. **今月の Actions 枠は 10/6〜10/7 頃に尽きる見込み(【推測】)**。10/1〜10/5 の平均が 1 日およそ 380 分で、10/5 時点で 1,883 分。9/19〜10/1 の営業KPI の連続失敗(下の 4-2)は、まさにこの枠切れで起きた。設計とは別に、直近の手当てが要る(判断 J1)。
5. HubSpot の Search API は **アプリの現行クライアントが 1 リクエスト/秒に絞っている**。Python は 4.5/秒で回しており、1 回の更新で約 1,800 回(うち 74% がリスト在庫の全件走査)。**同じ作りをリクエストの最中に走らせると、担当者別だけで 7 分、リスト在庫は 22 分かかる**。段階 1 は「画面を開いたときに取る」ではなく「ブロックごとに TTL を持つ背景更新」にする必要がある(第 5 章)。

## 4. HR_HR 側の既存資産

### 4-1. HubSpot クライアント(`src/hubspot/client.rs`、origin/main)

**【確認済】**

- `HubSpotClient`(読み取り専用、`AppState.hubspot: Option<Arc<..>>`)。環境変数は **`HUBSPOT_ACCESS_TOKEN`**(`config.rs` の `HubSpotApiConfig`。Legacy Private App / Service Key のどれでも `Bearer`)。Python 側は `HUBSPOT_TOKEN` → `HUBSPOT_ACCESS_TOKEN` の順に探す。トークンの値は見ていない。
- 使えるメソッド: `search(object, body)`(`deals` 可)、`deal_pipelines()`、`batch_read`、`get_object`、関連、`property_definitions`。**無いもの**: Owners 一覧(`GET /crm/v3/owners`、`archived` 両方、ページング)。`search()` は 1 ページしか返さない(9,800 件で打ち切る「最後の ID から取り直す」ページング補助は無い)。
- 流量制御: `search_min_interval` 既定 **1,000 ms(= 1 回/秒)**、1 つのロックで直列化。コメントに「鍵を既存バッチと共有しているため」とある。retry は `max_retries = 2`、タイムアウト 10 秒(Python は 30〜120 秒・最大 6〜8 回)。429 は `Retry-After` を尊重、最低 1 秒待つ。`X-HubSpot-RateLimit-*` を記録し、残り 10% 未満で warn。
- 利用者: `/api/crm/*`(`src/crm/routes.rs`、1 リクエスト最大 10 回の安全装置)と `crm_metadata`。**営業KPI からはまだ使っていない。**

**流用できるか**: 認証・retry・ヘッダ記録・トークンを出さない作りは流用できる。ただし次の 3 つの拡張が要る。(a) Owners の追加、(b) 検索ページングの補助(`hs_object_id` 昇順で 9,800 件ごとに取り直す。Python の `_fetch_shard` と同じ)、(c) **営業KPI 専用の `ClientOptions`(間隔 400 ms 前後、タイムアウト 30 秒、retry 6 回)の別インスタンス**。別インスタンスにするとゲートが別になり、CRM は 1 回/秒、営業KPI は 2.5 回/秒、合計 3.5 回/秒で 5 回/秒の上限に収まる(両方が同時に最大で動くとき)。ただし並走期間中は Python(4.5 回/秒)が同じ鍵で動くので、合計が 5 を超える時間帯ができる(第 5 章)。

### 4-2. トークン・scopes・Render の状態

- 営業KPI の直読みに要る読み取り権限(**【推測】** HubSpot の標準的な scope 名): `crm.objects.deals.read`(Search とプロパティ)、`crm.objects.owners.read`(Owners、退職者を含む)、`crm.schemas.deals.read`(パイプライン定義)。Python の `sync_daily.py` が同じエンドポイントを既存の鍵で叩いて成功しているので、**GitHub の Secret `HUBSPOT_TOKEN` の鍵には足りている**。
- **【未確認】(ブロッカー候補)**: Render の `HUBSPOT_ACCESS_TOKEN` に実際に値が入っているか。`docs/architecture/headless-crm-integration-plan.md` は「`render.yaml` で宣言したが実サービスには未設定」と書いている(2026-10 初め)。Render の鍵と GitHub Secret の鍵が同じか、Render の鍵に上の 3 scope があるかも未確認。値を見ずに確かめるには、`/api/crm` の疎通か、Render のダッシュボードで env 名の有無だけを見る。
- 同じ鍵を使う consumer: 今日の HubSpot 使用量は約 36,000 回で、営業KPI(約 1,800 回/回 × 2 回未満)より桁違いに多い。**同じ鍵(同じ 5 回/秒の Search 枠)を他のバッチも使っている【推測】**。

### 4-3. Rust の `classify()` と Python の写し

`src/handlers/sales_kpi/mod.rs` の `classify()` が正で、Python の `sync_daily.py`(1216 行付近)は「週次シートだけは集計済みの値を持つ」ための**写し**。冒頭のコメントどおり、片方だけ変えると週次だけ数字がずれる。**週次を Rust に移すと、この写しが消える**(それ自体が移行の利点)。週次のロジックは `weekly_cells()`(約 110 行)・`week_cells()`・`classify()` の周辺で、Rust 側には週の窓の数え方が部分的に無い **【推測】**。

### 4-4. 受け側のデータ構造

`Sheets` は 11 個の `Arc<SheetData>`(`header: Vec<String>`、`rows: Vec<Vec<Arc<str>>>`)と `all_cached` で、`build_payload(&Sheets, today)` が純粋関数(I/O なし)。`fixture.rs` が TSV から同じ `Sheets` を組む実績がある。**HubSpot 直読みは「`Sheets` と同じ列名・同じ文字列表現の `SheetData` を組む関数」を足すだけで、`build_payload` と JSON の形は 1 バイトも変えずに済む**(第 5 章)。

## 5. 設計案: 段階 1(画面だけ HubSpot 直読み)

### 5-1. 構造

```text
GET /api/sales-kpi/data
  └─ SALES_KPI_SOURCE = sheets(既定) | hubspot
       ├─ sheets  : 現行(load() が 11 シートを読む)
       └─ hubspot : HubspotSource が 6 ブロックを SheetData に組む
                    (商談/アポ/Cヨミ/決定者当日) (メンバー) (架電リスト)
                    (担当別) ← 以上を直読み
                    (架電日次/週次/決定者履歴/リスト在庫) ← 段階 1 ではシートのまま読む
  └─ build_payload(&Sheets, today)   ← 変更しない
```

- 新しい `hubspot_source.rs`(仮)に、Python の `deal_row()`・`member_rows()`・`kaden_list_rows()`・`kaden_by_owner_rows()`・`kettei_rows()` と同じ出力(同じ列名・同じ文字列表現: 日時は `yyyy-MM-dd HH:mm` JST、`事前アンケート` は「有」または空、など)を返す純粋関数を置く。**純粋関数にしておけば、記録した HubSpot の応答と、既存の TSV fixture(`tests/fixtures/sales_kpi/`)で突き合わせられる。**
- `Sheets` の組み立ては「直読みのブロック + シートのブロックの混成」になる。時点がずれる(カードは今の値、週次表は朝 6:30 の記録)が、現行でも週次は記録時点のものなので、新しい種類のずれではない。画面のブロックごとに「いつ取ったか」を出す(5-4)。

### 5-2. キャッシュ(TTL・初回・`?refresh=1`・二重取得の防止)

ブロックごとに別の TTL と取り方にする。**1 秒 1 回の現行ゲートでは、担当者別だけで約 7 分かかる**ので、リクエストの最中に取る作りにしない。

| ブロック | 呼び出し(見積) | 新鮮とみなす時間 | 更新の仕方 |
|---|---|---|---|
| A: 商談・アポ・Cヨミ・決定者(当日) | 約 25 | 5 分 | 期限切れ後の最初のリクエストで **背景更新を 1 本起動**し、**その間は直前の値を返す**(stale-while-revalidate)。画面に経過時間を出す |
| B: メンバー(Owners + 名簿 + 集計除外のシート) | 約 6 | 60 分 | 同上 |
| C: 架電リスト(全社・ステージ別) | 約 27 | 15 分 | 同上 |
| D: 架電リスト担当別 | 約 430 | 30 分 | **背景のみ**(2.5 回/秒で約 3 分)。リクエストでは起動しない |
| (リスト在庫・週次・架電日次・決定者履歴) | | 現行どおり(シート、TTL 60 分) | 段階 1 は変えない |

- **同時アクセスで二重に叩かない**: ブロックごとに single-flight(進行中の更新があれば、後から来たリクエストはそれを待つか、直前の値を受け取る)。`SheetStore::get` の「書き込みロックを取り直して再確認」と同じ考え方。
- **デプロイ直後の初回**: メモリは空。A・B・C を同期で取る(約 40 回、2.5 回/秒で約 16 秒)。その間は画面に「HubSpot から取得中」を出す。D は背景で取り、**取れるまでは「取得中」と出す**(0 件に見せない。ペイロードは担当別が空でも通る作りだが、「空 = 0 件」と見えないように状態を別に持つ)。**main へのマージ = Render 自動デプロイ**なので、デプロイのたびに D の約 430 回が発生する。1 日に何度もデプロイする日は D だけで数千回になる。段階 2a で保存先ができれば直近値から立ち上がれるようにする(ここは段階 1 の弱点として明記)。
- **`?refresh=1`**: A・B・C だけを捨てて読み直す(約 60 回・約 25 秒)。**同じ鍵への連打を防ぐため、直前の強制更新から 60 秒以内は無視し、その旨を応答に書く**。D・リスト在庫は `refresh` の対象にしない(管理者専用の別指定にする)。現状は `refresh=1` で全 11 シートを捨てる作りなので、挙動を変える点として明記する。
- **メモリ**: Render の過去の OOM 対策(CLAUDE.md に 512MB の言及。現在のプランのメモリは**【未確認】**)に配慮し、取引を丸ごと保持せず、ページごとに集計して捨てる(商談 2,316 行は保持してよい)。リスト在庫を段階 2a で持つときは、(リスト, 担当者, 企業人数の帯, 名前の真偽)をキーにしたカウンタ(数千キー)だけを持つ。

### 5-3. レート上限と共有

- HubSpot の Search は **5 回/秒(アカウント単位)** **【推測: 公式の標準値。現行クライアントのコメントも同値】**。別枠で 1 日 625,000 回、10 秒あたり 190 回(**【確認済】** ヘッダ)。
- 同じ鍵を共有するもの: CRM(`/api/crm/*`、1 回/秒)、営業KPI(新規、2.5 回/秒)、**Python の日次同期(並走期間中は 4.5 回/秒)**、他のバッチ **【推測】**。並走中にアプリの背景更新と Python が重なると合計が 5 を超えて 429 が出る。対策: ① 並走期間は Python の朝の便(約 8 分)とアプリの D 更新が重ならない時刻にする(Python が実際に始まる 8:20〜10:00 JST を避け、アプリの D・A・B・C 背景更新は TTL どおり回すが、Python 実行の最初の 10 分は 1 回/秒に落とす、など)。② 429 は `Retry-After` に従う(既存の実装どおり)。③ 429 が出た回数をログと画面の状態に出す。
- 1 日の増加量: A(25 回 × 5 分おきの更新 = 営業時間の画面を開いている間だけ)、B・C、D(約 430 回 × 30 分おき × 営業 12 時間 = 約 10,000 回/日)。1 日上限の 625,000 回に対して 2% 未満。ただし D を 30 分ごとに取り続けるのは重い。**D の TTL は 60 分、かつ画面を開いている人がいる間だけ更新する**ことを推奨(判断 J4)。

### 5-4. 失敗時の表示(シートに黙って戻さない)

- ペイロードに `source` を追加する(`SalesKpiData` に 1 フィールド、ts-rs の型と旧画面・React 画面の両方に反映): ブロックごとに `{ state: ok | stale | loading | error, fetched_at, error_kind }`。`error_kind` は `rate_limited` / `server_error` / `timeout` / `unauthorized` / `forbidden`(HubSpot クライアントの `HubSpotError` の分類をそのまま使う。**応答本文は載せない**)。
- 更新に失敗したら **直前の成功値を出し続けつつ、画面に「HubSpot からの更新に失敗(最後の成功 HH:MM)」を赤で出す**。**成功値が 1 度も無い場合(デプロイ直後に失敗)は 503 と理由**。**自動でシート読みに切り替えない**(2 つの時点のデータが混ざり、画面内で数字が食い違うため)。シートに戻すのは `SALES_KPI_SOURCE=sheets` を運用者が手で設定したときだけ。
- 401 / 403(トークン・scope)は「HubSpot の権限」と明示。起動時に何も通信しない現行方針(`main.rs` のコメント)は保つ。

### 5-5. 旧新一致の検証

1. **構造の一致(単体)**: 記録した HubSpot の JSON(商談 1 ページ分など)から作った `SheetData` が、同じ材料から `sync_daily.py` が書いたシートの TSV と**行・列の値で一致**すること(日時の JST 変換・`事前アンケート`・商談種別の内部値・チームの優先順位)。テストは具体値で。
2. **同時点の一致(実データ)**: Python の実行完了直後(`取得時刻` 以降)に、アプリの `?source=hubspot`(管理者のみ)で組んだ payload と、シート由来の payload を取り、**値で突き合わせる**ツールを用意する。HubSpot は動き続けるため、差は `hs_lastmodifieddate` が Python の取得時刻より後の取引だけで説明できなければならない(説明できない差を 0 にする)。既存の `scripts/sales_kpi/compare_rust_python.py` と `verify_sheets.py` の方式を踏襲。
3. **合格基準(案)**: 5 営業日の並走で、`商談 / アポ / Cヨミ / メンバー / 決定者(当日)` は dealId 集合と全列が一致(説明できる差のみ許容)、`架電リスト` と `担当別` は件数が一致(取得中に動いた分は取得条件に出す)、payload の全フィールドが一致。月をまたぐ日と月曜(週の入れ替わり)を各 1 回含めること。
4. 並走中は `SALES_KPI_SOURCE=sheets` が既定。`hubspot` は管理者の `?source=hubspot` でのみ見る。

### 6-3. 週次・日次スナップショットの保存先(比較と推奨)

保存が要るデータ: 週次(週 1 行 × 約 40 列)、決定者履歴((日付, 担当者) 行。10 日で 438 行、1 日 約 40 行)、Zoom 架電日次(3,321 行)、リスト在庫(再構築可だが 5 分かかるのでキャッシュ代わりに残す)。1 年でも数万行。**量は小さい**。

| 案 | 長所 | 短所・リスク |
|---|---|---|
| **A. 既存スプレッドシートにアプリから書く** | 形式が現行と同じなので Rust の読み取り(`SheetData`)も過去の行(週次 4 週・架電 3,321 行・決定者 438 行)もそのまま使える。人が見て直せる。新しいインフラも DB 書き込みも不要 | 書き込み権限が要る: **現行 `SheetsClient` は `spreadsheets.readonly` スコープ** **【確認済】**。Render のサービスアカウントにスプレッドシートの編集権限があるかは **【未確認】**(Python は同じ種類の鍵で書けている)。サービスアカウントは 125 枚の既存シートに書ける権限を持つことになるので、**コード側で `KPI営業_` 以外を拒否する**(Python の `sync_daily.py` と同じ防護)。読み書きの競合(Render のデプロイ中は旧新 2 つのプロセスが重なる)は、キー(週・日付)で上書きする冪等な書き方で受ける。Sheets の書き込みは 1 分あたりの上限がある |
| **B. audit Turso に表を足す** | 型とキーで管理でき、(週)・(日付, 担当者)に一意制約を付けられる。トランザクションがある。`headless-crm-design` の未決事項(Pending Sync Queue の保存先候補)とも合流できる | **DB への書き込み・表の作成はユーザーの実行のみ**(CLAUDE.md の絶対ルール。過去に 2026-01 に $195 超過請求)。audit DB は 1 年で削除する運用(`purge_old_activity`)なので、保持期間の扱いを分ける必要。人が見て直しにくい。過去の行の取り込み(シート → Turso)が別途要る |
| **C. `reclog-analytics` Turso(consulting-snapshot が使っている)** | Python が既に同じ型の「日次の台帳」を積んでいる前例(`consulting_snapshot`)がある | HR_HR は現在この DB に接続していない **【未確認】**(env とクライアントが増える)。B と同じ書き込みのルール |
| D. Render のローカルファイル / ディスク | | デプロイのたびに消える(永続ディスクは別契約)。単一インスタンス前提。却下 |
| E. HubSpot のカスタムプロパティ・カスタムオブジェクト | | HubSpot を週次の台帳にするのは ADR-005/006 の趣旨(独自の台帳を作らない)に反し、スコープも増える。却下 |

**推奨: A(段階 2a の着手時)**。理由は、過去の履歴がそのまま使える(移行ゼロ)、人が見て直せる、DB 書き込みのルールに触れない、読み取りの形を変えなくてよいため。**前提は 2 つ**: ① サービスアカウントの編集権限の確認(未確認)、② 書き込みを `KPI営業_*` に限定するガード。①が満たせない、または Sheets の書き込み競合が実際に問題になった場合は B(audit Turso)へ切り替える。その切り替えを後からでもできるよう、保存先は `SnapshotStore` という小さな trait(`get_weekly` / `upsert_weekly` / `append_kettei`…)の裏に置く。

スケジューラ: アプリ内(`tokio`)で JST の朝(例 06:30)・夕(18:00)を起点に動かす。Render の再起動をまたぐので、**起動時に「当日分が無ければ追いかけて実行する」**(catch-up)と、キー(週・日付)での上書きで冪等にする。`cs_dashboard::prefetch` と audit の 24 時間 purge に同種の実装が既にある。GitHub の cron の遅延(第 1-4 章)は消える。**失敗の通知は現在 Actions の赤い実行に頼っている**ので、アプリ内では画面の鮮度表示と、Slack 通知(Render に Slack の鍵があるか **【未確認】**)で代える必要がある。

### 6-4. 移した後に Actions の workflow をいつ・どう止めるか

並走期間を置き、旧新の一致を値で確認してから、依存の少ないほうから止める。

| 順 | 時期 | 操作 | 戻し方 |
|---|---|---|---|
| 1 | 段階 1 の切り替え後 1〜2 週間 | Hubspot リポで `sync_daily.py` に `--skip-owner-counts` を足し、担当者別だけ止める(朝 7 分に) | フラグを外す |
| 2 | 段階 2a の影武者運用(アプリは並走して**別名の**シート/表に書く。本物には書かない)5 営業日、月曜 1 回を含む | アプリの週次・決定者・在庫を Python の本物と**値で**突き合わせる。**週次は先週ぶんの入れ直し(「週_」列)と今週ぶんの両方**を比べる | 影武者を止めるだけ |
| 3 | 一致を確認したら | 画面の読み取りを「アプリの保存先」へ切り替え(`SALES_KPI_SOURCE` とは別の env で週次の出どころを切り替え)。**Python の `--skip-weekly`**(週次の二重書き込みを避けるため、先に Python の週次を止める) | env を戻す。Python の週次は dispatch で再開できる |
| 4 | 1〜2 日後 | Python を `--skip-shodan` 相当(HubSpot 取得をすべて止める)にする。夕方の便は既に `--skip-shodan` | フラグを外す |
| 5 | 段階 2b の並走が一致したら | `sales_kpi_daily.yml` の **schedule をコメントアウトする**。他の workflow と同じ流儀で、冒頭に「いつ・なぜ止めたか・再開手順・止めると何が止まるか」を書く。**workflow_dispatch は残す**(手動フォールバック) | コメントを外す |
| 6 | さらに 2 週間 | 問題が無ければファイルを削除する(履歴は git に残る)。`KPI営業_*` のシートは**削除しない**(履歴の保存先 A では本体) | git から戻す |

- **止める順番の根拠**: 週次が他のシート(商談・アポ・Cヨミ・架電日次・架電リスト・メンバー・在庫)を読むので、先に週次を止めて(3)から HubSpot の書き込みを止める(4)。逆にすると、週次が古いシートから計算する。
- 止める前に必ず影響範囲を出す(`call_quality_daily.yml` の教訓: 止めてから「相乗りしていたもの」が止まることに気づいた)。`sales_kpi_daily.yml` は `verify_sheets.py` も回しているので、止める前にそれが見ていた項目(既存シートに触れていないことなど)を画面の鮮度表示とアプリ側のテストで代替する。
- 並走中の二重書き込み: 影武者は別名で書くため、**本物のシートに Python とアプリが同時に書く期間を作らない**。
