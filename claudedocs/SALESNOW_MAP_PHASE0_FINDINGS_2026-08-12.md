## 結論

**条件付きで使える。** ただし守るべき条件が 5 つあり、うち 2 つは既存実装に現存する不具合である。

| | 判定 | 根拠 |
|---|------|------|

| 欠損率 | ✅ 十分 | 人員推移 96.3%、住所からの市区町村特定 99.1%、両方揃う 95.6% (§3) |

## 1. `employee_delta_*` の単位 — 実データで確定した

事故歴 2 回 (2026-04-30 / 2026-05-14) のある項目のため、カラム名・仕様書・既存コードを一切信用せず、
**実値の分布のみ**から判定した。

### 1.1 判定方法

従業員数は整数である。したがって「増減人数」が整数になる解釈だけが正しい。
4 つの解釈それぞれで増減人数を復元し、整数になる割合を測った。
丸め誤差の影響を避けるため `employee_count` 10〜1,000 人の 129,758 社に限定。

| 解釈 | 増減人数の式 | 整数になる割合 (±0.02) |
|------|-------------|----------------------|
| **A. 対過去比 %** `d=(現在-過去)/過去×100` | `now × d / (100 + d)` | **98.9%** |
| B. 対現在比 % `d=(現在-過去)/現在×100` | `now × d / 100` | 7.1% |
| C. 対過去比 比率 `d=(現在-過去)/過去` | `now × d / (1 + d)` | 6.9% |
| D. 人数そのもの | `d` | 9.4% |

(ランダムな連続値なら 4% 前後になるのが基準線)

規模別に見ると解釈 A の一致はさらに明確になる。丸め誤差が最も小さい小規模帯で 100.0%。

| `employee_count` | 社数 | 解釈 A | 解釈 B |
|------------------|------|--------|--------|
| 10〜50 人 | 79,276 | **100.0%** | 1.3% |
| 50〜100 人 | 23,845 | 99.9% | 18.8% |
| 100〜300 人 | 19,282 | 99.9% | 14.1% |
| 300〜1,000 人 | 7,352 | 81.5% | 12.1% |

(300 人以上で A が下がるのは、`d` が小数第 2 位で丸められているため大企業ほど丸め誤差が
±0.02 人を超えるだけであり、解釈の誤りではない)

### 1.2 独立した補強証拠 2 つ

**証拠 2: 分布の下限が厳密に -100 で、上限に制約が無い**

| 列 | 最小値 | 最大値 | `= -100` ちょうど | `< -100` |
|----|--------|--------|------------------|----------|
| `employee_delta_1m` | -100.00 | 1,800.00 | 122 | **0** |
| `employee_delta_3m` | -100.00 | 48,600.00 | 669 | **0** |
| `employee_delta_6m` | -100.00 | 3,300.00 | 1,112 | **0** |
| `employee_delta_1y` | -100.00 | 520,900.00 | 1,919 | **0** |
| `employee_delta_2y` | -100.00 | 138,900.00 | 2,996 | **0** |

対過去比なら現在人数 ≧ 0 より `d ≧ -100` が数学的下限で、上限は無い。観測はこれに完全に一致する。
対現在比なら逆に上限が +100 になるはずだが、`d > 100` の企業が 667 社存在するため成立しない。

**証拠 3: `d = -100` の企業は全社 `employee_count = 0`**

`employee_delta_1y = -100` の 1,919 社は、`employee_count` が **100.0%** ちょうど 0 だった。
対過去比の定義 (過去にいた全員が居なくなった → 現在 0 人) と完全に整合する。

### 1.3 確定した仕様

```
employee_delta_{1m,3m,6m,1y,2y} = (現在の従業員数 - N期間前の従業員数) / N期間前の従業員数 × 100
単位: パーセント (5.0 = +5%)
分母: 過去時点 (対過去比)
値域: -100 以上、上限なし
増減人数の復元式: employee_count × d / (100 + d)
```

**復元式の妥当性検証** (203,380 社が復元可能 = 全体の 95.4%):

- 復元した増減人数の整数からのズレ: 最大 **0.4983** (小数第 2 位丸めに由来する範囲内)
- 復元した 1 年前の従業員数が負になった企業: **0 社**
- 全国合計: 1 年前 22,358,692 人 → 現在 22,646,032 人 (純増 **+287,341 人 / +1.29%**)

### 1.4 既存コードの 3 層 grep — 単位の扱いは一貫していた

| 層 | 箇所 | 実装 | 判定 |
|----|------|------|------|
| データ層 | `company/fetch.rs:333`, `jobmap/company_markers.rs:73,74,91,92` | `employee_count * delta / (100.0 + delta)` | ✅ 解釈 A と一致 |
| 計算層 | `company/fetch.rs:903,929-933,1232,1264-1270` | 閾値 `10.0` `5.0` `-5.0` `±300` | ✅ % 単位前提で一貫 |
| 表示層 | `company/render.rs:238-251,350-354,996-1019`、`static/js/companymap.js:113-117`、`static/js/laborflow.js:111,241` | 生値をそのまま `%` 表示 | ✅ `×100` は無し |

**100 倍ずれの再発は無い。**

あわせて、`docs/audit_2026_04_24/deepdive_d2_survey_report.md` Q2.2 で
「`employee_delta_1y` の定義 (対過去比 vs 対現在比) がベンダー仕様未確認。仮定が違えば全 net_change 値が誤り」
と残されていた未解決事項は、本実査により **対過去比で確定** した。
既存の `net_change` 式は正しい。

## 2. 既存実装に現存する不具合 2 件

どちらも今回の新機能が同じ列を地域集計するため、そのまま踏襲すると同じ誤りを引き継ぐ。

### 2.1 🔴 単純平均 `AVG(employee_delta_1y)` の外れ値汚染 — 画面に出ている

**該当**: `company/fetch.rs:334`、`jobmap/company_markers.rs:75, 93` (いずれも値域フィルタ無し)
**表示先**: `static/js/laborflow.js:111` 「平均変動率: +○○%」、`company/render.rs:997` 地域平均、`api_v1.rs:296`

`employee_delta_1y` は平均 3.28 に対し**標準偏差 1,150.3**。1 社の外れ値が地域平均を破壊する。

都道府県 × 業種 1,230 セル (n≥5) を検査した結果、単純平均と人数加重の増減率の乖離:

| 乖離 | 値 |
|------|-----|
| 中央値 | 1.4 ポイント |
| p95 | 7.3 ポイント |
| p99 | 20.4 ポイント |
| **最大** | **750.1 ポイント** |
| 10 ポイント超のセル | 37 (3.0%) |

**最悪ケース (現に API が返している値)**:

| 都道府県 | 業種 | 社数 | 単純平均 | 中央値 | 人数加重 | セル内最大値 |
|---------|------|------|---------|--------|---------|-------------|
| 東京都 | 人材・アウトソーシング | 696 | **+752.7%** | +1.2% | +2.6% | 520,900 |
| 静岡県 | エンタメ・娯楽 | 25 | +58.7% | 0.0% | +1.1% | 1,500 |
| 高知県 | 医療・製薬・福祉 | 9 | +56.5% | +2.6% | +2.9% | 500 |

原因は 1 社 —「株式会社インディードリクルートパートナーズ」(東京都、`employee_count` 5,210、
`employee_delta_1y` 520,900)。復元すると 1 年前 1 人 → 現在 5,210 人。
値そのものは定義上正しいが、696 社の平均を単独で +752.7% に押し上げている。

`employee_delta_1y > 1000%` の 24 社を調べると、13 社が「1 年前 1 人以下」だった。
外れ値の正体は新設・実体化した法人であり、地域の人員動向を語る材料にはならない。

**対処**: 地域集計に単純平均を使わず、人数加重 (増減人数の合計 ÷ 過去の従業員数合計) を用いる。
既に `pick_band` では `in_realistic_range` (±300%) が使われているが、`AVG` の 3 箇所には適用されていない。

### 2.2 🟡 `CAST(... AS INTEGER)` の切り捨てによる系統的な過小評価

**該当**: `company/fetch.rs:333`、`jobmap/company_markers.rs:73, 74, 91, 92`

SQLite の `CAST(real AS INTEGER)` は四捨五入せず 0 方向へ切り捨てる。
増減人数の真値は整数だが、浮動小数点演算の結果は 2.9983 のような値になるため 1 人分が落ちる。

| | 値 |
|---|-----|
| 真値 (四捨五入) の全国合計 | 287,341 人 |
| `CAST` (切り捨て) の全国合計 | 285,339 人 |
| 差 | **-2,002 人 (-0.7%)** |
| 1 人ずれた企業 | **66,794 社 (32.8%)** |
| ├ 増加側で -1 された | 34,398 社 |
| └ 減少側で +1 された | 32,396 社 |

増加も減少も絶対値が縮む方向のバイアス。全国合計では -0.7% だが、企業数の少ない市区町村では
社数に比例して効くため無視できない。**対処**: `CAST` を `ROUND` に置き換える。

## 4. ⚠️ `collated_at` — 時点が揃っていない

これが本データ最大の弱点である。

| 項目 | 値 |
|------|-----|
| 範囲 | 2025-11-10 〜 2026-07-13 |
| 幅 | **244 日** |
| ユニーク日数 | 161 日 |
| 最頻日 2025-11-10 | 116,192 件 (54.5%) |
| 2025 年内の収集 | 172,627 件 (81.0%) |
| 2026 年の収集 | 40,282 件 (18.9%) |

`employee_delta_1y` の「1 年前」は `collated_at` 起点である。したがって同一の地域集計の中に
**「2024/11 → 2025/11 の増減」と「2025/07 → 2026/07 の増減」が混在する**。

ただし収集月ごとの水準差は小さい。中央値はすべての月で 0.00、平均は 1.22〜4.57 の範囲。
月ごとに極端な段差は観測されなかったため、混在が結果を大きく歪める兆候は今のところ無い。

**運用上の帰結**:
- 「◯年◯月〜◯年◯月の増減」とは書けない。**「2025 年 11 月時点を中心とする直近 1 年」**のような表記に留める必要がある
- 「この地域は今こうなっている」という現在形の断定はできない。8 割は 2025 年末時点の姿である
- 時系列の比較 (前回集計との差分) には使えない

## 5. ⚠️ 地域集計に耐える件数か

市区町村を 1,855 拾えた (`employee_delta_1y` 保有企業ベース)。1 市区町村あたりの社数:

| 分位 | 社数 |
|------|------|
| p10 | 5 |
| p25 | **14** |
| p50 (中央値) | **46** |
| p75 | 115 |
| p90 | 284 |
| 最大 (港区) | 3,016 |

| 閾値 | 該当市区町村 | 割合 |
|------|------------|------|
| 5 社未満 | 161 | 8.7% |
| 10 社未満 | 333 | 18.0% |
| **30 社未満** | **751** | **40.5%** |
| 50 社未満 | 976 | 52.6% |
| 100 社未満 | 1,328 | 71.6% |

**業種 × 市区町村まで割ると成立しない**: 25,771 組合せのうち中央値 3 社、
30 社以上あるのは **1,412 組合せ (5.5%)** のみ。

**1 社依存度**: 企業数 30 社以上の市区町村 1,101 件で、増減量の最大 1 社が地域全体に占める割合は
中央値 15%、p90 で 37%。**1 社で 50% 以上を占める市区町村が 58 件 (5.3%)** ある。

企業数を増やすと地域増減率の暴れは収まる:

| 閾値 | 市区町村数 | p5 | p50 | p95 | 最大 |
|------|-----------|-----|-----|-----|------|
| n≥1 | 1,855 | -5.8% | +0.6% | +6.0% | +159.2% |
| n≥30 | 1,101 | -2.6% | +0.8% | +4.7% | +62.2% |
| n≥100 | 523 | -1.7% | +0.8% | +4.0% | +13.5% |

**運用上の帰結**: 市区町村単位の人員推移は **30 社以上**を表示条件とし、
下回るセルは値を出さず「企業数が少なく傾向を示せない」と明示すべき。
業種 × 市区町村の掛け合わせは都道府県単位に留めるのが現実的。

## 6. 住所と地図配置 — フェーズ1 は成立する

### 6.1 住所からの市区町村抽出: 99.1%

`prefecture` + `address` の先頭一致で `master_city.csv` の市区町村名を貪欲マッチ。

| | 件数 |
|---|------|
| 抽出成功 | 211,263 (99.1%) |
| 抽出失敗 | 1,646 (0.8%) |
| `address` が空 | 236 (0.1%) |

**抽出失敗 1,646 件は全件が浜松市**で、原因が特定できた。
`src/geo/master_city.csv` は浜松市を旧 7 区 (中区/東区/西区/南区/北区/浜北区/天竜区) で保持しているが、
企業データの住所は 2024-01-01 の行政区再編後の 3 区 (中央区/浜名区/天竜区) を使っている。
**master_city.csv 側の更新漏れ**であり、修正すれば 99.9% まで上がる。

### 6.2 重心座標への配置: 91.3%

`municipality_centroids.csv` (1,959 行 = 市区町村 1,784 + 区 128 + 都道府県 47) と突き合わせた。
郡プレフィックスの除去 (既存の `strip_county_prefix` と同じ規則) を適用済み。

| 状態 | 社数 | 割合 |
|------|------|------|
| 名前が一意に一致 | **194,514** | 96.4% |
| 同名衝突の可能性あり | 5,889 | 2.9% |
| centroids に存在しない | 1,402 | 0.7% |

**機械的な突合だけで 213,145 社中 91.3% が置ける。**

**「同名衝突の可能性あり」5,889 社は、座標を確認したところ実際には正しく解決できる。**
該当は東京都の港区 (2,989) / 中央区 (2,538) / 北区 (362) の 3 件のみ。
`municipality_centroids.csv` に都道府県列が無いため、名古屋市港区・大阪市中央区などとの
衝突を機械的に排除できず保守的に倒した判定だった。実際の座標は以下の通りで、素の区名は
東京 23 区として一意に格納されている (政令市の区は「札幌市中央区」の完全形と「白石区」の
素形が混在するが、いずれも特定の区役所座標を 1 件だけ持つ)。

| centroids の `name` | lat | lon | `source_name` | 実体 |
|--------------------|-----|-----|--------------|------|
| 港区 | 35.6581 | 139.7516 | 港区役所 | 東京都港区 ✓ |
| 中央区 | 35.6706 | 139.7720 | 中央区役所 | 東京都中央区 ✓ |
| 北区 | 35.7528 | 139.7337 | 北区役所 | 東京都北区 ✓ |
| 白石区 | 43.0454 | 141.3964 | 白石区役所 | 札幌市白石区 ✓ |

したがって**実質的に配置できるのは 200,403 社 = 全体の 94.0%**。

**「centroids に存在しない」1,402 社 / 62 市区町村は、同名衝突ではなく単純な収録漏れ**だった。
府中市・伊達市・松前町・森町・太子町・丹波篠山市はいずれも centroids に **1 件も存在しない**
(重複していて 1 件に潰れているのではない)。内訳上位は府中市 (東京 223 社 / 広島 100 社)、
伊達市 (福島 74 社)、糟屋郡須惠町 (52 社)、丹波篠山市 (52 社)、伊予郡松前町 (51 社)。

**フェーズ1 の判断**: ジオコーディング無しで **94.0%** を配置できる。
残る 1,402 社 (0.7%) は 62 市区町村の重心を centroids に追記すれば解消する (作業量小)。
将来の同名衝突を防ぐため、あわせて都道府県列を追加しておくのが望ましい。

## 8. フェーズ1 に進む場合の必須条件

| # | 条件 | 理由 | 状態 |
|---|------|------|------|

## 9. 実装した対策 (2026-08-12 追記)

§8 の条件 1・2・3 と、新たに判明した 3b をコードに落とした。
実装は `src/handlers/region_headcount.rs` に集約し、17 本のテストで逆証明している。

### 9.1 追加で判明したこと: 人数加重にするだけでは足りない

§8 条件 1 (単純平均 → 人数加重) を守っても止まらないケースがある。

山梨県南都留郡道志村 (9 社) の実測値:

| 指標 | 値 |
|------|-----|
| 単純平均 `AVG(delta)` | +36.08% |
| **人数加重増減率** | **+159.17%** |
| 純増 | +573 人 (1 年前 360 人 → 現在 933 人) |
| 最大 1 社の増減 | +570 人 (株式会社加藤電器製作所、206 人 → 776 人) |
| 最大 1 社の占有率 | **98.4%** |
| その 1 社の `employee_delta_1y` | +276.70% |

この地域では**人数加重の方が単純平均より大きく出る**。加重は「大きい 1 社」の影響を
強めるためで、条件 1 は「分母の小さい企業の率が暴れる」問題しか解かない。
さらにこの 1 社の delta は +276.70% なので、既存の `in_realistic_range` (±300%) も通過する。

したがって**集中度を独立に測るゲートが要る**。条件 1 と条件 3b は別々の問題を解いている。

### 9.2 閾値の実測根拠

全国 1,855 市区町村の人数加重増減率の最大絶対値:

| 適用ゲート | 残る市区町村 | 最大絶対値 |
|---|---|---|
| (なし) | 1,855 | 159.2% |
| 企業数 ≥ 30 | 1,101 | 62.2% |
| **企業数 ≥ 30 かつ 最大 1 社 < 50%** | **1,043** | **9.2%** |
| 企業数 ≥ 30 かつ 最大 1 社 < 40% | 1,006 | 9.0% |
| 企業数 ≥ 50 かつ 最大 1 社 < 50% | 836 | 9.2% |

40% や 50 社まで厳しくしても改善しないため **30 社 / 50%** を採用した。
過去従業員数の下限ゲートは設けていない。企業数 30 社を課すと過去従業員数の最小が
491 人 (p1 = 810 人) になり、独立したゲートを足す根拠が実データに無いため。

ゲート通過後も市区町村の 56.2% が残り、**企業数の 92.3%・従業員数の 94.2%** をカバーする。
落ちるのは元々ほとんど企業が存在しない地域である。

### 9.3 半径集計が汚染されないようにした仕組み

`HeadcountAggregate` は率ではなく**人数**(現在・過去・増減・増減の絶対値合計・最大 1 社)
を保持する。半径◯km の集計は市区町村ごとの集計値を `merge` して作るため、
率を平均したときのような歪みが起きない。

最大 1 社は「各地域の最大の中の最大」であり全体の最大と厳密に一致するので、
合算後も集中度ゲートが正しく効く。逆に、半径を広げて十分な企業数が入り集中が解消すれば
表示できるようになる (テスト `radius_merge_can_show_when_concentration_resolves`)。

### 9.4 抑制した値を表示経路から到達不能にした

`displayed_rate_pct()` はゲートを通らなければ `None` を返す。呼び出し側が
判定を忘れて生値を描画する経路を作れないようにしてある
(生値が要る場合のみ `weighted_rate_pct()` を明示的に使う)。
値を伏せたときは `DisplayGate::notice()` が理由の日本語を返すので、
画面が「空欄」だけになって利用者に理由が伝わらない状態も避けている。

- 企業数不足: 「この範囲の対象企業は 9 社です。30 社に満たないため、地域の傾向としては示していません。」
- 1 社集中: 「この範囲の人員変動の 98% を 1 社が占めています。地域の傾向としては示していません。」

### 9.5 既存の地図タブに適用した

`/api/jobmap/labor-flow` (地図タブの「人材フロー」パネル) を差し替えた。

| | 旧 | 新 |

| JSON フィールド | `avg_delta_1y` (単純平均) | `headcount_rate_1y` (人数加重、抑制時 `null`) + `headcount_notice` + `top1_share_pct` |

`docs/openapi.yaml` の契約も更新済み。`laborflow.js` は `?v=4` に上げた
(`/static` は immutable 配信のため、上げないと更新が最大 7 日届かない)。

フロントとバックエンドのキー不一致 (2026-04-23 の 8 panel 全滅と同じクラスの事故) を防ぐため、
`global_contract_audit_test.rs` に両ソースを突き合わせるテストを追加した。

### 11.2 妥当だったもの (修正した)

**① `merge` のドキュメントが実装を先取りしていた**

`region_headcount.rs` は「半径◯km の集計は市区町村ごとの本構造体を `merge` して作る」と
現在形で書いていたが、**`merge` と `from_companies` は本番から 1 度も呼ばれていない**
(呼び出しは `from_parts` の 2 箇所のみ)。半径検索そのものが未実装のため。

念のため、地図タブの既存の半径検索が無ゲートで人員増減率を出していないかを確認した →
`jobmap/fetch.rs` は公的求人データのみを参照し、企業データを一切見ていない (grep 0 件)。
**抜け道は無い。** ドキュメントを現状に合わせて修正した。

**② `merge` の「最大 1 社は全体の最大と厳密に一致する」という無条件の断定が誤り**

これは**地域どうしが企業について互いに素な場合にのみ成立する**。同じ企業が 2 つの地域に
入ると、分母 `total_abs_change` だけ二重に積まれて分子 `top1_abs_change` は 1 社分のままなので、
集中度が**過小評価**される。つまり本来止めるべきセルがゲートを通る、安全側に倒れない誤り。

前提条件を doc に明記し、`merge_double_counted_company_underestimates_concentration` で
挙動を固定した (同じ地域を 2 回 merge すると占有率がちょうど半分になり、
77% → 38% でゲートを通ってしまうことを assert)。

**③ `ORDER BY net_change_1y DESC` が非決定的**

SQLite は同値の順序を保証しない。`net_change_1y` が同値になる業種の組は実データに **110 組**あり、
**37/47 都道府県**で発生する。小さな fixture で再現させたところ、インデックスの有無だけで
並びが完全に反転した。

```
tie-break なし: index 無し ['金融','製造','教育','建設','商社','IT']
                index 有り ['IT','商社','建設','教育','製造','金融']  ← 反転
tie-break あり: どちらも    ['IT','商社','建設','教育','製造','金融']  ← 一致
```

値は変わらないが、本番 Turso と手元で同じデータの画面が再現しない。
`ORDER BY net_change_1y DESC, sn_industry` に修正し、契約テストで固定した。

### 11.3 修正後の E2E 裏取り

tie-break 修正と型非依存性を、実 Rust サーバ経由で確認した。
経路は `HTTP → company_markers::labor_flow → get_i64 → HeadcountAggregate::from_parts → gate() → JSON`。

| 検証 | 規模 | 結果 |
|------|------|------|
| tie-break 修正前 (index 有無で並びが変わる都道府県) | 47 | **37 / 47** |
| tie-break 修正後 (同上) | 47 | **0 / 47** |
| 修正前後の値の比較 | 9,681 フィールド | **不一致 0** (並びだけ直り、値は不変) |
| REAL 版 DB vs INTEGER 版 DB (API 出力) | 9,681 フィールド | **不一致 0** |
| REAL 版 API vs Python 独立計算 | 1,383 セル | **不一致 0** |
| `total_emp` 全国合計 (REAL / INTEGER / SQL 直接) | 3 経路 | 22,048,050 で一致、差 0 |

`get_i64` は REAL の `SUM` を 1 人も落とさない。内部では float 分岐で
`as_f64().map(|f| f as i64)` の 0 方向切り捨てに落ちるが、全 1,383 セルの
`SUM(employee_count)` が厳密な整数 (非整数 0 件) のため切り捨てが効く場面が無い。

`ROUND` の 0.5 境界については、割れる double を網羅探索した結果 **`±0.49999999999999994` の 2 値のみ**で、
N≥1 では割れない。実データの最接近は危険域から **約 494 億 half-ulp** 離れている。

### 11.4 報告のみ (実害なしと判断、修正せず)

- **絶対値最大が複数社で同率のセルが 66 件**ある (例: 宮城県 生活関連サービス 51 社中 3 社が同値)。
  `top1_abs_change` は 1 社分の値なので集計は正しく、注記の「1 社が占めています」も
  誤りではないが、厳密には「最大 1 社と同率の社が他にもいる」ケース
- `net_change_3m` の `CASE WHEN employee_delta_3m > -100 ... ELSE 0` は
  `employee_delta_3m IS NULL` を「増減 0」に潰す。該当は 178,587 社中 **9 社 (0.01%)**、
  最悪セルでも欠測率 2.0%。旧実装 (`SUM` が NULL を読み飛ばす) と正味の挙動は同じ

### 11.5 未対応 (差分の外にある既存の課題)

`company/fetch.rs` には tie-break の無い `ORDER BY employee_count DESC LIMIT N` が
10 箇所以上ある。`LIMIT` 付きのため、同値が境界にあると**どの企業が表示されるか自体**が
環境で変わりうる。今回の差分の外なので手を入れていないが、同じクラスの問題として記録する。
