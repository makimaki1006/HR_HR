# 求人索引: 値を保持して本文の再取得を減らす（2026-10-16）

全件のページは本文なしで読み、本文の構造化項目は必要な求人だけ100件ずつ・最大4本で取得する。
HubSpotが正本。Rustの認可・Background優先度・共有送信間隔・gatewayを維持する。
#230の監査Tursoへの保存・復元を利用し、保存形式はv2にする。

Listingのそれ以外の値は、媒体ID・住所・公開状態・案の状態・CSV検出日・関連等の専用項目から作る。
検索、絞り込み、件数、カード、顧客表、職種・給与等の表示と並び順を維持する。
詳細のversions、選択比較、表示行の本文変更日の取得も維持する。
本文・画像・応募者情報を保存へ追加しない。保持するのは構造化した要約だけ。

## 取得と引き継ぎ

- 保存なしの初回: 掲載終了を含め全求人の本文を取得する。元々値が無いもの以外は未取得にしない。
- 掲載終了以外（掲載中・掲載前・不明）: 毎回本文を取得する。
- 前回も今回も掲載終了: 同じ求人ID・媒体・媒体側求人ID・アカウントで、前回に本文を取得済みなら本文由来の値だけを引き継ぐ。
- 新しく終了した求人、前回にない求人、前回の本文取得済み情報がない求人、掲載中に戻った求人、媒体の紐づけが変わった求人: 本文を取得する。
- 住所とAirWorkの専用項目は今回のページ値を使う。前回のsummary全体で上書きしない。

全件ページの既存項目には本文専用の更新日時がない。body_changed_atには本文履歴が必要で、全件取得の更新判定には使えない。
hs_lastmodifieddateは週次実績などの変更でも動くため、本文の更新判定には使わない。
**前提: 掲載終了になった後は本文を変更しない。** この前提のもとで、前回も掲載終了だった取得済み値を引き継ぐ。
掲載終了後にも本文を編集する運用がある場合、その編集は今回の引き継ぎでは検出できない。本文専用の更新指標が必要になる。

取得済みを表す内部のbody_summaryを保持する。Some（項目が全てnullでも本文を確認済み）とNone（本文を未取得）を区別する。
APIには返さず、#230のPrivateListingに含めて保存・復元する。公開summaryの本文由来値も従来どおり保持する。
v1保存にはこの取得済み情報がないため、v2では復元せず全件を取得する。保存前後・同一プロセスのどちらでも同じ引き継ぎ条件を使う。

本文補完の入力と応答のID集合・件数・errorsを検査する。部分失敗では新しい索引を公開せず、前回の完全な索引を維持する。

## 選択肢の比較

| 案 | 値の維持 | 転送量 | 判断 |
|---|---|---|---|
| 毎回全件ページで本文を取得（#230） | 維持 | 毎回全件分 | 比較の基準 |
| 終了求人の本文由来値を落とす（旧#231） | 終了求人の表示・並び順が変わる | 少ない | 利用者判断により不採用 |
| 値と取得済み情報を保存し、終了求人だけ引き継ぐ | 前提のもとで維持 | 初回は全件、以後は終了以外＋新しく終了等の差分 | 採用 |
| hs_lastmodifieddateで再取得する | 維持 | 週次実績変更でも再取得しやすい | 本文専用の指標でないため不採用 |

## 検証・計測

具体値（職種、時給、下限0・上限1800、9時〜17時、日曜）を両媒体で検査する。
保存なし、偽Tursoに保存・復元した索引、同じプロセスの前回索引、新しく終了した求人、再公開した求人を検査する。
空の本文の取得済みと未取得、紐づけ変更、AirWorkの専用項目と住所の更新も検査する。
保存の旧版・破損・期限切れの拒否は#230のテストを維持する。

偽HubSpotの41,000件、うち掲載終了以外3,000件。本文ありページ約1.60MB、本文なし約0.25MB。
本文は13,500 bytes/件で、職種・給与・時間・休日を含む合成文面にする。実データは使わない。
共有3,000,000 bytes/sの転送待ちを偽サーバに入れ、実HTTP、JSON解析、共有送信間隔、関連・取引取得を含める。
保存なし初回と、偽Tursoで保存・復元してからの作り直しを別々に測る。保存・復元そのものの時間は作成時間に含めない。
変更前はページで全本文を取得し、本文補完を行わない#230と同じ読み取り経路で測る。
時間・受信量・呼び出し回数と受信窓はPRと指定artifactsに記録する。受信窓は観測値で、通常のgatewayテストは別途実行する。
ローカルの帯域モデルであり本番時間の保証ではない。圧縮・ネットワークの揺れ・実際の本文長分布は再現していない。
