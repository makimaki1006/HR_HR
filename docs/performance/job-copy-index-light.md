# 求人索引の本文取得範囲（2026-10-16）

対象: `src/handlers/job_copy_live/listings.rs` の全件ページと行の生成。
HubSpot が正本、Rust が読み取りと認可を担当する既存の設計を維持する。
保存・復元と `start_worker` / `refresh` は別作業の範囲。

`Listing` の生成はこの表以外に本文を参照しない。本文は索引へ保存しない。
所在地フィルタも専用住所項目から生成する。ホーム `listing_home::compute` はsummaryを参照せず、公開状況・指定状態・関連・週次要約のみを使う。

掲載終了の本文由来列はnullとなり、画面に「未取得」を表示する。
給与などの列をソートすると、従来の取得値による順からnull同士のID順へ変わる（昇順では未取得が先、降順では後）。
一括職種指定の終了求人では本文由来の参考職種が出ないが、保存された職種と絞り込みは維持。
詳細の `/versions` と選んだ求人の `/listing-comparison` は従来どおり本文を読むので、終了求人も開けば全文・構造化項目を確認できる。
開いたことで索引のnullを更新する仕様は加えていない。

## 選択肢の比較

| 案 | 受信量 | 表示と機能 | 採否 |
|---|---|---|---|
| 全件の本文をページで取得（従来） | 約41,000件分 | すべての行の比較値を保持 | 起動時の転送負担が大きい |
| 軽いページ + 必要な求人をbatch read | 約41,000件の専用項目 + 対象約3,000件の本文 | 対象求人の比較値を維持。終了求人だけ影響を限定できる | 採用。明確な掲載終了だけ除外、状態不明も補完する |
| 本文由来summaryを索引から一律削除 | 最小 | 掲載中の比較表・給与ソート・参考職種も失う | 現在使われているため不採用 |
| 週次実績も削除 | さらに減る | ホームのカード・顧客表の応募/課金集計が変わる | 不採用 |

## 取得の制御

ページのID区間8本と境界検査は維持。区間の完了後に掲載終了以外を100件ずつ、最大4本で補完し、本文を破棄してsummaryだけ残す。
既存のBackground優先度・共有送信間隔130ms・gateway・ページ同様の局所再試行を使う。
入力ID集合と応答ID集合・件数・errorsを検査し、欠落・重複・別ID・エラーは全件完成として公開しない。
補完失敗は既存のrefreshに返り、前回のsnapshotを維持する。

## 計測手順

`listing_index_loading_tests::index_payload_latency_probe` を明示実行。
合成41,000件、うち3,000件が掲載中。実データ・外部認証情報は使用しない。
100件ページの本文あり約1.60MB / 本文なし約0.25MB、本文batchは約1.35MB。
偽サーバの応答全体に共有3,000,000 bytes/sの転送待ちを入れ、実HTTP・JSON解析・既存gateway/送信間隔・関連/取引取得を含めて測る。
これは帯域をモデル化したローカル計測であり本番所要時間の保証ではない。圧縮・ネットワークの揺れ・実際の本文長の分布は再現していない。
変更前は同じfixtureでorigin/mainのlistings.rsを使用する。結果はPRと指定artifactsに記録する。
