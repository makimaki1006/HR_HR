# 求人票作成から求人文面管理への案の保存

作成日: 2026-10-11。対象: `/app/jobgen`、`/app/job-copy`、求人オブジェクト `0-420`。

ユーザー承認: 案用の5項目は既に作成済み（2026-10-11 の引き継ぎ指示）。新しい定義は作らず既存を利用する。実際の求人への書き込みは検証では行わず、アプリでは明示的な保存・確認状態変更の操作に限る。

## 実装計画

1. 既存の求人一覧・本文の履歴・比較・給与の組み立てを使う。CRMのコードは変更しない。
2. 求人情報グループの既存5項目を使う。本文はRustの84列の順序で全項目を `列名：値` として保存する。未取得は空文字で保持し、表示で未取得とする。
3. `jobgen_draft_facts` は、事実・84項目・作成日時・元データの種類・案の識別子・確認状態をひとまとまりにしたJSON文字列。別項目の履歴時刻が一致するとは仮定せず、この情報の変更履歴から案を復元する。同じ識別子の状態変更は同じ案としてまとめる。同じ本文を再び保存した場合も別の案になる。生成日時と保存順は区別し、先に生成した案を後から保存した場合も現在値を最新の保存として扱う。
4. 明示操作 → Googleログインと求人文面管理の許可 → 書き込みの設定 → レコード単位のロック → 現在値を相乗りせず取得 → 競合検査 → 再送用台帳 → 共通のHubSpot関所を通すPATCH、の順で処理する。保存者は非公開のログと操作台帳に残す。
5. 一時障害は既存監査DBで再送を保持する。恒久エラー・競合は自動再送しない。再送でも競合・権限・無効化・書き込み設定を確認する。台帳が使えないときはHubSpotに書かない。未確認の結果を保存成功とは表示しない。
6. 最新の案は今の版との比較を最初に表示する。過去の案も版の選択肢に入れる。確認状態の変更は最新の案に限定し、掲載中の本文は変更しない。比較は全文で検知して列で特定し、元データの原文を開けるようにする。
7. 保存内容、認可拒否、競合、冪等性、再送、履歴、状態変更、文字の色付け、給与、全文と列の違い・元データの原文を具体値のモックで検証する。1440・1920幅の操作と1440幅の画像、既存検査、CIを確認する。

## ADR-019 — 求人の案の再送操作を既存監査DBの専用表に保持する

Status: Accepted for this implementation (既存の再送方式を求人の案に適用)。

- 現行の決定: ADR-005/006はHubSpotを正本にし、新しいDBを作らない。ADR-018は既存監査Tursoで未反映の操作を保持する。
- 問題: CRMの再送台帳・workerは取引向けの設定と認可を使う。求人の操作を混ぜると別オブジェクトに誤適用しうる。CRMの変更は今回禁止されている。
- 採用: 同じ監査DBに `job_copy_draft_operations` 表を追加する。これは求人の一覧・案の履歴ではなく、未反映操作と重複送信の防止だけに使う。履歴の正本はHubSpot。保存済み・失敗の操作は7日で削除し、保存者は非公開ログに記録する。
- 利点: 新しいDB・外部サービスを導入せず、再起動後も再送・重複防止が効く。既存CRMの処理に影響しない。
- 現行を保つ利点: CRMと同じ表・workerならコードが共通になるが、対象・認可・設定の拡張が必要となり、今回の範囲を越える。
- 戻すコスト: 表と求人の再送workerだけを廃止できる。HubSpotの案・比較は影響を受けない。
- 制約: レコードの直列化とworkerは既存と同じ単一インスタンス前提。件数・試行回数・保存受付を制限し、ポーリングでUPDATEしない。監査DB未接続なら保存を拒否する。新しい環境の接続先は作らない。

## プロパティと公式仕様

定義の正本は `src/job_gen/draft_properties.json`。グループは `tab_p_1_kyuujinjouhou`。説明はすべて「求人票作成の画面が書く。手で編集しない」。既存の同名定義は型・表示形式・グループ・選択肢を照合し、違いがあれば変更せず停止する。

[HubSpot公式のプロパティ仕様](https://developers.hubspot.com/docs/api-reference/legacy/crm/properties/guide)に従い、複数行本文はstring/textarea、日時はdatetime/date、状態・種類はenumeration/selectにする。文字列は65,536文字までに制限する。定義作成のスクリプトはプロパティAPIだけを呼び、求人レコード用のAPIは呼ばない。

案を作った日時は生成応答を受け取った日時を使い、後から保存・確認状態を変更しても変えない。

## 有効化と運用

`JOB_COPY_DRAFT_WRITES_ENABLED=true` または `JOB_COPY_DRAFT_WRITE_ALLOWLIST` に指定された求人に限って書ける（既定は停止）。さらに会社ドメイン (`ALLOWED_DOMAINS`) のGoogleログイン、無効化されていないアカウント、既存監査DBの接続がすべて必要。検証では実際の設定・求人への書き込みは行わない。

再送は1分・5分・30分・2時間・以降6時間、最大8回。新しい保留操作はworkerへ通知し、待ちがあるときは30秒ごと、ないときは10分ごとに読み取りのみで確認する。保存済み・失敗の掃除は1日1回。恒久失敗は保存結果の照会で表示し、操作者と結果は非公開ログに記録する。複数インスタンスでの排他は今回の対象外で、既存と同じ単一インスタンス前提。

## 比較方式の変更（2026-10-11 ユーザー指示）

従来は表示向けに組み立てた本文から給与・保険・手当などを取り出し、抽出事実と比べていた。見出しや改行の書き方による見落としを避けるため、全文で変更を検知し、列で特定する2段階へ変更する。事実との突き合わせ欄は削除し、保存済みの事実は比較に使わない。

検知は保存された本文の全文を使い、両端の空白と改行コードだけを揃える。内部の半角・全角スペース、数字、条件、段落は変更しない。表示用の求人票と判定用の全文を分けて保持する。変更がある場合だけ、共有の列定義と84列の保存形式の列名で値を対応付け、変わった項目の今の値・案の値を表示する。案は保存された84列の行データを直接使い、値の中の列名らしい行も分割しない。値は複数行のまま比較し、片方しかない項目は追加・削除、対応できない見出しはその他として残す。文字の色付けは既存の仕組みを使う。管理用の識別子の値は画面に表示しない。

元データの原文は既存の控えに追加して保存し、「元データを見る」で開く。文章・CSV・HTMLは取り込み前の本文を改変せず保持し、その他の形式は取得した求人原文を保持する。旧形式の控えも読み込めるよう追加項目を省略可能とし、保存されていない原文は未取得と表示する。新しいHubSpot項目は作らない。既存の文字数制限を超える場合は保存を拒否し、原文を切り詰めない。

全文の差を取りこぼさず、変更箇所を項目で確認できることが変更の利点。従来方式を維持する利点は抽出事実と掲載文を並べられることだが、今回はユーザー指示により優先しない。保存先・認可・再送・履歴の設計は継続し、旧い案の再保存は不要。比較方式を戻す場合は画面と検査を戻せるが、新方式の原文保存は互換性を保ったまま残せる。

具体値の検査は、夜勤手当3,500円/回の次の行への「（月4回まで）」追加、半角・全角スペース1文字、変更のない配送スタッフ・勤務時間の除外、独自の待遇の20,000円から10,000円への変更をその他に表示、列の追加・削除・空欄・順序変更、原文の改行と空白の保存、旧形式の読み込みを含む。今の版の複数行値に見出しの形の行がある場合も、案の行データと列の順序を使って境界を確認し、未対応の独立した見出しは本文の途中でもその他に残す。

## 全文表示と貼り付け原文の修正

列順や区切り文字だけが違う場合も「その他」の左右に全文を表示する。表示時には管理情報の値を隠し、列の表示名を整えるが、変更の検知は加工前の本文で行う。求人・店舗・職種の識別子について区切り文字だけの変更を検査し、案件名・仕事内容・応募資格の並び替えでも3列すべての本文が左右に残ることを検査する。文章・CSV・HTMLの貼り付けは空白だけの入力を拒否しつつ、先頭空白・末尾改行を削らず取り込む。
