# リクロジメディア向け求人案

更新: 2026-11-02 ユーザー決定を反映。対象は求人文面管理での生成・確認・CSV出力と、CSVを出すときのHubSpotへの求人の作成（下の「2026-11-02 の決定」）。案を作る処理そのものは、外部送信・HubSpotへの書き込みを行わない。

## 今回の設計変更

従来は数字の通常/研修・時刻の役割などの意味と文字3-gramの重なりを照合していた。文脈の例外が増え、文字の重なり率も一致した文を説明できなかった。ユーザー決定により「全文で検知→細かい単位で特定」に変更する。
新方式は原文にある数字の表記と文そのものを示すので判断理由を確認しやすい。従来方式には意味の取り違えを検知できる利点があったが、その機能は廃止する。正しい数字を違う文脈で使った誤りは担当者が確認する。画面と生成指示に限界を明記する。
保存形式・HubSpotの関連・生成モデルは変えない。永続データの移行は不要。従来方式へ戻す場合は新しい文一致の結果と画面を含めて旧実装を再導入する必要があり、単なるしきい値変更では戻らない。

## 実装方針

- 基準は読み取りサービスで取得したHRハッカー本文の全列。求人→取引→会社の関連から同じ取引先の全求人をたどる。関連の欠落・部分取得は生成を止める。
- AirWorkのみの求人では既存の正規化された求人状態を優先し、公開中を含め、公開前・公開終了を除外する。2026-10-11に読み取りで項目定義を確認した。両媒体の識別値を持つ求人ではこの状態をAirWorkのものと推測しない。AirWork固有の生状態が公開・掲載中・公開中なら含め、非公開・公開終了・掲載終了・公開開始前・未掲載・掲載停止・停止中なら除外する。それ以外・欠損は不明として含める。数値コードの意味は推測しない。
- 項目ごとにMiniMax（Geminiは使わない）で文章を書く。条件の数字を生成文に書かず、書くなら原文の表記のままという指示を加える。文字数・禁止表現の検査は既存と共通化し、数字にはリクロジ専用の表記一致だけを使う。
- 84列の土台を原本から写し、生成対象5列だけを差し替える。制作メモは非公開のため空欄。CSVを作成・再読込して、転記列すべての値と列順を照合する。改行・空白も完全一致。違いがあればCSVを返さず要確認。求人・店舗・画像の各スロットも照合対象。
- 数字はNFKC・桁区切りカンマ・空白をそろえ、原文全体にかたまりがそのまま含まれるかだけを見る。時刻を分へ換算する等の言い換えはしない。NFKCで面積の単位がm2になった場合も、単位内の数字を分離せず一つのかたまりとして扱う。通貨・面積・期間等の単位が原文と違う場合、数字だけの一致で通さない。「25万」等の桁を表す字もかたまりに含め、金額へ換算せず原文の表記と比べる。無かった表記を画面に示し、その生成列を空欄にする。
- 全文が比較本文に含まれる場合は即不合格。句点・感嘆符・疑問符・改行で分割した文の一致率を相手ごとに計算し、一致した文を示す。内部空白や表現はそろえない。しきい値以上を不合格。しきい値は仮の0.2、短文の最短文字数は暫定の8（2026-10-11ユーザー決定）。合格ラインは暫定（実際の案で要確認の出方を見て調整する）。除外後に文が無い場合は未取得。

## 実測

`scripts/measure_sentence_overlap.py` は標準ライブラリだけで動く読み取り専用スクリプト。認証情報は環境変数、無ければ指定のローカルenvを読む。値は表示しない。すべての窓口を毎秒1回以下に抑えるためSearchも上限を超えない。CRMと同じアカウントの上限に余裕を残し、429ではRetry-Afterを待つ。独立プロセスなのでアプリ内のゲートウェイを直接共有するものではない。
既存の正規化された状態が公開中で、HRハッカーの識別値を持たないAirWork求人を識別値順に検索し、一意の取引先が分かる候補を最大200社取得する。会社→全取引→全求人をたどり、HRハッカーと掲載中と判定できるAirWorkが両方ある会社を集計する。本文は100件ずつまとめて読む。確認済みの関連を処理中のメモリに保持して重複した読み取りを減らす。掲載中か不明は生成時の比較には含めるが、実測の「掲載中」の標本には含めない。候補の取り方による偏りがあるため全集団の無作為標本とは扱わない。
同じ会社のHRハッカー→AirWorkの全組み合わせと、AirWorkどうしの全組み合わせを測る。一致率は方向があるためAirWorkどうしは両方向を数える。最短文字数0と8、p10/p25/p50/p75/p90/p95、0.1刻みの度数、測れなかった件数、全文一致件数を集計する。度数の最後の区間は0.9以上1.0以下、それ以外は下端以上・上端未満。分位点は線形補間。
結果は指定されたリポジトリ外の `codex-logs/rikurozi-overlap/summary.json` に件数と数値だけを保存する。本文・会社名・求人名・識別値を保存しない。本文は処理中のメモリでだけ保持する。測れない値を0へ置き換えない。アプリとスクリプトは共通の架空データの具体例で文の定義を検証する。

## 2026-11-02 の決定

ユーザー決定（2026-11-02）に従い、次のとおりに変えた。

1. AIが書く列は26列。案件名、仕事内容、キャッチコピー、メリット、Indeed表示職種名、仕事情報補足1〜4（タイトルと内容）、応募資格、給与補足、試用・研修の詳細情報、自由項目1〜4（タイトルと内容）、受動喫煙についての補足情報、応募後のプロセス。それ以外は元のHRハッカー求人から写す（写した列の一致検査は従来どおり）。
2. 画像は元の求人の画像1〜3を同じ順に写すだけ。ランダムは作らない。
3. CSVの求人idは空にする（新しい求人として取り込む）。
4. HubSpotに値のない列（職種id・問い合わせ電話番号・連絡先メール・応募時の通知先メール・フォームの種類・その他の質問1〜3・公開開始/終了日時・公開）は空のまま。
5. 文章を書くAIはMiniMaxだけ。Geminiの呼び出しは使わない。

### 「この案でCSVを出す」でHubSpotに求人を1件作る

- 案を作るときは何も書かない。画面の「この案でCSVを出す」を押したときだけ、HubSpotに新しい求人（0-420）を1件作り、元のHRハッカー求人が関連しているすべての取引（0-3）に関連付けてから、CSVを出す。作れなかったときはCSVを出さない。
- 入れる値は夜間の取込（Hubspot_Job-Posting の `reclogi_applicants.py`）がリクロジ求人を作るときと同じ考え方。元のHR求人から写す: 職種（`zhizhong`）、勤務地、勤務時間、都道府県・市区町村、雇用形態、給与形態、年収の下限・上限、担当者、一次対応の既定、応募者管理シートURL。AIが書いた文で置き換える: 求人名（`hs_name`＝案件名）、仕事内容（`shigotonaiyou`）、応募資格（`hissushikaku_shousai`）。ほかのAI列はCSVだけに使う。AIの文が空欄（要確認で空にした）の項目は、元の文を代わりに入れず空のままにする。
- 固定で入れる: `reclogi_moto_hr_kyuujin_id`＝元のHRハッカー求人ID、`kyuujin_status`＝公開前、管理区分＝弊社管理、パイプライン＝求人票管理の「募集準備中」。入れない: `id_hrhakkaa`、`id_shop_hrhakkaa`（HRの取込・夜間の紐付けと取り違えないため）、`id_reclogi`（リクロジに取り込んだあとで決まる）。
- 二重に作らない方式（ADR-010の考え方。新しい表・DB・HubSpot項目は使わない）:
  1. 作る処理は全体で1本ずつ（プロセス内のロック）。二度押し・同時押しは2回目が「すでにある」になる。
  2. 作る前に、同じ元HR求人IDで `id_reclogi` が空の求人をHubSpotで検索し、あればそれを使う。再起動後や別の画面からの再送でも作らない。
  3. 作った直後は検索の反映が遅れるため、作った求人のIDを10分だけプロセス内に覚える。
  - 「すでにある」場合も、足りない取引の関連だけを付け直す（付けられなかった取引があれば、もう一度押すと付く）。
  - 作成の送信は再送しない。通信が途中で途切れた場合は画面に失敗と出るので、少し待ってから押し直す（検索が反映されていれば二重にならない）。
  - 単一インスタンス前提（案の保存や他の画面と同じ）。複数台にする場合は検索だけが頼りになる。
  - 案の保存と同じ書き込みの設定（`JOB_COPY_DRAFT_WRITES_ENABLED` と `JOB_COPY_DRAFT_WRITE_ALLOWLIST`）に従う。止まっているときは求人を作らず、CSVだけを出す（画面にそう表示する）。
- HubSpotの呼び出し回数（1回の「CSVを出す」）: 新しく作るとき 4＋N 回（元の求人の読み取り1、元の求人の取引一覧1、同じ元IDの求人の検索1、作成1、取引への関連付けN回。Nは取引の数）。すでにあるとき 3〜4＋（足りない取引の数）回（読み取り1、取引一覧1、検索1（覚えている間は0）、その求人の関連一覧1）。作成は1回だけ送り、retryしない。
- 画面を開いたときの読み取りは2回（元の求人1、同じ元IDの求人の検索1）。案を作る処理の呼び出しは従来どおり。

### リクロジの求人IDの入力

- リクロジに取り込んだあとで人がIDを入れられるよう、元のHR求人の案の画面に「リクロジ向けに作った求人」を出す。`id_reclogi` が空の求人には小さな入力欄と「IDを保存」を付け、入っている求人にはIDを表示する。
- 保存は `id_reclogi` だけを書く（`PUT /api/job-copy/rikurozi-listings/{id}/reclogi-id`）。半角数字だけを受ける。対象がリクロジ向けに作った求人（元のHR求人IDがあり、HRハッカー・AirWorkの識別値が無い）でなければ保存しない。すでにIDが入っているときも保存しない。別の求人が同じIDを持っているときは、理由を出して保存しない。呼び出しは3回（対象の読み取り1、同じIDの検索1、書き込み1）。
- 最初の応募が来たときに、同じ取引・同じ元HR求人ID・`id_reclogi` 空の求人が1件ならそれを使う直しは Hubspot_Job-Posting 側で別に行う。そのため同じ元HR求人IDで `id_reclogi` が空の求人は1件に保つ（上の検索による重複確認が、この前提を守る）。
