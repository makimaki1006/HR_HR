顧客向け応募者画面 計画（段階 1 の試作）

作成 2026-10-20 ／ 更新 2026-10-26（見る画面・更新の確かめ方・行の見分け方を 10.1 に追加。PR4） ／ 2026-10-26（社内用シートのつくり・整合の取り方・呼び出し回数を 9.2〜9.5 に追加。PR1） ／ 2026-10-22（2 段階認証の流れ・メール環境への対策・応募の通知を追加。別のサービスを使わない） ／ 実装は別のセッションで行う ／ 関連: headless-crm-design.md §21、architecture-decisions.md
要約。顧客ごとの応募者管理スプレッドシートを、顧客がメールアドレスとパスワードでログインして見る・書く画面にする。 段階 1 ではシートを正本のまま残し、画面はシートを直接読み書きする。顧客と社内のどちら向きも、反映の遅れは 1 分以内。 HR_HR（Rust / Axum ＋ React）の中に顧客専用の入口 /portal を作り、追加の費用はかけない。 顧客側は Google アカウントに依存しない。

4. シートとの連携

4.1 準備（一度だけ）

  1. Google Cloud にプロジェクトを作り、Sheets API と Drive API を有効にする（請求先の登録は不要）。
  2. 顧客画面専用のサービスアカウントを作る。今の読み取り専用の鍵（GOOGLE_SA_KEY_B64）は書き込みに広げず、別にする。鍵は Render の新しい環境変数に入れる（例: PORTAL_GOOGLE_SA_KEY_B64）。スコープは spreadsheets と drive.metadata.readonly。
  3. 対象のシートに、サービスアカウントのメールアドレスを編集者として共有する（社内の人が行う）。
  4. 社内の管理画面で、顧客ごとにシートの URL・タブ・見出しの行・見せる列・書ける列を登録する。登録時に試しに読み、開けることを確かめる。

4.2 読む（シート → 画面）

手順API内容
形を読むspreadsheets.getタブ（数字の sheetId で特定し、名前の変更に強くする）、入力規則（プルダウンの選択肢）。10 分キャッシュ
更新の確認Drive files.get（modifiedTime だけ）画面を開いている間、30 秒おき。同じシートはサーバーで 30 秒に 1 回にまとめる
値を読むvalues.batchGet最終更新時刻が変わったときと、初めて開いたときだけ。登録した列だけを画面に返す

4.3 書く（画面 → シート）

  1. 顧客が 1 行を直して保存する。画面は開いたときの行の中身を一緒に送る。
  2. サーバーがシートのその行を読み直す（キャッシュを使わない）。中身が丸ごと同じでなければ書かず、「シートで変更されています」と最新の値を返す。
  3. 書ける列だけを values.update（valueInputOption=RAW）で書く。数式として解釈させない。
  4. そのシートのキャッシュを捨て、社内用シートの操作の記録に誰が・どの行の・何を・どう変えたかを残す。
  5. 同じシートへの保存はサーバーの中で 1 本ずつ通す（単一インスタンス前提。CRM の書き込みと同じ）。

シートを開いたままの社内の人が、古い画面のまま書くと、Google の仕組みでそのまま上書きされる。こちらはアプリでは防げない。

4.4 回数の見積り（無料枠）

枠上限使い方
Sheets の読み取りサービスアカウント 1 つで 1 分 60 回（プロジェクトで 1 分 300 回）書き換わったシートと、保存前の確認だけ
Sheets の書き込みサービスアカウント 1 つで 1 分 60 回保存 1 回につき 1 回
Drive の確認Sheets より大きい（公式の上限表で確認する）開いているシート 100 枚で 1 分 200 回

1 分に 60 枚以上のシートが同時に書き換わると、Sheets の読み取りが上限に当たる。そのときは前に読んだ中身と「○時○分時点」を出し、次の確認で読み直す。足りなくなったらサービスアカウントを 2 つに分ける（無料）。

未確認: シートを編集してから Drive の modifiedTime が変わるまでの秒数。PR4 で測り、1 分に収まらなければ、開いているシートを Sheets で直接 60 秒おきに読む方式に替える。

5.1 2 段階認証の流れ

別のサービス（SMS の送信・外部の認証サービス・有料のメール配信）は使わない（2026-10-22 ユーザー決定）。確認コードは会社の Google Workspace の Gmail から送る。

  1. メールアドレスとパスワードを入れる。違っていれば「メールアドレスかパスワードが違います」だけを返し、コードは送らない。
  2. パスワードが合えば、ブラウザに「覚えた端末の札」があるかを見る。札が有効でその人のものなら、そのままログインする。
  3. 札が無い（初めてのブラウザ・Cookie を消した・期限切れ）なら、6 桁のコードをメールで送り、入力画面に進む。
  4. 正しいコードを入れたらログインし、そのブラウザに新しい札を渡す。次からはコードを聞かない。
項目内容
確認コード6 桁の乱数。10 分有効、間違いは 5 回まで（超えたら無効にして送り直し）。サーバーにはハッシュだけを置き、その時のログインのやり取りに結び付ける（別のブラウザで同じコードを入れても通らない）。送り直しは回数に上限を付ける
覚えた端末の札推測できない長い乱数を Cookie（__Host-・HttpOnly・Secure）で渡し、表にはハッシュだけを置く。最後に使ってから 90 日で切れる。パスワードの変更・アカウントの停止でまとめて無効にする
弱いところ強さはコードを受け取るメールボックスの守りと同じ。パスワードの再設定はメールではできず社内の招待リンクだけなので、メールボックスだけを盗られても入られない。覚えた端末を盗まれた場合は、社内からアカウントを止めて札を消す
後で足せる手段認証アプリ（TOTP）とパスキー。どちらも外部のサービスは要らない。今は作らない

5.2 顧客のメール環境への対策

確認コードは顧客のメール環境の影響を受ける（迷惑メールへの振り分け、外からのメールの検査による遅れ、社外からのメールを受け取らない設定、会社のメールをスマホで読めない）。

  • 会社のドメインの送信認証（SPF・DKIM・DMARC）を整える（今の設定は未確認）。
  • 件名にコードを入れ、本文は短い文字だけにする。リンク・画像は入れない。
  • 確認コードの追加の送り先（スマホで読めるアドレス）を使えるようにする。
  • 覚えた端末では 90 日聞かない。導入のときに PC とスマホで 1 回ずつログインしてもらう。
  • 画面から送り直せるようにする（回数に上限）。届かないときは社内の人が受信許可を案内する。
  • 最初に試す数社で、届くまでの時間と迷惑メールに入らないかを確かめる。多くの顧客で届かなければ、認証アプリを選べるようにする。

6. 見える範囲と社内画面との分離

  • サーバーは毎回の要求で「この人の顧客に登録したシートか」を確かめる。ブラウザから来るのは登録の番号だけで、シートの ID は受け取らない。
  • URL・API・Cookie・画面の入口を社内と分ける: /portal/*、/api/portal/*、Cookie __Host-portal_session、Vite の入口 portal。顧客用の画面には社内画面のコードを含めない。
  • 顧客の Cookie では、社内の /app/*・/api/*・/tab/* は全て 401 になる。社内の Cookie でも /api/portal の顧客の操作はできない（社内の人は管理画面から見る）。
  • 顧客ごとの段階（シートだけ／両方／画面だけ）を管理画面に持ち、一覧で見られるようにする。

9.1 置き方の決まり

  • 顧客には共有しない。社内の共有ドライブに置き、外部へ共有できない設定にする。開ける人はできるだけ絞る。
  • 招待リンクと端末の鍵は、ハッシュだけを置く（見えても使えない）。パスワードは bcrypt のハッシュだけ。
  • このシートの読み書きには、応募者のシートとは別のサービスアカウントを使い、書き込みの回数の枠（1 分 60 回）を分ける。保存 1 回につき、応募者のシートへ 1 回、このシートの記録へ 1 回書く。
  • アプリは起動時と数分おきにアカウント・設定を読み、メモリに持つ（ログインのたびにシートを読まない）。
  • 受け入れたリスク: シートを開ける社内の人は、記録や設定を書き換えられる。記録は「社内の人なら書き換えられる」前提のものになる。社員の Google アカウントの乗っ取り・共有の誤り・退職者の権限の消し忘れは、社内の Google の管理で防ぐ。
  • 操作の記録には応募者の個人情報（前と後の値）が入る。残す期間は別途決める。
  • DB への移行の目安: 記録を証拠として示す必要が出たとき、書き込みの回数の枠に当たるとき、顧客が増えて同時の書き込みが増えたとき。

9.2 社内用シートのつくり（PR1 で作成）

アプリは起動したときにタブが無ければ作り、1 行目に見出しを書く。列の順はアプリが決める。2 行目から 1 行に 1 件。値はすべて RAW で書く（数式として解釈させない）。日時は日本時間の ISO 形式（例 2026-10-26T09:00:00.000+09:00）、真偽は TRUE / FALSE。

  • 人がシートで直してよいこと: 値の手直し（例: アカウントの状態を disabled にする）、行の並べ替え、空の行、右端に自分用の列を足すこと。アプリは書く前に「行を見分ける列」を読み直して行を探すので、並べ替えても別の行には書かない。行を消すと、その顧客・アカウントなどはアプリからも消える（アカウントなら使えなくなる）。
  • してはいけないこと: 1 行目の見出しを変える・列の間に列を入れる。見出しが違うとアプリは読み込まず、管理画面にどのタブかを出す。新しい版で列が増えるときは、アプリが右端に見出しを書き足す。
  • 操作の記録に、PR1 では応募者の値を入れない（シートを試しに読んだことだけを残す）。応募者の値（前・後）が入るのは PR5 の保存から。
  • PR1 に入れていないもの: 選考状況の選択肢ごとの段階、シートごとの名前の列・状況の列・面接日の列の指定、顧客ごとに出す機能。PR4 で右端に列を足す。

9.3 整合の取り方（単一インスタンス前提）

PortalStore は同期の読み書きなので、アプリはシートの中身をメモリに持ち、シートへは裏で書き戻す（src/portal/sheet_store.rs）。

  1. 起動時にタブの一覧と全タブ（操作の記録を除く）を読み、メモリに入れる。読み終えるまでは顧客の画面も管理画面も使えない（管理画面は「読み込んでいます」の帯と理由）。読めなければ 5 秒から倍々で最長 5 分おきに読み直す。
  2. 読み取りはすべてメモリから。ログインのたびにシートを読まない。
  3. 書き込みは先にメモリへ入れる（その場で効く。アカウントの停止・ログアウトはすぐ効く）。変わった行を覚え、裏の 1 本の処理が 0.5 秒待ってからまとめて書く。書き込みどうしは最短 3 秒あける。書く前に「行を見分ける列」を読み直し、1 回の呼び出しで全部の行を書く。記録は別に 1 回で追記する。
  4. 管理画面の操作は、シートに書けるまで最大 8 秒待ってから答える。ログアウトは最大 3 秒待つ。
  5. 5 分おきにシートを読み直し、社内の人がシートで直した値を取り込む。保存待ちがあっても読み直す。保存待ちの行はメモリの方を残す。シートから消えた行はメモリからも消す。
  6. 停止の列（アカウントの状態・顧客の停止）は「どちらかが止めていれば停止」。社内の人がシートで止めた行は、保存待ちがあっても読み直しで取り込み（アカウントなら覚えた端末・ログイン中の画面・招待も無効にする）、書き戻しで止めたのを戻さない。書く直前にシートで止められていたら、止めたまま書いてメモリも止める。アプリで止めて、アプリで再開したときはシートも再開する（アプリが書いた停止と、人がシートで書いた停止を見分ける）。
  7. 書き戻しの処理が何かで止まったら（プログラムの不具合など）、管理画面に赤い帯で理由を出し、少し待ってやり直す。黙って止まったままにしない。
起きたことどうなるか
書き込みが失敗したメモリでは効いたまま。保存待ちに残し、2 秒から倍々で最長 60 秒おきに書き直す。管理画面に「保存待ちが N 件」と理由を赤い帯で出す
保存待ちが残ったまま再起動したその変更は失われる（アプリで止めたアカウントが戻る、ログアウトした画面が戻る、出した招待のリンクが使えない など）。デプロイの前に帯が出ていないことを確かめる。急ぐときはシートで直接、アカウントの状態を disabled にする（シートで止めたものは再起動でも消えず、保存待ちがあっても最大 5 分で取り込み、アプリの書き戻しでも戻らない）
書き戻しの処理が止まった管理画面に赤い帯で理由を出し、やり直す。保存待ちは残る
見出しが違う読み込まない（使えないまま）。どのタブかを帯に出す
記録だけが書けない5000 件まで持って再試行し、超えたら古いものから捨てる。追記の再試行で同じ記録が 2 回入ることがある
2 台以上で動かす対応しない（台ごとに別のメモリを持ち、互いの変更が最大 5 分見えない）。CRM の書き込みと同じ単一インスタンス前提

  • 「両方」「画面だけ」に進めるのは、見せる項目のあるシートがあるときだけ。顧客を止める、または段階を「シートだけ」に戻すと、その顧客のアカウントは全員すぐログインできなくなる。
  • 社内用シート（PORTAL_STORE_SPREADSHEET_ID）は、試しに読むことも顧客のシートとして登録することもできない。起動時に 2 つの鍵が同じサービスアカウントなら、顧客のシート側を使わず警告を出す。
  • 見出しはセル内の改行・タブを空白 1 つにして比べる（登録・項目の作成・項目の保存で同じ）。
  • 見出しの行を変えて保存すると、その行を読んで項目を作り直す（同じ見出しの設定は引き継ぎ、無くなった見出しの項目は消える）。読めなければ何も変えない。
  • 顧客を止めると、その顧客の全アカウントのログイン中の画面・覚えた端末・招待を無効にする。顧客を再開しても、これらは生き返らない（パスワードと確認コードでログインし直す。招待は出し直す）。
  • 試しに読むは記録が残る操作なので POST（CSRF の確認を通す）。記録にはスプレッドシート ID とタブ（番号と名前）を残す（値は残さない）。
  • 試しに読んだ結果には応募者の個人情報が入る。管理者にだけ返し、応答は保存させず（Cache-Control: no-store）、ログには行数だけを出す。

10.2 行の見分け方（PR7 の通知で使う）

  • いま（PR4）: 画面と API は行を「シートの行番号」で見分ける（URL の row= も同じ）。並べ替え・途中への行の挿入で番号は変わるので、詳細はいつも最新の読み取りから出す。保存（PR5）は 4.3 のとおり、書く直前にその行を読み直し、開いたときと丸ごと同じでなければ書かない。
  • PR7 で使う「行の指紋」: その行の、項目の設定で種類を「電話」「メール」にした項目の値（電話は数字だけ、メールは小文字）と、種類が「日付」の項目のうち並びが最初のもの（ふつうは応募日）をつないだもの。見せない項目も使う。状況・面接日・備考など、後から書き換わる値は入れない。
  • 新しい応募 ＝ 前回の読み取りに無かった指紋の行。書き換え・並べ替え・途中への挿入では「新しい」にならない。同じ指紋の行が 2 つある（同じ人が 2 回応募した）ときは、上から順に 1・2 を付けて区別する。電話もメールも日付も空の行は、「前回の読み取りで空だった行番号に値が入った」ときだけ新しいとみなす。
  • 指紋は画面・API に出さない（電話番号の数字から元の値を割り出せるため）。前回の指紋はプロセス内に持ち、残す必要が出たら鍵付きのハッシュ（HMAC）にする。
  • 段階 2 でシートに応募 ID の列を足したら、指紋でなくその列で見分ける（12 章）。
