# ユーザー報告前の逆証明・数値検証

2026-10-04。ユーザー指示により、このリポジトリの可否・設計提案・数値・進捗・完成報告に適用する。質問への回答や進捗でも重要な断定は対象。実施予定の対策を実装済みとして報告しない。

## 報告前の必須順序

1. 報告する主張を列挙する。「画像取得できた」「取り下げ後も表示できる」「容量を減らせる」は別の主張にする。
2. 結果から必要条件へ逆にたどる。過去表示→保存画像の読み出し→履歴から原本参照→保存成功receipt→画像bytesの耐久確保→元URLが生きている間の取得、のように根拠の鎖を作る。
3. 各主張を崩す反例を作る。正常時の説明だけで合格させない。反例を解決した実テストか、未実装の設計条件かを区別する。
4. 数値を計算し直す。対象数、単位、重複、期間、分母、欠損を固定する。保存容量・取得通信量・ブラウザー表示通信量を混ぜない。実測を全件へ無条件に外挿しない。
5. 証拠の場所と検証範囲を照合する。ローカル、API単体、既存アプリ、配備済み本番を区別する。古い証跡を最新の成功と扱わない。
6. 反例で崩れた主張は修正または撤回する。未検証の必要条件が残るものは条件付き案とし、その条件を報告する。
7. 文書化する報告はJSON記録をゲートへ渡す。数値・hash・分類の形式チェック後も、反例が本当に主張を崩さないかを意味の面から再確認する。

報告は結論、証拠と対象範囲、残る条件の順に簡潔に伝える。検証待ちを「完成」と言い換えない。今回の誤報は、画像取得の時点・原本確保・差分検知の順序を分けず、成立する案として伝えたこと。

## 判定

| 分類 | 報告してよい内容 |
| --- | --- |
| verified | 明記した対象範囲で実証でき、反例への対処も証拠付きで確認済み |
| conditional | 必要条件を整理した設計案。未実装・未検証条件を併記する |
| unknown | 判断に必要な証拠がない。取得可否や完成を断定しない |

ゲートは構造、証拠ファイルのSHA-256、Decimalによる計算を検査する。証拠の内容が主張を証明するか、反例が十分か、仕様や本番運用が成立するかは自動判定しない。ローカルテストから本番の保証を作らない。

```powershell
python scripts/report_verification_gate.py <非公開の報告記録.json>
python -m unittest discover -s scripts -p test_report_verification_gate.py
```

記録は `claims` 配列（id / assertion / scope / classification / evidence / counterexamples / limitations）と `calculations` 配列。evidenceはファイルpathとsha256。counterexamplesはscenario / disposition / evidenceを持つ。verifiedの反例は `verified_handled`、条件付き案の未検証対策は `design_only`、未解決は `unresolved` と記載。`refuted` は常に不合格。verifiedは未解決や設計だけの反例を許さない。

calculationsはid / operation / inputs / expected / unit。operationはsum / difference / product / ratio。ratioは比率そのもの（0〜1等）で、百分率へ変換した値ではない。入力・期待値は有限の十進数、既定で厳密一致。丸めが必要なら非負のtoleranceを明記する。欠損を0にした計算は禁止。

## 今回の画像設計に当てた反例

| 反例 | 結論 |
| --- | --- |
| 本文の差分を検知してから取得したらURL消失 | その順序では成立しない。本文変更を待たず毎観測で画像取得が必要 |
| キューにはURLだけ、実行時には消失 | 成立しない。取得bytesの耐久確保後に保存処理へ渡す必要がある。本番の確保方法は未決 |
| 同じURLの画像内容が置換 | URL不変だけでは変更なしと言えない。内容取得・hash比較が必要 |
| ローカル保存後に本番サーバー消失 | ローカル実証は本番耐久性の証拠にならない。再起動・保存先障害からの実復旧検証が必要 |
| 日次観測の間に新画像が公開され削除 | 日次だけでは捕捉不能。全変更を保存できるとは報告しない |
| 画像20参照だが原本内容は9種類 | 参照数と保存ファイル数を分離。9/20＝0.45は種類数の比率であり、容量45%とは言えない |
| 原本保存を重複排除したから通信も少ない | 保存容量削減と日次取得通信は別。転送量の削減は別途実測が必要 |
| Files権限とURL仕様がある | 実アカウントへの保存・復旧・アプリ表示成功を証明しない |

今回の本番画像保存案は **conditional**。実20求人の取得成功は限定範囲の事実だが、本番の画像保存・配信・取り下げ後表示は未実証。[画像設計案](job-copy-online-image-proposal.md) と [取得証跡](job-copy-hrhacker-image-verdict.md) を参照。
