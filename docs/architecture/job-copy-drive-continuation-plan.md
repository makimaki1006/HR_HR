# 現フォルダでの画像保存継続と将来の移行

2026-10-05。ユーザー方針: 現在の実験フォルダを継続利用し、将来別の保存先へ移す。保存先確定を待たず、ロジックと実データ構築を進める。

## 現行実装との差分

現在は operation ID の計算・receipt の同一性・復旧照合が物理フォルダIDに結合している。画像・manifestを新しいフォルダへ同じIDで移しても、再実行や復旧が一致しなくなる。HubSpot の pointer は画像履歴manifestのIDと原bytesのhashを持つため、物理パスに依存していない。

実装前に既存 DrivePilot / DriveManifestPilot / recover とRust画像参照、関連ADRを照合した。Rust/Axum・既存React・HubSpot正本・秘密値のサーバー保持を維持する。新規DB・共有ドライブ・認証方式を追加しない。別セッションが所有する求人・応募同期は変更しない。

## 今回実装すること

1. **同一性の基準IDと現在の保存先IDを分離**する。`identity_folder_id` は初回フォルダIDを固定した識別用の値、`folder_id` は現在の実フォルダ。省略時は従来と同じ値を使い、既存manifest・receiptを変更しない。
2. 画像・manifestの冪等キーと既存receiptの `folder_id` は識別用IDで照合する。実際の保存・親フォルダ検査・候補列挙は現在の保存先IDを使う。生bytesのhashと親フォルダの検査は緩めない。
3. 同じIDのファイルを新フォルダへ移した模擬環境で、再実行CREATE0・同じID・原本一致・復旧成功を確認する。部分移動や識別用IDの誤設定は失敗させる。実ファイルの移動は今回行わない。
4. 36求人・317応募のレビュー版にある取得済み画像原本を照合し、画像がある求人について現実験フォルダへの保存とmanifest構築を広げる。既存3原本・2manifestは再利用する。縮小data URIを原本に代用しない。
5. Rustから専用HubSpot参照を登録し、読戻し・画像取得・再実行を検証する。既存同期項目は更新しない。画像0件と取得失敗を区別する。
6. 実応募のレビュー版の画像をDrive参照へ接続し、全件の原本hash・実応募集計の不変性・E2Eを確認する。統合窓口へ設定と結果を引き継ぐ。

## 移行時の条件

フォルダ自体を同じIDで移す場合はID指定を維持できる。中身を新しいフォルダへ移す場合は物理保存先のみ更新し、識別用IDを保持する。コピー・再アップロードは別IDとなるため、この手順の対象外であり、履歴参照の移行が別途必要。

実移行時は書込を一時停止し、原本とmanifestを同じIDのまま移動できる権限・方法を確認する。読み取り権限、全ファイルの移動完了、原bytes照合、復旧、HubSpot経由の表示を確認してから再開する。共有ドライブへの実移行、本番の日次実行や複数writer排他は今回の実証範囲に含めない。
