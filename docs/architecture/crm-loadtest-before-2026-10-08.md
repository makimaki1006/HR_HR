# CRM 架電画面 負荷試験 — BEFORE (main, 2026-10-08)

HubSpot ゲートウェイ (feat/hubspot-gateway) を入れる前の main で、架電画面の API を 100 人で叩いた結果。
同じ道具 (`scripts/loadtest/`、使い方は `scripts/loadtest/README.md`) で、ゲートウェイのブランチの「AFTER」を測って比べる。

- 対象: origin/main `bb99a17` + 計測用のローカル変更 `scripts/loadtest/before-main-base-url.patch`
  (HubSpot の接続先を `HUBSPOT_BASE_URL` で偽物に向ける 3 行。コミットしていない)。debug ビルド
  (Google ログインを偽物に向ける `GOOGLE_OIDC_DISCOVERY_URL_DEBUG` が debug ビルドにしか無いため)
- HubSpot: 偽物 (`fake_hubspot.mjs`)。応答 400 ± 150 ms、一般 API 190 回/10 秒 かつ 19 回/秒、Search 5 回/秒 (別枠)、Deal 20,000 件
- 利用者: 100 人 (うち管理者 10 人)。全員が偽 Google でログインした本物のセッション (`/api/crm/*` の認可をそのまま通る)
- シナリオ: 0〜10 秒の間に全員が画面を開く (朝の一斉起動) → 30〜90 秒ごとに案件を開く・条件を変える・次のページを読む・
  開き直す (`fresh=1` を含む)。キューが出なかった人は次の操作の代わりに読み直す。5 分
- 実行: 外部バッチなし 2 回 (run1, run2) と、外部バッチが一般枠を 5 回/秒使う 1 回 (bg5)

## ボトルネック (観測から)

1. **Search の間隔制限 (プロセス全体で 1 回/秒) が全員のキューを直列にしている。**
   `ClientOptions::search_min_interval = 1000 ms` (`src/hubspot/client.rs`) で、Search は全利用者で 1 本ずつ 1 秒おきにしか始まらない。
   既定の並びのキュー 1 ページ目は Search を最大 3 回使う (1 ページ分 + 辿らなかった段階の件数を数える分)。
   キューは毎秒 0.3〜1 件しか返せず、100 人分には数分かかる。全体の締め切り 20 秒 (`CRM_REQUEST_DEADLINE`) を超えた要求は 504 になり、
   それまでに使った Search は無駄になる。504 を見た人が読み直すと、また列の後ろに並ぶ (定常でもキューの成功率が 18〜31%)。
   偽 HubSpot の Search は 5 回/秒まで受けられたが、実測は常に 1.0 回/秒だった (制約はアプリ側)。
2. **同時実行の枠 4 (`MAX_CONCURRENT_RECORD_READS`) をキューと案件の詳細で共有している。**
   キューの要求が Search の順番を待つ間も枠を持ち続けるので、案件の詳細はキューの後ろで枠を待つ。
   競合なしなら 1.3 秒の詳細が、p50 14〜17 秒になった (HubSpot の呼び出し自体は 1 回の詳細で 6〜8 回・約 1.5 秒)。
3. **案件の詳細は呼び出しを並列に出すので、1 秒枠 (19 回/秒) に当たる。** 429 は全部 1 秒枠で、client の retry (最低 1 秒待ち) が
   その分だけ詳細を遅らせる。外部バッチ 5 回/秒が加わると 429 は約 3〜5 倍 (21〜40 → 117) になった。1. と 2. に比べれば小さい。
4. 小さいもの: `owners?email=` (本人の owner の解決) は同時に来たミスをまとめないので、約 90 人分で 113〜120 回呼んだ。
   定義系 (properties / groups / pipelines / 関連ラベル) はキャッシュとまとめ読みが効いていて 2〜6 回で済んでいる。
   案件の詳細の 60 秒キャッシュ (利用者をまたいで共有) は、同じ案件を開いた人には効いている。

## この計測の限界

- 偽 HubSpot の遅延は一様乱数、上限の数え方 (到着時に判定、拒否は数えない) は本物と同じとは限らない。1 秒枠 19 回/秒は仮定
  (コードのコメントは共有鍵の枠を「100 回/10 秒」としている。`--limit-10s 100` で測り直せる)。
- debug ビルド。アプリ自体の処理時間は HubSpot の待ちより十分小さいが、release とは違う。
- 書き込み (架電結果の保存) は API がまだ無いので含めていない。画面の静的ファイル (`/app/crm` の JS) も読んでいない。
- 「キューが出なかったら読み直す」は利用者の行動の仮定。読み直さなければ定常の要求は減るが、その人は何もできない。
- 回ごとの揺れは大きい (一度でもキューが出た人 54〜70 人)。AFTER も同じオプションで複数回回して範囲で比べること。
- 最初の 1 回 (記録していない) は道具の不具合で捨てた: キューが出ていない人が共有の人気案件を開き続けてキャッシュの当たりで速く見えたこと、
  終了時刻に全員の操作が重なったこと。直した版で取ったのが上の 3 回。
