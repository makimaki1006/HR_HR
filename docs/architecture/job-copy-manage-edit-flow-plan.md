## 実装計画

1. Reactの既存詳細に手直しフォームを追加。84項目の対応表を使い、管理番号の値は隠して維持する。
2. 今の本文または保存済み案を基に、Rustで基準を再取得して検証する。給与・勤務地・勤務時間・雇用形態・休日に変更があれば理由を必須にする。
3. 案の保存・再送・認可は既存の仕組みを使用。手直しは既存の元データ種類 `free_text`（文章）とし、手直しの基準・理由を既存 `jobgen_draft_facts` の控えに保存する。プロパティや選択肢の追加は不要。
4. 確認状態変更の担当者・日時を同じ非公開の控えに記録。公開ログには個人・求人の識別情報を出さない。
5. 一覧の全件索引に公開状況・確認状態の絞り込みを追加し、保存完了時には索引も更新する。
6. 任意の二つの版・案を比較し、採用した案の求人票表示と既存84列CSV出力につなぐ。
7. 架空データのE2Eで給与の変更値、理由必須、保存状態、採用CSVの84列・値、権限を検証。Rust・frontend・既存E2E・CIを確認。

HubSpotや本番・先方への実書き込みは行わない。CRM配下は変更しない。新しい永続ストアは追加しない。

## 実装結果と制約

- 81項目は入力欄、3つの管理情報は値を隠した読み取り専用欄。管理情報は選んだ求人の現在値をサーバーでも確認し、別の求人の番号へ変わらないよう維持する。
- 本文・紹介文・補足欄にも募集条件が含まれるため、それらの文章を変えた場合も確認理由を求める。AIで意味を判定して警告を省略しない。
- 手直しの基準は今の版または取得できた保存済み案。元の求人本文と案の版を再確認し、更新されていれば上書きを止める。保存の通信失敗は既存の再送待ち・操作番号で扱う。
- 確認状態の変更は従来どおり最新の案のみ。変更者と日時は既存の案の控えに追加してHubSpotに保存し、公開のアプリログには載せない。画面には変更日時のみ表示する。
- AirWorkは本文を仕事の内容に保ち、取得できない84項目は空欄にする。金額を推測・補完しない。
- 求人票の84項目の保存用解析を表示用解析から分け、公開状態や連絡先、管理情報も欠落させない。
- 本番・HubSpot・先方には書き込んでいない。Gemini呼び出しは追加していない。テストの生成応答・保存先はすべて架空の応答。
