# HR_HR Headless CRM 設計

更新日: 2026-10-08
状態: 設計方針確定 / 実装前

## 1. 背景

現在、テレアポ BPO のアルバイトに HubSpot Core Seat を割り当てている。
Core Seat は 1人 12,000円/月だが、BPO は月数回程度しか利用しないケースがあり費用対効果が低い。

目的は HubSpot を置き換えることではない。

**HubSpot を System of Record / CRM Engine として維持し、
人が日常的に操作する UI を HR_HR 側へ移す。**

## 2. 基本アーキテクチャ

```text
Browser
│
│ React + TypeScript
│ HR_HR CRM Workspace
│
▼
Rust / Axum (HR_HR / Render)
│
├ HubSpot Adapter
├ Zoom Phone Adapter
├ Authorization / RBAC
├ Validation
├ Retry / Pending Sync
└ System Logging
     │
     ├──────────────► HubSpot
     │                System of Record
     │
     └──────────────► Zoom Phone
                      Telephony
```

HR_HR 本体と同じ Rust / Axum / Render アプリケーションへ載せる。
別サービスへ分離することを前提にしない。

Frontend は HR_HR の React 移行方針に従う。

## 7. Zoom Phone

Zoom Phone は既存契約を継続利用する。

HR_HR から発信できる UI を提供する。

Call Activity は Zoom Phone for HubSpot (純正連携) が作る。HR_HR は Call を作らない
(ADR-007、2026-09-29 改訂)。

HR_HR が行うこと:

- Smart Embed のイベントから callId / callLogId、相手番号、発信時刻を受け取る
- HubSpot 上の Call を相手番号 (`hs_call_to_number` の正規化) と時刻窓で照合する
- 見つかった Call と同じ Contact / Deal に、架電結果の Note と Property 更新を紐づける
- 見つからなければ Pending Sync で遅延再照合し、一定時間後も無ければ管理画面に出す
- API での Call 作成は、純正連携が記録しなかった場合の手動フォールバックに限る

読み取り時の注意 (実データで確認済みの罠):

- Call は Deal と多対多。1 件に潰さない
- 接触は Deal より Contact に付くことが多い。Deal の直近アクティビティは Deal → Contact → Call も辿る
- Call の系統は `hs_call_source` で区別する (`INTEGRATIONS_PLATFORM` = 純正連携)
- Deal の contact 経由の通話には、同じ Contact の**別 Deal** の通話も混ざりうる (絞り込みは PR4 以降)
- 読み取りは 1 リクエストあたり HubSpot 呼び出し最大 6 回 (本体+関連 1 / Deal の contact→calls 1 / Engagement 型ごと batch read 4)、安全装置で 10 回まで、全体 20 秒で 504 `crm_timeout`。鍵を既存バッチと共有しているため
- 架電ワークスペースは emails を読み、活動カードに表示する。メールの関連・本文読み取りの権限が不足する場合はその部分を `partial.emails` とし、取引本体を表示する。HR_HR からの送信は本人の Gmail、業務履歴の正本は HubSpot の emails (ADR-021)。Gmail の送信と HubSpot の記録は別々に管理し、記録の再試行でメールを再送しない。
- 架電画面の詳細 (`GET /api/crm/workspace/deals/{id}`) は順番に待つ段が 3 つ (案件 + 関連 ID → 担当者・会社・メモ等 → 通話)。担当者・会社の関連ラベルは関連ラベルの定義 (6 時間キャッシュ) で付ける (2026-10-08)
- 同じ詳細はサーバで 60 秒キャッシュし、利用者をまたいで共有する (最大 500 件)。認可 (rbac とレコード単位の関門) はキャッシュがあっても毎回通す。欠けのある応答は入れない。`?fresh=1` (画面の「最新にする」と、発信した通話が終わった後の自動の読み直し) でその案件の分を捨てて読み直す。HubSpot へ書き込む操作を足すときは、その案件のキャッシュを捨てる (`WorkspaceCache::invalidate_deal`) (2026-10-08 ユーザー承認)

### 案件を切り替えるときの待ちを短くする (2026-10-12)

実測: 詳細 (`GET /api/crm/workspace/deals/{id}`) は、キャッシュが無いと 2.0〜3.1 秒 (HubSpot を順番に 3 段)、サーバのキャッシュにあると約 280 ms。画面は切り替えのたびに「読み込み中」で中央・右を空にしていた。BPO は一覧を上から順に進むことが多い。

- **見出しを一覧の行から即出す** (`RowPreview.tsx`): 詳細が届くまで、行がすでに持つ値 (会社・担当者・番号・ステージ・次回/最終架電・担当) だけで見出しを出し、届いたら詳細に入れ替える。発信・編集のボタンは出さない。
- **画面のキャッシュ** (`detailCache.ts`): 直近 20 件を 60 秒、鍵は (案件, モード, 選んだ項目)。同じ案件を開くと即座に前の内容を出し、裏で通常の読み取りをして入れ替える (stale-while-revalidate)。確かめに失敗しても内容は残し、読めなかったことを添える。`fresh` の読み直し・通話が終わった案件・403/401・書き込み (`patchDeal` を送るとき) はその案件の分を捨てる。
- **先読み**: 開いた案件の詳細が届いたら、一覧の次の 1 行を `?prefetch=1` で読む。行へのポインタ・フォーカスを 200 ms 置いたときもその行を読む (離れたら取り消し、選んでいる行は読まない)。同時に 1 本まで、キャッシュにあれば読まない、失敗は黙って捨てる。結果は画面のキャッシュ (と、サーバのキャッシュ) に入れるだけ。
- **サーバ**: `prefetch=1` は認可 (rbac・レコード関門) を通常と同じに通し、キャッシュの鍵も変えない。HubSpot の読み取りは `Background` の優先度 (画面の操作の列が空のときだけ進む)。読み取りの枠は 2 つ残して先読みに使わせず、枠が足りない・10 秒で終わらないときは 503 `hubspot_busy` で断る (画面は無視する)。キャッシュにあれば HubSpot を呼ばずに返す。§18 の関所の上限は変えない。観測用に `GatewaySnapshot.granted_by_priority` (優先度別の許可回数) を足した。

現行を保つ利点 / 変える利点:
- 現行を保つ利点: HubSpot の呼び出しが選んだ案件の分だけで、画面とサーバの状態が単純。
- 変える利点: 1 回の選択につき詳細 1 件分 (3 段: 約 6 回、キャッシュ済みなら 0 回) の読み取りが背景の優先度で増える代わりに、次の案件が約 0.3 秒、先読みが済んでいれば即座に出る。見出しが一覧の値で出るので、先読みが無い場合も空白にならない。
- 戻すコスト: 先読みの呼び出し (`useDetailPrefetch`) を外すだけで先読みが止まる。画面のキャッシュの TTL を 0 にすれば元の動きに戻る。サーバの変更は `prefetch` を読まなければ従来どおり。
- 注意: 画面のキャッシュは最大 60 秒古い内容を先に見せる (すぐ裏で確かめて入れ替える)。他の人・HubSpot 側の変更の反映が 1 回の確認 (約 0.3〜3 秒) 遅れて見えることがある。

純正連携の全機能を HR_HR で再現しない。

## 10. Durable Retry / Pending Sync Queue

目的:
HubSpot へデータが返らない外的障害時に、BPO が入力したデータを失わないこと。

これは CRM DB ではない。

保持するのは **HubSpot へまだ反映されていない操作** のみ。

例:

```text
operation_id
operator_id / operator_email
hubspot_contact_id
hubspot_company_id
hubspot_deal_id
zoom_call_log_id
operation
payload
status
retry_count
last_error
created_at
next_retry_at
```

正常時:

```text
Frontend
↓
Rust
↓
HubSpot
↓
200 OK
↓
完了
```

一時障害:

- 429
- 5xx
- timeout
- transient network failure

```text
HubSpot write fail
↓
Pending Sync Queue
↓
backoff
↓
retry
↓
HubSpot recovery
↓
success
↓
Queue から削除
```

恒久エラー:

- 400 validation
- 401 authentication
- 403 permission

無限 retry しない。

```text
FAILED / Dead Letter
↓
管理者通知
↓
内容確認
```

Durable Retry の保存技術は ADR-018 (2026-10-09) で **既存の監査 Turso の表 `crm_pending_operations`** と決めた。

書き込みのステージ移動は架電の6本 + 納品管理2本を対象とする (2026-10-16 ユーザー決定、案件管理 `/app/job-copy` から利用)。
納品管理は同じパイプライン内だけ移動でき、架電一覧・指標の候補や件数には含めない。
納品管理の必須ルールも HubSpot 画面の内部 API を読み取り、既存と同じ手順で写した。

### 実装状況 (2026-10-09、`src/crm/write.rs` / `pending.rs`)

- 実装済み: `PATCH /api/crm/deals/{id}` (既定 OFF。`CRM_WRITES_ENABLED` / `CRM_WRITE_DEAL_ALLOWLIST`)、
  一時障害 (429・5xx・タイムアウト・接続失敗・混雑) だけを `pending` にして 202、worker が再送
  (1 分・5 分・30 分・2 時間・以降 6 時間、最大 8 回。**再送のたびに競合と必須項目を確かめ、HubSpot の値が変わっていたら上書きせず `failed`**)。
- 書ける項目 (ADR-018): 担当者 (owner) を選ぶ型の項目 (`referencedObjectType=OWNER`。アポ獲得者・FS担当者など) も含む。ステージの必須項目にあり、書けないと移せないため。値は担当者の一覧にある owner ID だけ許す (`hubspot_owner_id` は対象外のまま)。移す画面は「アポ獲得者」「アポ取得者」が空なら操作者本人を最初から入れる (2026-10-14)。
- 恒久エラー (400 / 401 / 403 / 404 / 422)・競合・上限超えは即 `failed`。管理者の一覧 `GET /api/admin/crm-operations?status=failed|pending`、
  再試行 / 破棄 `POST /api/admin/crm-operations/{id}/retry|discard`。
- 表は起動時に自動作成 (`CREATE TABLE IF NOT EXISTS`)。Turso への書き込みは受付・送信結果ごと・1 日 1 回の掃除だけで、
  worker は書き込みでポーリングしない (期限が来た行の SELECT のみ。再送待ちが無ければ 10 分おき)。
  期限が来た行は案件ごとに束ね、案件どうしを 4 件まで同時に再送する (下の「負荷試験への対応」)。
- 上限 `CRM_PENDING_MAX` (既定 50000) を超える一時障害は 503 `queue_full` (台帳は `failed`、再送しない)。
- 1 人あたりの受付は 1 分 200 件まで (`CRM_WRITE_RATE_PER_MIN`、既定 200、最小 1。0・不正は 200)。超えたら 429 `rate_limited` で何も保存せず積まない。画面は「短時間に保存が多すぎます。少し待ってから保存してください。何も保存されていません。」を赤で出す。
- 台帳に記録できない (監査 DB 未接続・Turso 障害) ときは HubSpot に書かず 503 `queue_unavailable`。
- 未実装: Dead Letter の管理者通知 (一覧に出るだけ)、再送成功後のキャッシュ即時破棄 (60 秒 / 30 秒で自然に切れる)、
  複数インスタンスでの worker の排他 (現状 Render は 1 インスタンス前提)。

### 実装メモ: 同じレコードへの同時書き込み (2026-10-09、`src/crm/record_lock.rs`)

本番相当の試験で、同じ Deal に同じ `base` で 15 件を同時に PATCH すると全部 200 になり、最後の書き込みだけが残った
(Deal あたり 14 件の更新の取りこぼし)。原因は 2 つ。

1. 「現在値を読む → `base` と比べる → PATCH」が不可分でなく、同時の要求が全員「書く前の値」と比べて通った (TOCTOU)。
2. 競合確認の読み取りが HubSpot 関所の singleflight で相乗りされ (`coalesced` が増える)、書き込み後の値を見られなかった。

対策:

- **レコード単位の直列化**: (オブジェクト種別, id) をキーにしたプロセス内の async ロックを、競合確認の読み取りから
  PATCH・台帳・監査の更新まで持つ。1 要求が触る Deal / Contact / Company は、Deal を先に、続いて担当者・会社を整列した順に取る
  (別の順で取り合って詰まらない)。再送 worker も同じ鍵を取ってから送る (取れなければ見送り、次の周回でやり直す)。
- 待つのは最大 10 秒 (`WriteConfig.lock_wait`)。超えたら黙って並ばせず 503 `record_busy` (何も保存されていない) を返す。
  競合 (409) で終わる要求は監査の書き込みの前に鍵を放す。使われなくなった鍵は表から消す。
- 競合確認の読み取りは `HubSpotClient::get_object_fresh` で、関所の相乗りを使わず必ず HubSpot へ送る。ワークスペースの 60 秒キャッシュも通らない。
- **単一インスタンス前提**: ロックはプロセス内のメモリにある。Render が 2 インスタンス以上に増える場合は、分散ロック
  (または HubSpot 側の条件付き更新) が必要になる。再送 worker の排他 (上の「未実装」) と同じ前提。

### 実装メモ: 書き込み経路の負荷試験への対応 (2026-10-09、負荷試験 PR #122 の指摘 1〜7)

100 人で書き込み経路を負荷試験した結果 (`docs/architecture/crm-write-loadtest-2026-10-09.md`、PR #122) の指摘に対応した。
修正前後の数字は §10 末尾の表にある。

1. **操作の状態の照会を Turso から外した** (`src/crm/op_status.rs`)。202 のあと画面は `GET /api/crm/operations/{id}` を何度も呼ぶ。
   これまでは毎回 `crm_pending_operations` を SELECT していた (負荷試験: 202 が 1,741 件 → 照会 78,593 回 → SELECT 約 19.5 万)。
   台帳を更新する場所 (受付・再送 worker・管理者の再試行/破棄) が同じ瞬間にプロセス内の表 (operation_id → 状態・回数・直近のエラーコード・次の再送時刻・持ち主)
   も更新し、照会は表から答える。上限 20,000 件・最後の更新から 1 時間。表に無い (再起動した・期限が切れた・押し出された) ときだけ台帳を 1 回読んで表に入れ直す。
   持ち主の確認 (本人か管理者) は表から答えるときも同じ。**単一インスタンス前提** (record_lock と同じ。複数台になったら表をやめるか有効期間を短くする)。
   画面の確認も間引いた: 5 秒後に最初の確認、以降は倍々 (10・20・40 秒) で最大 60 秒おき、30 分で確認をやめて黄色のまま「まだ反映待ちです」を出す。
   タブが隠れている間は確認せず (時間も数えない)、表示に戻ったらすぐ確認する (`frontend/src/screens/crm/useCrmWrite.ts`)。
2. **打ち切られた要求が `in_progress` のまま取り残される問題**: 要求の本体を別のタスクで走らせ、ハンドラは締め切り (`WriteConfig.deadline`、既定 20 秒) まで待つだけにした。
   締め切りが来たとき、まだ台帳に記録していなければ取り下げて 504 `crm_timeout` (タスクは記録の直前で気づいて何も送らない)。
   もう記録していれば**打ち切らずにタスクを最後まで走らせ** (送信・台帳の確定)、ハンドラは 202 `queued` を返す。記録するか取り下げるかは 1 つの原子的な切り替え (`CommitGate`) で決めるので、
   「取り下げたのに送った」「送ったのに 504」は起きない。この修正で、書けたのに 504 と答える「幻」も無くなる。
   プロセスが送信中に落ちたときのための保険として、`in_progress` を再送の対象にするまでの時間も 600 秒 → 90 秒に縮めた
   (worker は同じレコードの鍵を取ってから触るので、生きている送信とは二重にならない)。
3. **プロパティ一覧の取得失敗で全保存が 502 になる問題**: 前に取れた一覧が残っているなら、期限が切れても取り直しに失敗した間はそれを返す (stale-while-error)。
   一度も取れていないときだけ失敗を返す。失敗を覚える時間も 60 秒 → 5 秒に縮めた (障害が終わったらすぐ取り直す)。
4. **拒否した要求を監査 (`activity_logs`) に書かない**: 監査に残すのは受け付けた結果 (保存・再送待ち・競合・送ったあとの失敗) だけ。
   混雑 (`hubspot_busy`)・速さの上限 (`rate_limited`)・鍵の混雑 (`record_busy`)・入力の誤りと必須項目の不足 (`validation` / `missing_required`)・読み取りの失敗 (`read_failed:*`)・
   受付の上限 (`queue_full`) などは、プロセス内の種類別カウンターに数えるだけにした。`GET /api/admin/hubspot-usage` の `write_rejections` で見られる (起動してからの合計)。
5. **無駄な読み取り**: (a) HubSpot の関所に「受け入れの見積もり」(`Gateway::admit`) を足し、競合確認の読み取りの前に、読み取り + PATCH が今の混み具合で待ちの上限に収まるかを確かめて、収まらなければ読まずに 503 `hubspot_busy`。
   (b) 保存の PATCH は新しい優先度 `Continuation` で関所を通す (新しい読み取りより先に通す。待てる上限は読み取り 5 秒 + 429 の最長停止 10 秒)。
   読み取りが済んだ保存の PATCH が他の人の新しい読み取りに負けて断られ、読み取りだけ無駄になるのを防ぐ。再送 worker は背景のまま。
   (c) 混んでいるとき、状態の表に載っていない operation_id (= 新しい保存) は、台帳の照会 (Turso の SELECT) の前に断る。受け付け済みの操作の再送は通して、保存された結果を返す。
6. **再送 worker の処理速度**: 期限が来た行を案件ごとに束ね (同じ案件は古い順に直列)、案件どうしは 4 件まで同時に進める (`WORKER_CONCURRENCY`、1 周 40 件)。
   取り切れていない間は待たずに次の周回へ (鍵が取れずに見送った行で空回りしないよう、最短 2 秒の待ちは残す)。HubSpot への呼び出しは背景の優先度のままなので、関所では画面の操作が先。
   Turso の書き込みは増やしていない (監査の account_id の SELECT は監査を書くときだけ)。
7. **「失敗と答えたのに入っていた」(幻)**: 送ったあとの曖昧な失敗 (タイムアウト・5xx・通信断・応答が読めない) は書けたかどうか分からない。
   (a) 締め切りで打ち切らない (上の 2)。(b) 再送待ちが満杯のとき、これまでは曖昧な失敗を「queue_full で失敗」と断定していた。
   今は HubSpot を読み直して、書く値がすでにあれば保存済み (200)、確かに書けていなければ `queue_full`、読み直せなければ上限を超えても再送待ちに積む。
   (c) 再送 worker も、最後の試行 (8 回目) でも曖昧な失敗なら、同じ読み直しをしてから `max_attempts` で失敗にする。

#### 現行を保つ利点 / 変える利点 (AGENTS.md rule 16)

- 状態の表: 変える利点 = Turso の読み取りが 202 の件数 × 照会回数に比例しなくなる。現行を保つ利点 = 台帳が唯一の正本で、表との食い違いを考えなくてよい。
  食い違いは「台帳を更新した場所が必ず表も更新する」(更新に成功したときだけ写す) と、有効期間 1 時間で抑える。戻すコスト = 照会で表を見ずに台帳を読むだけ。
- 照会の間隔: 変える利点 = 長く詰まったときに HTTP の照会が減る (10 分で 60 回 → 12 回、30 分で 33 回)。現行を保つ利点 = 保存済みへの切り替わりが速い (最大 10 秒)。変えた結果、最初の確認は 5 秒後と速くなり、遅いのは長く待っている操作だけ。
- 締め切り: 変える利点 = 送った操作が台帳で宙に浮かず、画面が誤って「失敗」と言わない。現行を保つ利点 = 要求が必ず締め切りで終わる (タスクは記録後に最大でさらに HubSpot のタイムアウト分走る)。
- `Continuation` と `admit`: 変える利点 = 過負荷で読み取りだけ HubSpot に飛ぶ無駄が無くなり、関所の枠を保存の完了に使える。現行を保つ利点 = 関所の優先度が 2 種で単純。
  過負荷のとき 202 に積んでいた分 (積んでも HubSpot の枠が無く何十分も空かなかった) が、すぐ 503 `hubspot_busy` になる (何も保存されていないと分かる)。

#### 評価のみ: 1 保存あたりの HubSpot 呼び出し (読み取り + PATCH = 2 回) を減らせるか

結論: **読み取りは省けない**。「自分が直前に読んだ値と `base` が同じなら読まない」は、鍵 (レコード単位の直列化) を持ち続けていた間なら安全だが、
鍵は要求ごとに放す。要求と要求の間 (数秒〜数十秒) に、HubSpot 側 (人の画面編集・Workflow・Zoom の純正連携・夜間バッチ) が書き換える可能性があり、
HR_HR はそれを検知する手段が読み取りしかない (HubSpot の CRM v3 の PATCH に If-Match / ETag のような条件付き更新が無い)。
鍵を要求をまたいで持つ (数十秒) のは `record_busy` を増やすだけで、HubSpot 側の変更も防げない。
削れるのは、同じ要求の中の重複だけ: すでに 1 要求 = 1 レコードにつき読み取り 1 回 + PATCH 1 回 (複数項目・ステージ移動は 1 回の PATCH)。
画面が項目ごとに別の要求を送る使い方 (5〜15 項目を数秒で連続保存) なら、画面側で短い間にたまった変更を 1 要求にまとめる (debounce) のが、呼び出しを減らす本当の手段 (別の変更として扱う)。

## 11. Idempotency

Retry を安全にする。

特に CREATE 系:

- Call Activity
- Task
- Note

は二重作成対策必須。

利用候補:

- operation_id
- zoom_call_log_id

例:

```text
zoom_call_log_id = ABC123
↓
HubSpotに既にあるか確認
├ YES → CREATEしない
└ NO  → CREATE
```

Property PATCH のような同一値更新は比較的 retry しやすい。

実装 (2026-10-09): PATCH はクライアントが付ける `operation_id` を台帳 (`crm_pending_operations`) に**送る前**に記録し、
同じ `operation_id` の再送は保存された結果をそのまま返す (HubSpot へは 2 度書かない)。PATCH 自体も同じ値なら冪等。
再送では「HubSpot の現在値が書く値と同じ」なら保存済みとして扱う (応答だけ失われた書き込みを競合にしない)。
同じレコードへの同時書き込みは、冪等性とは別にレコード単位の直列化で守る (§10 の実装メモ。単一インスタンス前提)。
Call / Task / Note の CREATE 系は ADR-007 により HR_HR では作らないので、この仕組みの対象外。

## 12. User Feedback

保存状態を UI で区別する。

- 緑: HubSpot 保存済み
- 黄: 一時保存済み / HubSpot 同期待ち
- 赤: どこにも保存できていない

Queue への保存にも失敗しているのに「保存しました」と表示してはいけない。

実装 (2026-10-09): 緑 = 200 `saved`、黄 = 202 `queued` (`GET /api/crm/operations/{id}` で `pending` / `retrying` / `saved` / `failed` を確かめる)、
赤 = 409 競合・422 検証/必須不足・503 `queue_full` / `queue_unavailable`・ネットワーク失敗。
黄のあとの確認は 5 秒後から倍々 (10・20・40 秒) で最大 60 秒おき、30 分で打ち切って黄色のまま「まだ反映待ちです」を出す。タブが隠れている間は確認しない。
照会への応答はプロセス内の表から返す (負荷試験への対応 1。Turso を読まない)。
締め切りで要求が打ち切られたとき、台帳に記録済みなら 504 でなく 202 を返す (送った操作を「失敗」と見せない)。

## 13. RBAC

Core Seat を外すことで、HubSpot native write permission を BPO の安全境界として使えなくなる。

Rust Backend が新しい権限境界になる。

BPO の例:

許可:
- Contact / Company read
- Call create
- 指定 Property write
- 指定 Task create

禁止例:
- Delete
- Deal amount update
- unrestricted owner change
- unrestricted pipeline change
- 他部署 record への不要アクセス

2026-10-16 ユーザー決定: プロパティの書き込みは役割で絞らない (金額・担当者を含む)。今の HubSpot の運用でも絞っていないため。上の禁止例のうち Deal amount update は採らない。書ける項目は ADR-018 の is_writable (HubSpot が API で書かせる項目) で決まる。

HubSpot Service credential を Browser に渡さない。

## 14. Backup / Recovery

Headless CRM 専用の CRM backup DB は作らない。

CRM data は HubSpot が正本。
Zoom 通話一次情報は Zoom。

ただし HubSpot の保持 / restore 機能は完全な無期限 snapshot ではないため、
会社として必要な retention policy は Headless CRM とは別軸で定義する。

## 15. DB を追加する条件

以下のときのみ再検討する。

**HubSpot にも Zoom にも置くべきではない、HR_HR 固有の永続データが発生した場合。**

例:
- 独自 business entity
- HubSpot と独立した長期 state
- compliance 上必要な別監査情報

以下だけでは DB 導入理由にしない。

- ユーザー数が増えた
- API 呼び出しが増えた
- 一般的な Web App では DB を置くことが多い

## 16. Pricing / Reversibility

この設計は「永久に Core Seat を回避できる」ことを前提にしない。

HubSpot の価格 / API / permission model が変わり経済合理性を失った場合、
Core Seat 運用へ戻すことは可能。

したがって最大の要件は vendor pricing の完全予測ではなく、
今の期間に削減できる費用と業務 UX が実装 / 保守費を上回ること。

### 架電一覧の追加条件 (2026-10-12 更新)
- 条件編集は右から開くパネルにまとめ、一覧の開始位置を動かさない。各まとまりのカードに条件チップと追加ボタンを置き、カード間を「または」でつなぐ。項目は検索と選択を一つの入力で行い、数値チップは桁区切りで表示する。
- 追加前に既存の段階・日付・実効所有者を含む条件数を計算し、残りが 0 なら追加を止める。サーバーの上限検証も維持し、上限エラーには再試行ボタンを表示しない。
- 項目の並べ替えは上部の並び選択の「ほかの項目で並べ替え…」から小さなダイアログで設定する。条件パネルには並べ替えを置かない。
- 取引の既存プロパティ一覧から型に合う条件を選ぶ。最大 3 つのまとまり、各 6 条件で、まとまりの中は AND・まとまり同士は OR。文字の否定・数値/日付の範囲・選択肢の空判定・真偽の空判定を追加する。
- 相対日付はサーバーが同じ要求の JST の今日を基準に解決する。過去/今後 N 日は今日を含む N 日間 (1〜3650)。日付型は UTC 午前0時の暦日、日時型は JST の一日の開始/終了 (両端を含む) へ変換し、解決後の値をキャッシュと続きの条件に含める。画面も相対日付の日付変更時に取り直す。
- 項目名・選択肢・有限数値・日付・範囲の逆転を Rust で検証する。値は 200 文字、選択肢は 20 個まで。並べ替えも取引カタログにある型だけ (文字・数値・日付・日時・真偽・単一選択) を許可する。
- 既存グループと追加のまとまりを AND の直積として一つの検索に入れる。グループ 5 個・各 6 条件・合計 18 条件、検索本文 3000 文字を超える指定は Search 前に 400 で返し、画面は「条件が多すぎます。条件かまとまりを減らしてください」と案内する。Search の回数は増やさない。
- 既定と既存の固定の並びは維持。任意項目の並び (`sort=property:<項目>:asc/desc`) は全対象を単一段階で検索し、その項目順だけでページ送りする。次回日・ステージの決まりは絞り込みとして適用し、未架電や次回日による優先順は付けない。空の値と同値の順は HubSpot に従う。
- 架電禁止・ブロックの除外は常に取得後にも確認する。上限を満たすため検索中の任意の停止除外条件だけを省く場合も、利用者の条件は削らない。件数・ページ・続き・キャッシュには全まとまりと項目/向きの並びを含める。
- 詳細条件で使った項目と、項目での並べ替えの項目は、一覧の各行に値を 1 行で添える（並べ替えの項目が先、条件の項目は出てきた順、重複なし、最大 4 つ。次回架電日・最終架電日・担当者・案件名・ステージなど行に出している項目は除く）。値は既存の Search の `properties` に足して同じ応答で読み、HubSpot の呼び出しは増やさない。行の `extra` は使った項目が無いとき省く。画面は項目の表示名と型に合わせて整え（数値は桁区切り・日付は YYYY/MM/DD・日時は日本時間・選択肢は表示名・真偽は はい/いいえ・空は「（空）」）、表示名が分からない項目は出さない。キャッシュの鍵は条件と並びを含むので、値が別の条件の応答に混ざらない。
- URL は旧 `conditions` (平坦な条件配列) と既存の `sort` を読み続ける。2つ以上のまとまりは `condition_groups` (条件配列の配列) に保存し、両形式の同時指定は拒否する。B のビュー保存は URL をそのまま保存・復元でき、独自の保存先は追加しない。


#### 対象の範囲

従来は単一パイプラインの架電対象内だけを検索し、漏れの調査ができなかった。`QUEUE_PIPELINES` の6つから1つ以上を選び、架電対象だけ／すべての取引を切り替える。単一・架電対象の既定を保つ利点は旧URLと日々の架電順を維持できること。範囲を広げる利点は横断してHubSpotと同じ条件の取引を調査できることで、戻す場合も既存URLと保存ビューは維持できる。

- 1つは旧 `pipeline=<id>`、複数は `pipelines=<id>,<id>`、全取引は `scope=all`。両pipeline形式の同時指定・許可リスト外・別パイプラインのステージは400。集合は昇順に正規化し、範囲・解決したステージ・条件・並びをキャッシュ、件数、cursorの鍵に含める。保存ビューのURL方式を維持する。
- 架電対象は各パイプラインのAll/Due/Excludeをまとめた和集合。段階内のステージINをまとめ、パイプライン数でSearch回数を増やさない。旧URLは従来と同じ検索条件と段階を使う。
- 全取引は許可されたパイプラインのステージ定義（追加されたステージを含む）のINで検索し、自動の次回日条件・停止理由の除外を使わない。利用者が指定した日付範囲・所有者・項目条件は適用する。電話番号がない取引も表示し、架電禁止・ブロックは印を出してZoom・端末の発信を止める。書き込みの認可は維持する。
- 全取引の既定は `created_desc`（作成日の新しい順）。既存の日付順や項目順も単一段階で並べ、次回日を優先する段階順は使わない。空値・同値の順はHubSpotに従う。件数は同じSearchのtotalを使い、表示件数へ置き換えない。
- 範囲やパイプライン数によらず、グループ5・各6条件・合計18条件と検索本文の上限を全Searchの前に検証する。超過は既存の条件上限の文言で400。画面も残り条件数を計算し、追加を事前に止める。

参照: [HubSpot Search の比べ方・上限](https://developers.hubspot.com/docs/api-reference/latest/crm/search-the-crm)。

## 18. HubSpot 呼び出しの関所 (2026-10-08)

状態: 実装済み (PR「HubSpot 呼び出しの関所」)。CRM 利用者 約 100 人の同時利用に備える。2026-10-12 に ADR-025 で鍵ごとの枠へ変更。短時間枠は private app 別だが、日次上限と Search の公式上限はアカウントで共有する。管理画面の観測は選択された CRM の鍵の枠を表示する。

### 背景 / 問題

- 鍵は既存の外部バッチと共有している。HubSpot の上限 (応答ヘッダで確認: 10 秒 190 回・1 秒 19 回・1 日 625,000 回、Search はアカウントで約 5 回/秒) をアプリと外部バッチで分け合う。
- これまで流量の制限は Search の 1 回/秒 (クライアントごと) だけだった。CRM 用・営業KPI 用・求人票コピー用でクライアントが別々にあり (求人票コピーは独自の HTTP クライアント)、アプリ全体の上限が無かった。
- 429 を受けても止まるのはその 1 本だけで、他の要求はそのまま送り続けていた。
- 同じ案件を同時に開くと、同じ読み取りを人数分送っていた。
- 架電キューは毎回 HubSpot を読んでいた (案件の詳細だけ 60 秒キャッシュがあった)。

### 決定

1. **関所 (`src/hubspot/gateway.rs`)**: プロセス内の鍵ごとに 1 つ (ADR-025)。同じ鍵の本番 HubSpot クライアントは全部 `HubSpotClient::for_production` でこれに繋ぐ (CRM・求人票コピー・営業KPI 直読み・管理画面の鍵確認)。求人票コピーの独自クライアントは `HubSpotClient::read_raw` (retry しない生の読み取り) に置き換えた。画像連携の運用 CLI の書き込み 2 本 (プロパティ作成・PATCH) は読み取り専用クライアントに書き込み API を置かない方針のため独自の HTTP のまま、ただし送る前に関所の許可を得る。
   - 窓: Search 以外は「1 秒 8 回・10 秒 80 回」、Search は「1 秒 3 回」(環境変数で変更可。`docs/env_variables_reference.md` §2d-2)。直近の許可時刻で数えるので、どの区間を切り取っても超えない。HubSpot の上限の残り (10 秒 110 回・1 秒 11 回・Search 2 回/秒) は外部バッチの分。Search は従来クライアントごとに 1 回/秒だったが、負荷試験 (100 人、2026-10-08) で朝の架電キューの先頭ページの約 9 割が 20 秒の締め切りに間に合わず、HubSpot の上限には届いていなかったため 3 回/秒に上げた (§17 の「Search は 1 req/秒」の決定をこの節で置き換える)。
   - 優先度: `Interactive` (画面の操作) と `Background` (定義系キャッシュの先読み・営業KPI 直読み・運用 CLI)。待ち行列は優先度ごとで、画面の操作の列が空のときだけ背景が進む。
   - 待ちの上限: 画面の操作 5 秒・背景 60 秒。並んだ時点の見込み (窓が空くまで + 前に並ぶ数 × 間隔) が上限を超えるなら並ばずに、並んだ後でも上限に達したら列から抜けて、HubSpot を呼ばずに `HubSpotError::Busy` → 503 `hubspot_busy`。画面は「HubSpot が混み合っています。少し待ってから再試行してください」。締め切りで打ち切られた要求の順番待ちは列から外れる (後ろの人の Search の順番を食わない)。
   - 同時実行の枠: 架電キュー (8) と案件・レコードの読み取り (8) は別の枠にする (キューが Search の順番を待つ間に詳細の読み取りが後ろに並ばないように)。枠の待ちも同じ上限で `hubspot_busy` にする (20 秒待たせて `crm_timeout` にしない)。
   - 429: どの要求が受けても `Retry-After` (無い・0 なら 1 秒、最大 10 秒) の間、関所を通る全員を止める。各要求の retry の決まり (最大 2 回・最低 1 秒) は変えない (retry も 1 回として窓に数える)。
   - 相乗り: 同じ読み取り (優先度・メソッド・パス・query・本文が同じ) が同時に走っていれば 1 回にまとめる。優先度を鍵に入れるのは、画面の操作が背景の取得に相乗りして背景の列で待たされないようにするため。
   - 観測: 応答ごとに `X-HubSpot-RateLimit-*` を記録し、起動してからの回数 (種類別・Search・429・相乗り・断った回数)、待ち行列の長さ、直近 5 分の待ち時間 p50 / p95 を持つ。`GET /api/admin/hubspot-usage` (管理者だけ。数字だけで鍵や中身は返さない) と管理画面 `/app/admin?view=hubspot` (15 秒ごとに更新) で見る。
2. **架電キューのキャッシュ (`src/crm/queue_cache.rs`)**: 1 ページの中身を 30 秒、先頭ページの段階の件数を 60 秒。鍵は「パイプライン・絞り込み・並び・**解決済みの担当者** (`me` は本人の owner ID に直す)・今日 (JST)・ページの位置」。中身は利用者によらない部分だけで、cursor (本人に束縛した署名) と `scope` (役割・所属チーム) は要求ごとに作り直す。認可 (`rbac::authorize`) はキャッシュを見る前に毎回行う。関連の読み取りに欠けがある応答・数えるべき総数を数えられなかった応答は入れない。`?fresh=1` (画面の「再試行」「最初から読み直す」) は読み直して置き換える。上限 500 件 / 1,000 件。
3. **定義系キャッシュの先読み**: パイプライン定義 (5 分)・担当者一覧 (10 分)・プロパティ一覧 (6 時間)・関連ラベル (6 時間) は、有効期間の残りが 20% を切ったら背景の優先度で読み直す (画面の要求は待たない。同時に 1 本)。期限切れ後の最初の要求は従来どおりその場で読む。本人の owner ID (10 分) と CRM の定義 (60 秒、`?refresh`) は従来どおり。

### 現行を保つ利点 / 変える利点 (AGENTS.md rule 16)

- 現行を保つ利点: 待ち行列が無いので応答は速い (上限に当たるまでは)。仕組みが少ない。
- 変える利点: アプリ全体の流量が外部バッチの取り分を食わない。混雑時は 20 秒待たせずにすぐ「混み合っています」を返す。429 の後に全員で叩き続けない。同時に同じ案件・同じキューを開く人数に比例して HubSpot を呼ばない。
- 戻すコスト: 環境変数で上限を上げれば実質的に制限を外せる (`HUBSPOT_APP_RATE_PER_SEC=19` 等)。キャッシュは `fresh=1` で迂回できる。

### 前提・未確認

- HubSpot の Search が 10 秒・1 秒の窓に数えられるかは公開仕様で確定できなかった。関所では Search を別の窓 (1 回/秒) で数え、通常の窓には数えていない。
- 関所はプロセス内だけ。Render でインスタンスを 2 つ以上にすると上限はインスタンス数倍になる (今は 1 インスタンス)。
- 求人票コピーの読み取りは従来どおり retry 1 回 (Retry-After が 2 秒以下のときだけ) を呼び出し側で行う。

## 架電一覧の保存済みビュー（ADR-026）

- 一覧の URL クエリを文字列のまま既存監査 Turso の `crm_saved_views` に保存し、既存の一覧の検証を通す。条件の構造を別に解釈しない。
- 自分用は本人だけ、共有は全員が読める。共有を変更・削除できるのは作成者と管理者だけ。個人の自分用 50 件・全体の共有 100 件、クエリは 2,000 文字まで。
- タブで URL を切り替え、変更した条件は上書き・別名保存・復元を選ぶ。開くビューは URL の `view` に残す。
- 読み取りは 60 秒キャッシュし書き込みで破棄する。監査 DB が使えないときはビューの案内 1 行だけを出し、一覧は継続する。HubSpot の業務データは保存しない。

## 19. 今日の架電成績 (2026-10-13、ADR-027)

状態: 実装済み (`src/crm/caller_metrics.rs`)。ユーザーが定義を決めた (アポ = 営業KPI と同じ、本人の数字と比較の平均と順位の両方を見せる、管理者は全員)。

### 定義 (画面・API・テストで同じ)

- 単位は HubSpot の担当者 (owner)。期間は今日 (JST 0 時から今)。対象は Zoom 純正連携が作った Call (`hs_call_source = INTEGRATIONS_PLATFORM`)。
- 架電数 = `hs_call_direction = OUTBOUND` の件数。着信 (INBOUND) は「着信数」として別に数え、架電数に混ぜない。
- 通話 30 / 90 / 360 秒以上 = `hs_call_duration` (ミリ秒) がちょうどその秒数以上の架電の件数と割合 (割合 = 件数 ÷ 架電数。件数から毎回計算し、架電数 0 は null)。「接続率」「接触率」とは呼ばない。
- 通話時間の合計 = 架電の通話時間の合計。平均 = 合計 ÷ 通話時間が 0 より長い架電の件数 (無ければ null)。H:MM:SS / M:SS で表示。
- アポ数 = 「アポ日確定」ステージに今日入った取引の数 (BPO はパイプライン `753186575` のステージ `1095457875`、プロパティ `hs_v2_date_entered_1095457875`)。取引のアポ獲得者 (`bpo_26`) に付ける。空なら担当者 (`hubspot_owner_id`)。営業側 (`52035886`) は `caller_metrics.rs` の `APPOINTMENT_STAGES` に足せば数えられる (今は未使用)。
- 最初・最後の架電の時刻 = 発信の最初と最後。
- 比べる集団 = 今日 1 件以上架電した人のうち、見ている人と同じ HubSpot チームの人。見ている人にチームが無い・チームの人が今日誰も架電していない・担当者一覧が取れないときは「今日架電した全員」。平均は集団の 1 人あたり (割合は件数の合計から)。
- 本人の帯のアポ欄は、アポを数えるチーム (`APPOINTMENT_TEAMS` = BPO_リクロジ) の人かチーム無しの人にだけ出す (応答の `appointments_tracked`)。新規営業だけ・コンサル営業だけの人には数・平均・順位ごと出さない。管理者の全員の表は変えない。
- 順位は 1 が最良 (多い順)。対象は架電数・通話時間合計・90 秒以上の件数・アポ数。同じ値は同順位 (1, 1, 3)。今日の架電が 0 の人は集団に入らず、順位は出さない (数字は出す)。

### API

- `GET /api/crm/metrics/today`: 自分 (`owner=me` と同じく、メールから HubSpot の担当者を引く) の数字、集団の平均、順位、`as_of`、`stale`。担当者が引けなければ `me: null` と理由の文。CRM の利用者なら誰でも。
- `GET /api/crm/metrics/today/all`: 全員の表 (名前・チーム付き)。管理者だけ (それ以外は 403 `forbidden`。認可で落ちる限り HubSpot は呼ばない)。名前・チームは担当者一覧 (10 分キャッシュ) から付け、取れなくても数字は返す。
- 画面: 架電画面の上に「今日の成績」の帯 (架電数・90 秒以上・通話時間合計・アポ。それぞれ値・平均・順位、「○時○分時点」、閉じられる)。管理者は `/app/admin?view=callers` に全員の表 (並べ替え・チーム絞り込み)。どちらも 2 分ごとに自動で更新し、タブが隠れている間は止める。架空サンプル (`mode=fixture`) でも動く。

### データの流れと呼び出し回数

新しい DB は作らない。プロセス内に今日の Call を持つ (`CallerMetricsState`)。

1. 最初の要求: 今日 (JST 0 時から) の Call を Search で全部読む (200 件ずつ。窓の合計が 9,000 件を超えるなら時間で半分に割る。Search は 1 回 10,000 件まで)。アポの取引は `hs_v2_date_entered_<ステージ>` が今日のものを読む。
2. 以降: 前回の読み始めの 2 分前以降に更新された Call だけを `hs_lastmodifieddate` で読み、id で上書きする (重なっても数は増えない)。アポは 1 日数十件なので増分にせず今日の分を毎回読み直す (担当者の付け替えも拾える)。
3. 読み直しは 2 分に 1 回まで (要求が来たときだけ。利用者をまたいで共有)。読み直し中の別の要求は前回の結果を返す。失敗したら前回の結果を `stale: true` で返し、30 秒は再試行しない。JST の 0 時を過ぎたら捨てる。全部 `Background` 優先度 (関所の画面操作を先に通す)。
4. 最初の読み込みは要求から切り離して背景で 1 本だけ走らせる。起動時にも背景で始めて温め (`spawn_warmup`)、数字が無い間の `GET /api/crm/metrics/today` と `/today/all` は 504 にせず 200 `loading: true` (数字は空) を返す。画面は「今日の成績を集計しています…」を出して 12 秒おきに取り直す。失敗したら 30 秒は読まず、過ぎたあとの次の要求で読み直す (2026-10-14、再起動直後に要求の締め切りで読み込みごと打ち切られ 504 になった対策)。
5. 単一インスタンス前提 (record_lock と同じ)。複数台になると各台が別に読む (結果は同じだが呼び出しは台数倍)。

HubSpot への呼び出し回数 (実測ではなく見積り。直近の件数: 全社の通話は平日 約 5,000 件/日):

| 場面 | Search | その他 |
|---|---|---|
| 最初の読み込み (一番多い夕方) | Call 約 25 回 + 取引 1 回 = 約 26 回。Search は 1 秒に 3 回までなので約 9 秒 | 担当者の対応 (本人 1 回・10 分キャッシュ)、担当者一覧 (100 人ごと 1 回・10 分キャッシュ) は既存のキャッシュを共有 |
| 以降の読み直し (2 分に 1 回まで) | Call 1 回 (2 分間の更新は通常 200 件未満) + 取引 1 回 = 2 回 | なし |
| 1 日 (利用者がいる 8 時間) | 約 500 回 (2 回 × 30 回/時 × 8 時間 + 初回) | HubSpot の 1 日の上限 625,000 の 0.1% 未満 |

利用者が何人いても HubSpot への呼び出しは上の回数のまま (読み直しを共有しているため)。

### 現行を保つ利点 / 変える利点 (AGENTS.md rule 16)

- 現行 (日次バッチ + Google Sheets の 架電クオリティ・営業KPI だけ) を保つ利点: HubSpot を呼ばない。数字が 1 日 1 回確定し、画面ごとの食い違いがない。新しい仕組みが要らない。
- 変える利点: 架電中の本人が、自分の数字と平均・順位を今日のうちに見られる (翌朝では行動を変えられない)。管理者がその日のうちに全員の動きを見られる。
- 戻すコスト: 画面の帯・管理者の表・2 つの API を外すだけ (新しい表・DB・環境変数なし)。HubSpot のデータは変わらない。
- 食い違いの扱い: バッチの数字 (昨日まで) と今日の数字は、集計の定義が同じ (上記) になるよう揃えてある。バッチ側が使う Call の範囲 (純正連携だけか) は別途確認が要る。

### 新規営業向けの「今月」 (2026-10-14、ADR-027 の追補。`src/crm/caller_metrics_month.rs`)

ユーザー決定: BPO は今日だけ、新規営業 (セールス側) は今月を主にする。新規営業には 30 / 90 / 360 秒の基準は出さない。アポの数え方だけ日次バッチ (営業KPI) に合わせる。

定義:

- 対象は HubSpot のチーム「新規営業」の人だけ (応答の `month_view` が true の人の帯は今月が主、BPO は今日のまま)。期間は今月 (JST の 1 日 0 時 〜 いま)。
- 架電数・通話時間の合計と 1 件平均は今日の集計と同じ定義 (Zoom 純正連携の Call、OUTBOUND、通話時間 0 の架電は平均の分母に入れない)。今日の架電数は小さく添える (`today_outbound`)。

数え方:

- 項目 1 つにつき Search を 1 回組む: 各まとまりの解決した条件に「誰の」項目 IN 比べる相手の owner (100 人ずつ) を加え、1 回の Search の `filterGroups` に並べる。複数のまとまりに合う取引も和集合として 1 件とし、受信時にも ID で重複を除く。200 件ずつ最大 2,000 件まで読み、owner ごとに数える。最初の応答の `total` (100 人ずつの合計) が 2,000 を超えたら、それ以上読まずに `too_many`。黙って途中までの数字は出さない。
- 同じ定義 (解決した条件の全まとまり・数え方・項目・「誰の」・比べる相手の集合) の結果は人をまたいで 2 分キャッシュ (最大 500 件)。相対日付は解決した日付の値が鍵に入るので、日が変われば別の鍵。期限が切れたら前の値を返しながら背景で読み直す (同じ定義は 1 本だけ)。失敗 (関所の混雑 `hubspot_busy` 等) したら前の値を `stale` で返し、30 秒は読み直さない。一度も読めていなければ `unavailable`。HubSpot の呼び出しは全部 Background の優先度 (画面の操作が先)。単一インスタンス前提。

## 22. トークの振り返り (2026-10-19、ADR-033)

状態: 実装済み (`src/crm/talk_review/`)。既定 OFF (`CALL_REVIEW_ENABLED=1` のときだけ worker が判定する)。番号は ADR-028 / §20 が既に main にあるため ADR-033 / §22 とした。

### 目的

アポ率の低い人について、アポ取りの会話のどこで崩れているか (受付・日付の前・断られた後など) を、人ごと・日次/週次で早く掴む。著しくおかしい人には画面に印を出し、現場の管理者が個別に確認・介入できるようにする。Slack などへの通知は作らない (まず画面の印だけ)。

### 判定の基準

- 項目と判定の決まりは現場が承認した資料 `docs/sales_call_analysis/apo-talk-v1.html` (第 1 部と 07 章) に従う。
- アプリが使う定義は `src/crm/talk_review/checks.json` が唯一の正本。判定の言い方を直すときはこのファイルだけを直す。結果の行には checks の版 (内容のハッシュ) とモデル名を残す。
- 判定は MiniMax に項目ごとに行わせる (Gemini は使わない)。根拠は発言番号と短い引用、できていない項目だけ次に言うとよいことを付ける。アポ確定後の会話は判定に使わない。temperature 0、JSON 出力。
- 項目の判定は「該当」「できた」「できていない」の 3 つ。該当なしの電話は分母に入れない。

### データの流れ

```text
HubSpot の Call (純正連携 / 70 秒以上 / OUTBOUND)
  └ hs_call_body の録音 URL → Zoom の call log ID → 録音 ID
     └ Zoom: 文字起こし (話者を営業と先方に分ける)
        └ MiniMax: checks.json の項目ごとに判定
           └ 監査 Turso `call_talk_reviews` (1 行 = 1 Call)
```

- 文字起こしの全文は保存しない。画面で詳細を開くときに Zoom から取り直す (プロセス内に 10 分・最大 50 件のキャッシュ)。Zoom が録音を返さなければ「録音が残っていません」と出す。
- 文字起こしがまだ無い (Zoom が処理中) Call は、10 分・30 分・1 時間・2 時間・4 時間・8 時間・12 時間の間隔で再試行し、8 回で諦める。
- 録音 URL が無い Call は、作成から 2 時間待つ。BPO の発信は Zoom の Call Queue 経由で、HubSpot の本文に録音 URL が入らない。そのため待ったあと、Zoom の通話履歴 (`GET /v2/phone/call_history`、JST の日ごとに 10 分キャッシュ、最大 40 ページ) から相手番号 (下 9 桁、HubSpot の `hs_call_to_number`) と開始時刻 (差 60 秒以内で最も近いもの) で同じ通話を探し、その詳細 (`call_elements` の Call Queue の要素) の `recording_id` を使う。見つけた ID は行の `zoom_call_log_id` に `rec:` を付けて覚える。見つからなければ理由 `no_recording_found` で「取れない」にする。
- 起動後に 1 回、理由が旧 `no_recording_url` の「取れない」の行を順番待ちに戻して、通話履歴から探し直す。
- Zoom が 404 を返した Call は、通話から 1 日未満なら録音がまだ出来ていないものとして再試行し、1 日以上経っていれば録音が消えたものとして「取れない」にする。
- 営業しか話していない文字起こしは判定せず「取れない」にする。
- HubSpot・Zoom・MiniMax の一時的な失敗も上限付きで再試行する。
- worker は 10 分おき (`CALL_REVIEW_INTERVAL_SECS`) に、前回の読み取りの 30 分前以降に更新された Call を HubSpot の Search で読む (関所の `Background` 優先度、§18)。初回は過去 `CALL_REVIEW_BACKFILL_DAYS` 日 (既定 14 日) まで遡る。判定は同時に `CALL_REVIEW_CONCURRENCY` 本 (既定 4、最大 8)。判定済みの Call は二度判定しない。
- 全員の全架電は判定しない。見つけた Call はまず順番待ち (`queued`) の行にし、1 人 1 日 (JST) あたり `CALL_REVIEW_PER_PERSON_DAY` 本 (既定 10) まで、新しい電話から文字起こし待ちにする。枠は判定済み + 文字起こし待ちの本数で数え、取れなくなった電話の分は同じ人・同じ日の次の電話が枠に入る。順番待ちの行は画面の「待ち」に数えず、電話の一覧にも出さない。処理も新しい日から順に進める。
- checks の版が変わっても自動では判定し直さない。管理者が期間を指定して判定し直す操作は後で足せる (必須ではない)。

### 対象

- チーム: BPO (`BPO_リクロジ`) と社内の新規営業 (`新規営業`)。`CALL_REVIEW_TEAMS` で上書きできる。
- Call の条件: `hs_call_source = INTEGRATIONS_PLATFORM`、`hs_call_direction = OUTBOUND`、`hs_call_duration` が `checks.json` の `min_talk_sec` (70 秒) 以上。
- 架電数: 営業KPI と同じ値。日次同期がシート `KPI営業_架電日次` の「架電数」に書く、Zoom の通話ログのうち `result == "Auto Recorded"` (つながった通話) の数。`sales_kpi` の `kaden_of` / `kaden_period` をそのまま使い、HubSpot の Call では数えない。今日の分はシートの途中経過 (朝・夕の同期の時点) で、取得条件の「架電の最終日は途中」「架電の取得時刻」を見て画面に「○○ 時点の数」と出す (`sales_kpi::kaden_last_day` を営業KPI と共用)。シートが読めないときは架電数とアポ率を出さず (null / 「—」)、画面に読めなかったことを出す。HubSpot で数える旧経路へのフォールバックは無い。アポ率 = アポ数 ÷ 架電数。
- 今日の架電数 (2026-10-20): 期間に今日が入るときだけ、今日の分は Zoom の通話ログ (`phone/call_logs`) から約 15 分おきに数える (`live_dials.rs`。プロセス内で共有し、更新中は前の値を返す。失敗しても前の値を残し、値が無いときはシートの今日の値に戻る)。数え方は営業KPI の日次同期 (`fetch_outbound_by_user`) と同じ: 発信のみ・id で重複除外・JST の日に入るもの・`Auto Recorded` だけ、Zoom ユーザー → メール → HubSpot の担当者 (有効な人を優先)。今日より前の日はシートのまま。画面の「○○ 時点」は Zoom で数えた時刻になる。
- 発信数 (2026-10-20): 架電数の左に、相手が出る前に切ったもの・つながらなかったものを含む Zoom の発信すべてを「発信数」として出す。今日より前はシート `KPI営業_架電日次` の「発信」列 (`kaden_period` の `calls`)、今日は架電数と同じ Zoom の数え方から `Auto Recorded` の条件だけを外した件数 (同じ一回の取得で両方数える)。シートが読めないときは架電数と同じく null。アポ率は引き続きアポ数 ÷ 架電数。
- アポの数え方 (実装で確定。ステージは営業KPI と同じ `ST_APO` = `52035886` と `ST_APO_BPO` = `1095457875`):
  - 新規営業のアポ日確定 (`ST_APO`): `aposyutokubi` (JST) がステージに入った日の月に入り (`bpo_in_window` と同じ比較)、`aposyutokusya` が空でなければ、アポ取得者 `aposyutokusya` に付ける。無ければ取引の担当者 `hubspot_owner_id` に付ける。取得者は一度入ると残り続けるので月で絞る。インサイドセールスが取ったアポが取った人の数に入る (9/1 以降 1,277 件中 220 件は担当者と取得者が別)。
  - BPO のアポ日確定 (`ST_APO_BPO`): `bpo_appo_date` (JST) がステージに入った日の月に入り (`is_bpo` と同じ比較 `bpo_in_window`)、`bpo_26` が空でなければ、アポ獲得者 `bpo_26` に付ける。無ければ取引の担当者に付ける。担当者 (新規営業) には付けない。
  - どの取引も 1 人だけに付ける。アポを取った人は対象者の一覧に載っていなくてもその人に付ける (一覧に無ければ画面に出ないだけで、担当者には戻さない)。担当者に付けるのは取った人がいないときだけ。

### 集計の読み込み

- アポは日ごとにキャッシュして足す。確定した日は読み直さない。今日と昨日だけ 5 分で読み直す。架電数はシートから読む (営業KPI と同じ常駐キャッシュ)。
- 初めて 62 日分を読んでもアポは数回の Search。1 回の読み込みの上限は 600 回 (`counts.rs` の `MAX_SEARCHES`)。すべて `Background` 優先度 (§18)。
- 読み込みは画面の要求から切り離した。worker が毎周回、直近 `CALL_REVIEW_BACKFILL_DAYS` 日のアポを前もって数える。summary は数え終わっている日だけで答え、HubSpot を待たず 503 (`counting`) も返さない。数え終わっていない日は応答の `counting_days` に入れ、その日のアポは表に含めない。画面は「10/06〜10/08 のアポは数えている途中です」と出し、15 秒おきに取り直す。数え終わっていない日があるとき、要求は背景で読み始める (他が読んでいる最中なら任せる)。1 日だけの要求は他の日の数え中に待たされない。

### API (Google ログインした社内の人なら誰でも。2026-10-22 に管理者だけから変更。パスワードログインは 403 `google_login_required`、未ログインは 401、認可で落ちる限り外部を呼ばない)

| API | 内容 |
|---|---|
| `GET /api/crm/talk-review/summary?from&to&team` | 人ごとの表 (架電数・アポ数・アポ率・判定した本数・項目ごとのできていない割合) |
| `GET /api/crm/talk-review/calls?owner&from&to` | 1 人の電話の一覧 (日時・秒数・結果・項目ごとの ○ × −、助言の 1 文) |
| `GET /api/crm/talk-review/calls/{hubspot_call_id}` | 1 本の判定の詳細 (項目・判定・根拠の引用・次に言うとよいこと) と、Zoom から取り直した文字起こし |

期間は JST の日付。省略時は今日。最大 62 日。超えたら 400。`CALL_REVIEW_ENABLED` が未設定のときは summary が空の 200 (`enabled: false`) を返し、calls と詳細は 503 `not_configured` を返す。

### 画面

`/app/talk` (ナビ「トークの振り返り」。CRM と同じ条件で全員に出る)。管理画面の `/app/admin?view=talk` (「今日の架電成績」`view=callers` の隣) も同じ部品で残す。期間は今日・昨日・今週・先週・日付指定。チームで絞り込み。URL は `&from=&to=&team=&owner=&call=`。`&mode=fixture` で架空の数字を出す。

- 表は 1 行 1 人 (名前・チーム)。列は架電数、アポ数、アポ率 (アポ数 ÷ 架電数)、判定した電話数、項目ごとのできていない割合。最後の行はチーム全体。列見出しに資料の「全体でできていない割合」を小さく添える。
- 名前を押すとその人の電話の一覧、行を押すと判定の詳細と文字起こし (できていない根拠の発言に色) と HubSpot の Call へのリンク。
- 未判定・文字起こし待ち・取れない電話の本数も出す。判定した本数に「対象 N 本」(判定の対象になる 70 秒以上の電話、枠を超えて判定していない分を含む) を添え、割合はすべて判定した電話の中の割合だと画面の下に書く。API は人ごとに `eligible`、全体に `per_person_day`・`counting_days`・`dials_error`・`dials_partial`・`dials_fetched_at` を返す。人ごとの `dials` はシートが読めないとき null。

印の決まり (しきい値は 1 か所の設定にまとめ、画面の下に平易に書く):

- 項目の印: その項目の対象が 5 本以上で、本人のできていない割合がチーム全体の割合より 20% 以上高い。割合どうしの差で見る (例: チーム全体 30%、本人 50% 以上で印)。
- アポ率の印: 架電数が 100 本以上で、アポ率がチーム全体のアポ率の半分未満。
- しきい値は仮置き。現場で見ながら変えてよい。しきい値は `src/crm/talk_review/summary.rs` の `ALERT_RULES` の 1 か所にまとめる。画面に「pt」は出さず、割合を並べて見せる。

### 現行を保つ利点 / 変える利点 (AGENTS.md rule 16)

- 現行 (架電クオリティの日次バッチ + Google Sheets) を保つ利点: HR_HR の外で動き、アプリの障害の影響を受けない。Sheets は権限のある人が誰でも見られる。
- 変える利点: 無料枠の上限で止まっているバッチに頼らない。人ごとに選んで、判定の根拠を文字起こしと並べて見られる。判定結果が HubSpot の Call と同じ認可の中にある。
- 戻すコスト: `CALL_REVIEW_ENABLED` を外すと worker が止まる。画面・API を外せば機能は消え、表は残しても害はない。HubSpot・Zoom のデータは変わらない。

### 単一インスタンス前提

worker・判定の二重起動防止・Turso の書き込み絞り込みは、既存の再送 worker と同じく単一インスタンスを前提にする。複数台にする場合は、判定の取得に条件付きの claim が要る。

### 接触と日程切り (2026-10-22)

人ごとの表に「接触数・接触率・日程切り本数・日程切り率・1 接触あたりの日程切り回数」を足した。9 項目の判定とは別の周回 (`contact_worker.rs`) で動く。

- 定義: 接触 = 受付を越えて、営業が担当者・決裁者と話せた発信 (日程を出していなくても数える)。接触率 = 接触数 ÷ 発信数。日程切り本数 = 具体的な日時 (週・曜日・日付) を 1 回以上出した発信の本数、日程切り率 = 日程切り本数 ÷ 発信数。1 接触あたりの日程切り回数 = 接触した電話で日時を出した回数の合計 ÷ 接触数。分母の発信数は既存の「発信数」列 (Zoom の発信すべて) で、つながらなかった発信は接触 0・日程切り 0 として分母にだけ入る。
- 見つけ方: HubSpot ではなく Zoom の通話ログ (`phone/call_logs`) から、対象チームの人のつながった発信 (`result == "Auto Recorded"`) を、`live_dials` と同じ条件 (発信・ID で重複除外・JST の日・Zoom ユーザーのメールで担当者に結び付け) で拾う。初回は `CALL_CONTACT_BACKFILL_DAYS` 日 (既定 7、最大 62)、以後は今日と昨日だけを新しい日から見直す。録音は通話ログの ID で `recordings` を引く (`TranscriptSource::fetch`)。
- 判定: 文字起こしを MiniMax に渡し `{"contacted": bool, "date_proposals": 回数}` だけを返させる (長い電話は前から 8,000 字まで)。営業の声しか無い通話 (留守電など) は判定を呼ばずに接触なし。接触なしなら回数は 0。同時に `CALL_CONTACT_CONCURRENCY` 本 (既定 16、最大 64)。429 は全体で 60 秒待つ。再試行は 9 項目の worker と同じ間隔・回数で、取れない通話は「取れない」にして接触に数えない。
- 保存: 既存の監査 Turso に表 `call_contact_marks` (1 行 = つながった発信 1 本。判定結果は 0/1 と回数だけで、文字起こしは持たない)。書き込みは見つけたときのまとめ挿入 (50 行ずつ) と判定ごとの 1 回の更新だけ。つながらなかった発信は行を作らない。1 年で掃除する。
- 集計: `GET /api/crm/talk-review/summary` が人ごとと全体に `contacts` / `contact_rate_pct` / `date_proposal_calls` / `date_proposal_rate_pct` / `proposals_per_contact` / `contact_pending` を足す。率の分母が 0 または未取得は null、表を読めなければ全部 null (ほかの列は出す)。画面は `contact_pending` が 1 以上のとき「接触の判定待ち N 本」を添える。
