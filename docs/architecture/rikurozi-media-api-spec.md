# リクロジメディア 求人登録 API 連携仕様（案）

作成日: 2026-10-08
状態: 案（先方 API は未実装。本書をもとに先方と方式を決める）
読み手: リクロジメディア制作会社のエンジニア / 弊社 HR_HR チーム

表記: 「案」= 弊社からの提案で先方都合で変えてよいもの。「未確認」= 弊社で事実を確認できていないもの。

---

## 1. 目的と前提

- 弊社のシステム（HR_HR）から、リクロジメディアへ求人を **登録・更新・公開状態の切替** する。
- 求人の項目は、弊社が既に運用している求人媒体「HRハッカー」の求人 CSV と **同じ 84 項目** を使う。新しい項目体系は作らない。
- 渡し方は次の 2 方式を示す。先方がどちらか（または両方）を選んでよい。
  - **方式A**: JSON API（84 項目を「列名 → 値」で送る ＋ 管理用の項目を別ブロックで送る）
  - **方式B**: CSV アップロード（HRハッカーの 84 列 CSV をそのまま送る）
- 掲載する文面は、HRハッカーの求人票を基準に、同じ顧客（同じ取引先）で掲載中の AirWork の求人のどれとも重ならない文章として弊社側で生成する。給与・勤務時間などの事実は HRハッカーの値から変えない（6 章）。
- **範囲外**: 文面を生成するロジック（LLM の使い方・プロンプト等）。本書は「できあがった 84 項目をどう渡すか」と「事実を変えないための確認」だけを扱う。
- 弊社側の原則: 求人や取引の正本は HubSpot に置き、連携のために新しいデータベースは原則作らない（弊社 ADR）。

### 2.2 文字コード

- 案: **UTF-8**。CSV の場合は先頭に BOM（EF BB BF）を付ける。弊社の 84 列 CSV 出力は既に UTF-8 + BOM。
- 参考: HRハッカー本体からダウンロードする CSV は Shift-JIS。Shift-JIS で表せない文字（一部の記号・旧字体）があるため、リクロジメディアでは UTF-8 を希望する。

### 2.3 改行

- 値の中の改行は **LF（`\n`）** に統一して送る（案）。
- CSV の行区切りは CRLF。改行・カンマ・ダブルクォートを含む値は、RFC 4180 に従い全体を `"` で囲み、`"` は `""` にする（弊社出力は既にこの形式）。

### 2.4 画像の渡し方（要相談）

- 案: 画像 1〜3 は **公開 URL（https）** を渡し、先方が取得して保存する。
- 代案: 先方の画像アップロード API に先に送り、返ってきた画像 ID を「画像1〜3」に入れる。
- 確認したいこと: 対応形式（JPEG/PNG）、最大サイズ、縦横比、URL を先方がいつ取得するか（登録時に 1 回か）。

### 2.5 公開状態の切替

- 「公開」列（84 列目）で状態を指定する案と、専用の操作（方式A の 3.2）で切り替える案がある。方式A では専用操作を推奨（本文の更新と公開の切替を分けて、誤公開を防ぐため）。
- 求人の削除は、こちらからは行わない（案）。掲載をやめるときは「公開終了」にする。

### 2.6 弊社の求人キー `external_id`

- 弊社側の求人を一意に表すキーとして **`external_id`** を送る。先方はこれで「新規か更新か」を判断する。
- 84 列の「求人id」は HRハッカーが振った ID なので、**リクロジメディアのキーには使わない**。
- 形式（案）: 英数字とハイフン、最大 64 文字。例 `rl-0001234`。採番方法は弊社で決める（HubSpot の求人レコード ID を元にする案）。
- 先方の求人 ID（先方採番）は、登録時のレスポンスで返してほしい。

### 2.7 勤務地

- 84 列には勤務地住所の列が無い。HRハッカーでは「店舗id」で店舗マスタ（住所を含む）を参照している（店舗マスタの中身は未確認）。
- リクロジメディアでは勤務地（都道府県・市区町村・住所）をどう持つか要相談。案: 管理ブロック（方式A）または追加列（方式B）に `work_location`（都道府県 / 市区町村 / 住所）を足す。

## 3. 方式A: JSON API

### 3.1 エンドポイント案

| 操作 | メソッド / パス（案） | 内容 |
|---|---|---|
| 登録・更新 | `PUT /v1/jobs/{external_id}` | 無ければ作成、あれば全項目を置き換える（冪等な upsert） |
| 公開状態の変更 | `PUT /v1/jobs/{external_id}/status` | `{"status": "公開"}` など |
| 状態確認 | `GET /v1/jobs/{external_id}` | 先方の求人 ID・公開状態・最終更新日時・審査状況（あれば）を返す |

- PUT は「同じ内容を何度送っても結果が同じ」になるようにする。弊社は通信が途中で切れたときに同じ内容を再送するため（弊社 ADR-010）。
- 一部だけ更新する PATCH は不要（案）。毎回 84 項目すべてを送る。

### 3.2 認証案

- 案: 先方が発行する API キーを `Authorization: Bearer <キー>` ヘッダで送る。弊社サーバーからのみ送信し、ブラウザには渡さない。
- 代案: OAuth 2.0 クライアントクレデンシャル。送信元 IP の制限が必要なら弊社の送信元 IP を別途連絡する（Render の送信元 IP は固定でない可能性あり、未確認）。

### 3.3 リクエスト例（架空データ、項目は抜粋）

```http
PUT /v1/jobs/rl-0001234
Authorization: Bearer xxxxx
Content-Type: application/json; charset=utf-8
```

```json
{
  "schema_version": "1.0",
  "management": {
    "external_id": "rl-0001234",
    "client_code": "C-0099",
    "sent_at": "2026-10-08T10:00:00+09:00",
    "content_hash": "sha256:3f2a...",
    "work_location": { "prefecture": "東京都", "city": "江東区", "address": "架空1-2-3" }
  },
  "fields": {
    "案件名": "倉庫内のピッキング（日勤のみ）",
    "雇用形態": "アルバイト・パート",
    "給与形態": "時給",
    "基本給与 最小": "1200",
    "基本給与 最大": "1400",
    "勤務時間": "9:00〜18:00（休憩60分）",
    "自由項目1のタイトル": "休日・休暇",
    "自由項目1の内容": "土日祝休み",
    "仕事内容": "商品の棚から注文の品を集めて…",
    "画像1": "https://example.com/img/0001.jpg",
    "公開": "非公開"
  }
}
```

- `fields` には 84 列すべてのキーを入れる（値が無ければ空文字）。キーは列名そのまま（日本語）。英語キーが必要なら先方で対応表を用意してほしい。
- `management` は 84 列以外の管理情報。`content_hash` は弊社が同じ内容を重複送信していないか確認するための値で、先方は保存しなくてよい（案）。

### 3.4 レスポンス例

```json
{
  "external_id": "rl-0001234",
  "media_job_id": "RL-778899",
  "result": "created",
  "accepted_at": "2026-10-08T10:00:01+09:00",
  "status": "非公開"
}
```

`result` は `created` / `updated` / `unchanged`（案）。

### 3.5 エラー形式（案）

```json
{
  "error": "validation_failed",
  "message": "入力内容に誤りがあります",
  "field_errors": [
    { "field": "基本給与 最小", "code": "not_number", "message": "数値で指定してください" },
    { "field": "案件名", "code": "too_long", "message": "50文字以内で指定してください" }
  ]
}
```

- `field` は 84 列の列名（または `management.xxx`）で返してほしい。弊社画面で該当項目を示すため。

### 3.6 再送ルール（弊社側の動き）

| 応答 | 弊社の動き |
|---|---|
| 200 / 201 | 完了 |
| 429 | `Retry-After` 秒（無ければ一定時間）待って再送 |
| 5xx / タイムアウト / 通信断 | 間隔を広げながら再送（回数上限あり） |
| 400 / 401 / 403 / 404 / 422 | **再送しない**。弊社の担当者に通知して内容を直す |

- タイムアウトは 30 秒（案）。先方の処理が遅い場合は教えてほしい。
- 再送の待ち方・保存先は弊社の「Durable Retry（再送待ちの保持）」の仕組みで扱う（7 章）。

### 3.7 schema_version

- 項目の追加・変更に備えて `schema_version` を必ず送る。先方が知らない版を受け取ったら 400 で返してほしい（黙って無視しない）。
- 84 列に列が増えたときは版を上げ、事前に双方で合意する。

## 4. 方式B: CSV アップロード

### 4.1 エンドポイント案

| 操作 | メソッド / パス（案） |
|---|---|
| アップロード | `POST /v1/job-imports`（`multipart/form-data`、ファイル 1 つ） |
| 結果確認 | `GET /v1/job-imports/{import_id}` |

- 取り込みに時間がかかる場合は、アップロード時に `import_id` だけ返し、結果確認で処理完了を待つ（案）。

### 4.2 ファイル

- HRハッカー 84 列 CSV の形式（1 行目ヘッダ、UTF-8 + BOM、RFC 4180）。
- **1 ファイルに複数の求人（複数行）** を入れてよい（案: 上限 500 行。先方の上限を教えてほしい）。

### 4.3 `external_id` の持ち方（選択肢）

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| B-1 | **85 列目** に `external_id` 列を足す | 1 ファイルで完結。行とキーがずれない | 「84 列そのまま」ではなくなる |
| B-2 | 84 列の「求人id」列に `external_id` を入れる | 列数は 84 のまま | HRハッカーの ID と意味が混ざり、取り違えの元になる。**非推奨** |
| B-3 | 別ファイル（行番号 → external_id の対応 JSON）を同時に送る | CSV は 84 列のまま | 2 ファイルの対応が崩れると別求人を上書きする危険 |

弊社の推奨は **B-1**。管理情報（勤務地など、2.7）も 86 列目以降に足す形になる。

### 4.4 行ごとの結果

```json
{
  "import_id": "imp-20261008-0001",
  "state": "completed",
  "rows": [
    { "row": 2, "external_id": "rl-0001234", "result": "updated", "media_job_id": "RL-778899" },
    { "row": 3, "external_id": "rl-0001235", "result": "error",
      "field_errors": [ { "field": "給与形態", "code": "invalid_value", "message": "時給/日給/月給/年俸のいずれか" } ] }
  ]
}
```

- `row` は CSV の行番号（ヘッダを 1 行目とする）。行ごとに成功・失敗を返し、1 行の失敗でファイル全体を止めないでほしい（案）。

### 4.5 冪等性

- 同じ `external_id` の行は「上書き」とし、同じファイルを 2 回送っても求人が増えないようにしてほしい。
- 同じファイル内に同じ `external_id` が 2 行あればその行をエラーにする（案）。

## 5. 方式A / B の比較と推奨

| 観点 | 方式A JSON API | 方式B CSV アップロード |
|---|---|---|
| 先方の実装量 | API 3 本 + 項目検証 | アップロード + 非同期取り込み + 行ごとの結果 |
| 弊社の実装量 | 1 求人 1 リクエスト。単純 | CSV 生成は既存流用。結果の行と求人の対応付けが要る |
| エラーの分かりやすさ | 求人単位・項目単位で即時に返る | 取り込み完了まで待つ。行番号経由で対応付け |
| 再送の安全さ | PUT の冪等性で安全 | ファイル単位の再送で全行を送り直す |
| 大量の一括更新 | リクエスト数が多い（速度制限に注意） | 1 回で済む |
| 84 列との一致 | 列名をキーにするので一致 | そのまま一致（ただし external_id 列の追加が要る） |
| 公開切替 | 専用操作で本文更新と分けられる | 「公開」列で同時に変わる |

**弊社の推奨: 方式A（JSON API）**

理由:
1. 求人 1 件ごとに成功・失敗が即時に分かり、HubSpot の求人レコードへ結果をそのまま記録できる。
2. PUT の冪等な upsert により、通信障害時の再送で求人が二重登録されない。
3. 本文の更新と公開状態の切替を分けられ、誤って公開する事故を防げる。

一括の初期移行など大量投入が必要な場合に限り、方式B を併用してもよい。

## 6. 生成の基準と、変えない項目のシールド

### 6.1 考え方（2026-10-09 ユーザー決定）

- **基準は HRハッカーの求人票**。リクロジメディア版はある 1 件の HRハッカー求人から作る。
- **比べる相手は、同じ顧客（同じ取引先）で現在掲載中の AirWork の求人すべて**。そのどれとも文章が重ならないようにする。
- **AirWork のどの求人が「同じ仕事」かは特定しない**。「どれでもない」文章を作ればよいので、HRハッカーと AirWork の求人を 1 対 1 で結び付ける対応表は作らない。
- **事実は HRハッカーの値から写す**。次の項目は文章の言い回しが変わっても、値は HRハッカーの求人票と同じにする。
  - 給与（形態・金額・固定残業代・試用期間中の給与）
  - 勤務地
  - 勤務時間
  - 雇用形態
  - 休日

### 6.2 シールド（送信前の 3 つの確認）

1. **値は HRハッカーから写す**: 上の項目の列（2.1 の表で「シールド対象」）は、HRハッカーの 84 列 CSV（弊社 HubSpot に取り込み済み）の値をそのまま使う。文章生成（LLM）の出力は使わない。
2. **生成文が事実と矛盾しないか確かめる（案）**: 「仕事内容」「キャッチコピー」「メリット」など生成した文の中の数字（例: 時給 1,200 円、9 時〜18 時、残業月 10 時間）が、シールド値と一致するかを機械的に確かめる。一致しなければその項目は送らず、担当者の確認に回す。
   - 弊社の求人票作成機能には、生成文の数字が原文にあるかを確かめる仕組み（`validate_generated` の数値照合）が既にある。これをシールド値との照合に広げる案。
3. **どれとも重ならないか確かめる（案）**: 生成した文を、基準の HRハッカー求人と、同じ顧客で掲載中の AirWork 求人それぞれと比べる。どれか 1 つとでも似すぎていれば（例: 文字 n-gram の重なりが閾値以上。閾値は未決）送らず、作り直すか担当者の確認に回す。
   - 「同じ顧客」は HubSpot の取引先（取引・会社の関連）で決める。「掲載中」は AirWork の公開状態で決める（取得方法は実装時に確認。未確認）。
   - 比べた相手の件数と、いちばん近かった相手との重なりの度合いを、管理用の項目（3.3 の `management`）に残す案。

### 6.3 AirWork の扱い

- AirWork の求人は「比べる相手」として本文を読むだけで、値の写し元にはしない。
- そのため、HRハッカーと AirWork の列の対応表は作らない（以前の版の対応表は削除した）。

## 7. 弊社側の扱い

- **送信状態・先方 ID の記録（案）**: HubSpot の求人レコードに、リクロジメディアの求人 ID・最終送信日時・送信結果（成功 / 再送待ち / 失敗）・最後に送った内容のハッシュを残す。求人の正本は HubSpot であり、送信履歴のために新しいデータベースは作らない。
- **再送待ち**: 429 / 5xx / タイムアウトで送れなかった求人は、弊社 ADR-009 の「Durable Retry / Pending Sync」の仕組みで保持して再送する。保持する場所は未決定（候補は既存の監査用 Turso への表追加など）。保持するのは「まだ先方に届いていない送信」だけ。
- **恒久エラー**: 400 / 401 / 403 / 404 / 422 は再送せず、担当者に通知する。
- **画面表示**: 送信状態を「先方に反映済み / 再送待ち / 失敗（要対応）」で区別して見せる。どこにも保存できていないのに「送信しました」とは表示しない。
- **シールドで止まった求人**: 送信しない。担当者が確認・修正した後に送る（事実の不一致、似すぎ）。

## 8. 先方への確認事項

1. 方式A / 方式B のどちらを採用するか（両方か）。
2. 84 列のうち、先方で必須の項目・使わない項目・文字数上限・値の候補（給与形態、雇用形態、フォームの種類、公開状態）。
3. 弊社の `external_id` を先方で保存し、新規/更新の判定に使えるか。先方の求人 ID はレスポンスで返せるか。
4. 同じ内容の再送（PUT / 同じ行の再アップロード）で求人が二重にならないこと。
5. 勤務地を何で持つか（住所文字列 / 都道府県・市区町村コード / 先方の店舗マスタ）。
6. 画像の渡し方（URL 取得か、事前アップロードか）と形式・サイズ上限。
7. 公開状態の種類と切替方法。掲載前の審査があるか、あるなら審査結果の確認方法。
8. 認証方式（API キー / OAuth）、キーの発行・更新手順、IP 制限の有無。
9. 速度制限（1 秒・1 日あたりのリクエスト数、CSV の行数・ファイルサイズ上限）と、超えたときの応答（429 と `Retry-After`）。
10. エラー応答で項目名（84 列の列名）を返せるか。
11. 文字コード（UTF-8 で問題ないか）、値の中の改行の扱い、使えない文字。
12. 日時の書式とタイムゾーン。
13. テスト環境（本番と分けた送信先）の有無。
14. 項目追加など仕様変更時の連絡方法と `schema_version` の運用。
15. 求人の削除が必要になる場面があるか（弊社は「公開終了」で代える想定）。
