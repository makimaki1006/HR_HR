# コンサルKPI と 案件管理（求人管理）の役割の仕分け

更新日: 2026-10-17
状態: 仕分け案（ユーザー確認待ち）。機能の修正・改善はしない。今ある機能をどちらに置くかを分けるだけ。

## 0. 前提（2026-10-17 ユーザー）

- 2 つの画面は、いずれ 1 つのアプリにまとめる予定。ただし見る人と目的が違うので、機能ははっきり分ける。
- **コンサルKPI（`/consulting`）**: 管理職が、部下（コンサルタント）を管理する画面。
- **案件管理（`/app/job-copy`）**: コンサルタント本人が、自分の顧客の案件を管理する画面。

## 1. それぞれの役割（要件）

| | コンサルKPI（管理職） | 案件管理（コンサルタント） |
|---|---|---|
| 誰が | 管理職 | コンサルタント本人 |
| 答える問い | 誰の手が回っていないか。チームとして継続・成果は出ているか | 今日、自分はどの案件に何をするか。自分の求人はうまくいっているか |
| 単位 | 担当者・チーム・月 | 案件・求人・顧客 |
| 見せ方 | 担当者ごとの件数・率・推移（集計） | 1 件ずつの明細と、その場での操作 |
| 書き込み | しない（読むだけ） | する（契約・成果・ステージ・次の予定を HubSpot へ） |
| 数字の新しさ | 前日の集計で確定した数字でよい（日中に動かない方が比べやすい） | 今の値（HubSpot）。MTG・担当交代だけシートの前日の値 |
| 明細を見たいとき | 案件管理の案件の画面へ飛ぶ | — |

**分ける原則**

1. **操作するもの（書き込み・次の予定）は案件管理だけ**に置く。コンサルKPI は読むだけ。
2. **1 件ずつの明細は案件管理**、**人ごと・月ごとの集計はコンサルKPI**。同じ案件をコンサルKPI で見たいときは、案件管理の画面へ飛ばす（明細を 2 か所に作らない）。
3. **定義（継続率・MTG 途絶・名札・初回の目安など）は 1 か所**にして両方で使う。今も `cs_dashboard` の判定を案件管理が共用している。

## 2. 今ある機能の仕分け

記号: ◎ = ここに置く ／ → = もう一方へ移す（または相手側へのリンクにする） ／ △ = 両方に要るが見せ方を分ける

### 2-1. コンサルKPI にある機能

| 今の画面（コンサルKPI） | 中身 | 仕分け | 理由・分け方 |
|---|---|---|---|
| 今日 | 今日出す先（名札 2 本以上の上位 24 件）、今週満了、今週始まった契約、KPI 6 枚 | → 案件管理 | 「今日自分が何をするか」はコンサルタントの問い。案件管理のホーム（要対応・予定）が同じ役割。管理職向けには「担当者ごとの要対応の件数」だけ残す（2-3 の △） |
| 案件一覧 | 稼働中の全案件 15 列 | → 案件管理 | 案件管理の「案件の一覧」（#249）と同じ。明細は案件管理に一本化 |
| 担当者ごとの案件 | 担当を選ぶと、その人の案件一覧 | △ | 管理職の入口は「担当者ごとの件数・状態の表」（コンサルKPI）。担当者を押したら案件管理の案件の一覧をその担当で開く |
| 案件の詳細 | MTG・電話・担当交代の時系列、次の行動、同じ法人の他契約 | → 案件管理 | 1 件の明細なので案件の画面へ。コンサルKPI からはリンク |
| 顧客 / いま見るべき顧客 | 法人単位の状況、注力顧客 | △ | 顧客 1 社の明細は案件管理の顧客の画面。管理職向けには「注力顧客のうち手が回っていない数（担当者別）」 |
| 満了と継続 | 今月・来月・再来月の満了件数と金額、満了を過ぎて稼働中 | △ | 管理職: 月ごとの件数・金額の見通し（コンサルKPI）。コンサルタント: 自分の満了が近い案件（案件管理の要対応「契約満了が近い」にもうある） |
| チームと担当 | 担当者数、担当者×状態、接触の推移、担当交代の前後 | ◎ コンサルKPI | 部下を管理する問いそのもの |
| 電話 | 電話の状況（担当者別の接触など） | ◎ コンサルKPI | 担当者を比べる集計 |
| 成果と継続 | 月次継続率（件数・金額）、目標到達、立ち上がり、リスク、NPS・採用単価・LTV、本部アプローチ | ◎ コンサルKPI | 月の振り返り・本部へ持っていく材料 |
| 立ち上がり（成果と継続の中） | 契約の進み具合の分布、開始から初回 MTG までの日数、MTG 記録の無い初回契約 | △ | 管理職: 分布と遅れの件数（コンサルKPI）。コンサルタント: 自分の初回案件 1 件ずつ（案件管理の「初回案件だけ」#250） |
| 記録と数字の信頼度 | データの欠け・偏り、MTG 記録の確かさ、定義 | ◎ コンサルKPI | 数字を読む側（管理職）が確かめるもの。案件管理には出さない |

### 2-2. 案件管理にある機能

| 今の画面（案件管理） | 中身 | 仕分け | 理由・分け方 |
|---|---|---|---|
| ホーム: 要対応・予定・次の予定を入れる | 満了が近い・接触が空いた・応募が止まった・初回で成果が出ていない・NPS・採用目標・採用単価・MTG 途絶。期限切れ・今日・7 日以内の予定 | ◎ 案件管理 | 自分が今日やることそのもの。既定は「コンサル担当 × 自分」 |
| ホーム: 求人のカード | 応募ゼロのまま・ゼロになった・減った・増えた・ほぼ同じ・課金が高いまま応募が少ない・データが止まっている | ◎ 案件管理 | 自分の求人の手当て |
| ホーム: 直近 7 日に変更（内訳つき） | 変えた求人と、その求人の状態の内訳 | ◎ 案件管理 | 自分が変えた求人の確認。管理職向けには不要（必要なら「担当者ごとの変更件数」を後で検討） |
| ホーム: 顧客の表 | 顧客ごとの案件数・求人数・応募・課金 | ◎ 案件管理 | 自分の顧客の一覧 |
| 担当者で絞る | 既定は自分。ほかの担当者も選べる | △ | 案件管理は「自分」が既定。他人を選ぶのは代理・引き継ぎのときだけ。部下を見比べるのはコンサルKPI |
| 案件の一覧（#249）・初回案件だけ（#250） | 印・満了まで・最後の接触・最後の MTG・採用目標に対して・金額、初回の応募の立ち上がり | ◎ 案件管理 | 自分の案件の明細 |
| 案件の画面 | 契約・成果の編集、ステージ変更、次の予定、求人（掲載中／過去）、週ごとの応募、求人の横並び比較 | ◎ 案件管理 | 案件を動かす操作。コンサルKPI からのリンク先 |
| 顧客の画面 | 掲載中／過去の求人、案件 | ◎ 案件管理 | |
| 求人の画面 | タイムライン・ライフライン、本文・画像、応募推移・応募者構成・応募理由、課金・クリック、市場グラフ・要因と仮説、変更差分・全文比較、求人比較、顧客報告・検証 | ◎ 案件管理 | 求人を良くするための作業。管理職は使わない |
| 応募者で探す・横断比較 | 応募者の条件から求人を探す、取り込んだ求人を横に並べる | ◎ 案件管理 | |
| データ取込（HubSpot 読み取り・媒体の取込・課金 CSV）、外部文面の確認、職種をまとめて指定 | 運用の操作 | ◎ 案件管理（ツールの中） | コンサルタントまたは運用担当が使う。管理職の画面には置かない |

### 2-3. 両方に要る（△）ものの見せ方

| 中身 | コンサルKPI（管理職） | 案件管理（コンサルタント） |
|---|---|---|
| 要対応（名札） | 担当者ごとの件数（例: 担当A 要対応 12 件・うち MTG 90 日以上途絶 3 件）と推移 | 1 件ずつの印と、その場で次の予定を入れる |
| 満了 | 月ごとの件数・金額の見通し、満了を過ぎて稼働中の件数（担当者別） | 自分の満了が近い案件 |
| 初回の立ち上がり | 遅れている初回案件の件数（担当者別）、立ち上がりの分布 | 自分の初回案件の応募・目安との比べ |
| 担当者ごとの案件 | 担当者×状態の表（件数） | 担当者で絞った案件の一覧（押すとここへ飛ぶ） |
| 顧客 | 注力顧客のうち手が回っていない件数（担当者別） | 顧客 1 社の明細 |

### 2-4. コンサルKPI が案件管理から吸い上げる情報（2026-10-17 ユーザー）

コンサルKPI は上流のマネジメントの画面として、案件管理で起きたこと（コンサルタントの動き）とその結果を、担当者ごとに分かるようにする。中身の明細は案件管理に置いたまま、コンサルKPI は**記録（ログ）と数を吸い上げて、人ごと・期間ごとにまとめる**。

| 吸い上げる情報 | 元（案件管理側で今あるもの） | コンサルKPI での見せ方（例） |
|---|---|---|
| 求人票をいつ直したか | 求人の変更の記録（本文・給与・求人名の変更日時。直近 7 日の変更・求人のタイムラインと同じ元） | 担当者ごとの「今週・今月に直した求人の数」、直した求人の一覧（いつ・どの案件・何を変えたか）、長く直していない求人の数 |
| 直した後の応募 | 求人の応募（週ごと）と、ホームの分類（応募が減った・増えた・ゼロのまま など） | 担当者ごとに、直した求人のうち直す前の 4 週と後の 4 週で応募が増えた・減った数。応募が止まっているのに直していない求人の数 |
| 応募の情報 | 案件・求人に結び付いた応募（件数・応募日） | 担当者ごと・月ごとの応募数の推移、初回案件の立ち上がりの遅れの数 |
| 次の予定を入れているか | 案件の CSアクション予定日・内容（案件管理から入れたもの） | 担当者ごとの「予定の入っていない稼働中の案件」の数、期限切れの予定の数 |
| 契約・成果・ステージの更新 | 案件管理から HubSpot へ書いた操作の記録（誰が・いつ・どの項目） | 担当者ごとの更新の件数、成果（応募・面接・採用）の入力漏れの数 |
| 要対応の印 | 案件管理の要対応（満了が近い・接触が空いた・MTG 途絶 など） | 担当者ごとの件数と推移（2-3 の表） |

**吸い上げ方の考え方（実装は別に決める）**

- 吸い上げるのは「いつ・誰の案件で・何が起きたか」と数だけ。本文や応募者の個人情報はコンサルKPI に持ってこない。
- 定義は案件管理と同じものを使う（例: 「直した」は直近 7 日の変更と同じ判定、応募の増減はホームの分類と同じ判定）。
- 明細を見たいときは、案件管理の求人の画面・案件の画面へ飛ぶ。
- 決めること: 元の記録をどこから読むか（HubSpot の変更履歴・応募をコンサルKPI が直接読むか、案件管理がまとめた結果を渡すか）、どの期間で見るか（週・月）、前日確定の数字にするか。

## 3. 決めておくこと（仕分けを実装に移すとき）

- **管理職の権限**: 案件管理で他人の案件を書き換えられるか（今は誰でも書ける）。管理職がコンサルKPI から飛んだ先で直すことを許すか。
- **コンサルKPI の数字の新しさ**: 前日の確定値のままにするか、案件管理と同じ今の値に寄せるか。分けるなら「管理職は前日確定・コンサルタントは今」で食い違いが出ることを画面に書く。
- **リンクの向き**: コンサルKPI → 案件管理の案件の画面・案件の一覧（担当者で絞った状態）へ飛ぶ。逆向き（案件管理 → コンサルKPI）は要らない想定。
- **入口**: 1 つのアプリにまとめるとき、管理職とコンサルタントで最初に開く画面を分けるか（役割で既定の画面を変える）。

## 4. 現行を保つ利点 / 分ける利点

- **現行を保つ利点**: 作り直しが要らない。コンサルKPI だけで日々の案件も見られる。
- **分ける利点**: 見る人ごとに画面の目的が 1 つになる。明細と操作が案件管理の 1 か所になり、同じ案件を 2 か所で作らない。管理職は人と月の集計に集中できる。
- **戻すコスト**: 仕分けだけなので、コードの変更は無い。
