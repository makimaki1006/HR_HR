## 0. 要点

- HR_HR の `/app/call-practice` に React の画面を 1 つ足す。Rust / Axum の上に API を足し、LLM はサーバからだけ呼ぶ。
- 練習するのは、アポの日時が決まった後のヒアリング (2〜3 分)。お客さん役は「日時に了承した」ところから始まる。
- お客さん役は、型ごとの「隠れた答え」「性格」「言い回しの例」を渡された LLM が、その場で返す。言い回しの例はユーザーが大量に作って渡せる形にする。
- 採点は、ヒアリングの台本 v1 の 4 項目 (時期と人数 / 課題と意欲 / 検討と予算の有無 / 決める人と同席) が取れたか、「聞けていない」が残ったか、嫌がられた場面、質問の数、型の見立てが合ったか。
- 文字起こし (発言の並び) から 4 項目の取れ方を読む部分は、将来の「架電助言アプリ」と共有する。練習だけが持つのは「隠れた答えとの照らし合わせ」と「見立ての答え合わせ」。
- 発言の形は既存のトークの振り返りと同じ `TalkTurn` (番号・話し手・文) にそろえる。音声を足すときは、音声を文字にして同じ形で流し込むだけで済む。
- 練習の記録を残すか、残すならどこに置くかは未決 (§9)。第 1 段は保存しない形で出せる。

## 2. 既存の仕組み (調べた結果)

### 2.1 画面

- React の画面は `/app/{screen}` で配信する。Rust の `src/handlers/spa_shell.rs` が Vite の manifest を読み、HTML の殻 (`<div id="app-root">`) を返す。画面を足すときは 3 か所を足す。
  - `KNOWN_SCREENS` (`src/handlers/spa_shell.rs`) に名前
  - `frontend/src/entries/{screen}.tsx` (入口)
  - `frontend/vite.config.ts` の `input`
- トークの振り返り `/app/talk` が一番近い例。入口 `frontend/src/entries/talk.tsx`、画面 `frontend/src/screens/talk/TalkScreen.tsx`、中身は `frontend/src/screens/admin/TalkPanel.tsx` を使い回している。URL のクエリで画面の状態を持つ (`useQueryRoute`)。架空の数字で動かす `?mode=fixture` がある。
- ナビは Rust の `src/handlers/nav.rs` が `/api/nav` で返す。`/app/talk` は `requires: Some(Feature::Crm)` (CRM を開ける人だけに出す)。`hidden` フラグで隠せる。
- 共通部品: `frontend/src/components/` (DataTable / KpiCard / Note / EChart / DatePicker)、`frontend/src/shared/phrases.ts` (禁止の言い回しの検査)。
- API の呼び出し: `frontend/src/api/client.ts` の `apiGet` / `apiPost` / `apiPatch` / `apiPut` / `pollJob`。すべての要求に `X-Requested-With: fetch` を付ける (CSRF の確認、`src/lib.rs check_csrf`)。既定のタイムアウトは 15 秒。
- 型: Rust の構造体に `#[derive(Serialize, TS)]` を付け、ts-rs (`Cargo.toml` の `ts-rs = "12.0.1"`) で `frontend/src/generated/` に TypeScript の型を書き出す (現在 393 ファイル)。例: `src/crm/talk_review/types.rs`。

- どれもサーバ (Rust) から呼び、鍵はブラウザに渡していない。この練習アプリも同じにする。
- 判定の部品は差し替えられる形になっている。`Completer` (プロンプトを送って JSON を返す) と `Judge` のトレイトがあり、テストでは偽物に差し替えている。この練習アプリもこの `Completer` を使い回す。
- MiniMax は従量課金でなく月額の枠 (5 時間ごとと週ごとの上限)。上限に届くと、本番のトークの振り返りの判定も止まる (2026-10-26 に一度起きた)。練習で使う分も同じ枠を分け合う。

### 2.3 認証と役割

- トークの振り返りの API は `rbac::authorize(session, state, &ctx.access, None)` を通す (`src/crm/talk_review/routes.rs` の `login_gate`)。条件は、Google ログイン (会社ドメイン)・許可リスト・無効化されていないアカウント。役割は問わない。パスワードのログインは 403 `google_login_required`、未ログインは 401。
- 役割 (`access.role_of`) は監査 DB (`accounts.role`) から読める。管理者だけに絞る API は、同じ関門のあとで役割を確かめている。

### 2.4 保存先の決まり

- 新しい種類の保存先 (PostgreSQL・Redis・新しい Turso の DB など) は足さない (AGENTS.md rule 7)。既存の監査 Turso に表を足すのは候補になるが、採るなら ADR に理由を残す。
- 独自の CRM DB は作らない (ADR-006)。練習の記録は CRM のデータ (先方・取引) を持たないので、この決まりの対象とは別だが、置くなら監査 Turso の表になる。
- 監査 Turso は 2026-01 に請求の超過があり、書き込みの回数を絞る方針 (ADR-018 / ADR-033 ほか)。

## 3. 画面の流れ

URL: `/app/call-practice`。画面の状態は URL のクエリ (`?session=...&step=...`) に持つ (再読み込みで同じ練習に戻れる)。架空のお客さん役で動かす `?mode=fixture` も持つ (E2E と画面の確認用。LLM を呼ばない)。

### 3.1 練習を始める

- 説明を 3 行だけ出す: 「アポの日時が決まった直後から始まります」「台本の 4 項目を聞いて、記録欄に書いてください」「終えたら、取れた項目と、お客さんの本当の答えを見せます」。
- 「練習を始める」のボタン。
- 台本を横に出すか (見ながら / 見ないで) を選ぶ (未決 §9-7)。

### 3.2 型を伏せて割り当てる

- サーバが型を 1 つランダムに選ぶ。同じ型が続いてもよい (2026-10-29 ユーザー)。画面には型の名前を出さない。
- 型の中身 (職種・人数・時期など) は型ごとに固定し、ランダムに変えない。分岐が少なく、変えても練習の中身はあまり変わらないため (2026-10-29 ユーザー)。
- 応答には練習の番号と、お客さん役の最初の一言 (例: 「はい、ではその日でお願いします」) だけを入れる。隠れた答えはブラウザに送らない (開発者ツールで見えないようにする)。
- 型を指定して始める道 (復習・管理者の確認用) を付けるかは未決 (§9-6)。

### 3.3 やり取り

```text
┌──────────────────────────────┬──────────────────────┐
│ やり取り                     │ 記録欄               │
│  お客さん: はい、では…       │ ① 3か月以内の職種と人数│
│  あなた: ありがとうございます│ ① それ以外の募集      │
│  お客さん: …                 │ ② 課題と解決意欲      │
│                              │ ③ 検討できそうか      │
│                              │ ③ 予算の有無          │
│ [入力欄              ][送る] │ ④ 決める人と同席      │
│                              │ 見立て: 熱い/…       │
│ 経過 1:42                    │ [終える]             │
└──────────────────────────────┴──────────────────────┘
```

- 練習する人の入力は、最初から音声にする (2026-10-29 ユーザー決定)。ブラウザ (Chrome) の音声認識 (Web Speech API、ja-JP、途中の文字あり、続けて聞き取る) を使い、追加の依存・サーバ側の音声処理は足さない。
  - 話している途中の文字を画面に出し、認識が確定して約 0.9 秒、または確定しないまま無音が約 1.8 秒続いたら、自動で送る。「話す／止める」のボタンを置く。
  - 音声認識が使えないブラウザ・マイクを許可されなかったときは、文字入力に切り替えて、その旨を出す。文字入力の欄は常に残し、手で直して送れる。
  - お客さん役が返事を出している間は、聞き取った文字を送らず捨てる。返事が終わってから受け付ける。
  - お客さん役の返事は文字のまま (声にするのは後の段)。
- 自分の発言を送ると、お客さん役の返事が返る (目安 3 秒以内。§6.4)。
- 記録欄は台本の「記録する欄」と同じ欄。選択肢の欄は選択肢で、職種・課題は短い文で書く。どの欄にも「聞けていない」を選べる。
- 質問の数・型・残り時間などの採点に関わる数は、やり取りの間は出さない (見ながら数を合わせると練習にならないため)。経過時間だけ出す。
- お客さん役が会話を閉じることがある (嫌がり方が上限に達した、または締めの挨拶を受けた)。そのときは入力欄を閉じ、「記録を見直して終える」に進ませる。
- 往復の上限は 30 回 (未決 §9-11)。上限に来たら同じく終えるところへ進む。

### 3.4 終える

- 「終える」を押すと、記録欄の空欄を確かめる。空欄が残っていれば「空欄は『聞けていない』として採点します」と出し、そのまま進むか戻るかを選ばせる。
- 見立て (熱い / どちらとも言えない / 冷めている) は必須 (段階の数は未決 §9-4)。
- 送ると、記録と見立てがサーバに渡り、採点が返る (LLM を 1 回呼ぶので 5〜15 秒。待つ間は「採点しています」を出す)。

### 3.5 採点と振り返り

上から順に出す。

1. **4 項目の表**: 項目ごとに「取れた / 記録違い / 聞けていないと記録 / 空欄 / 聞かずに記入」(§5.2) と、あなたの記録・お客さんの本当の答え・その答えが出た発言の番号を並べる。
2. **「聞けていない」が残った項目**: 数と、どの項目か。
3. **嫌がられた場面**: 発言の番号・お客さんの言葉・直前のあなたの言葉。押すとやり取りのその場所へ移る。
4. **質問の数**: あなたの質問の数と、報告書の帯ごとの成約率 (§5.4)。
5. **見立て**: あなたの見立て、お客さんの型の熱さ、隠れた答えにあった熱い印の数と、そのうち聞き出せた数。
6. **良い例・悪い例**: やり取りから、良かった発言と直すとよい発言をそれぞれ 1〜3 個、発言の番号と一緒に。直すとよい発言には台本の言い回しを添える。
7. **お客さんの型の明かし**: 型の名前と、報告書にある参考の成約率 (§4.2)。
8. ボタン: 「同じ型でもう一度」「別の型で練習する」。

参考の成約率の下には注記を 1 行出す: 「成約率は相関の値。聞き方を変えたときの成約の増え方は示していない。人・時期をそろえていない素の率」。(phrase_validator の禁止語「確実に」「必ず」「100%」を出さない。)

## 4. お客さん役の作り方

### 4.1 構成

お客さん役は 3 つの材料から作る。

| 材料 | 中身 | 作る人 |
|---|---|---|
| 型 (persona) | 隠れた答え・性格・答えの出し方の決まり | ユーザーが作り、レビューして入れる (数十個の想定) |
| 言い回しの例 (phrase bank) | 「どの項目の、どの答えを、どんな口調で言うか」の例文 | ユーザーが大量に作れる (数千件の想定) |
| 決まり (rules) | 型を外れない・最初から全部言わない等の共通の指示 | この設計で決める (§4.4) |

毎ターン、サーバは「型 + その型に合う言い回しの例から数件を抜き出したもの + 決まり + これまでのやり取り + 今まで出した答えの記録」をプロンプトにして LLM を 1 回呼ぶ。言い回しの例が何千件あっても、1 回に入れるのは数十件なので、費用と速さは件数に比例しない。

### 4.2 型の一覧 (第 1 段の案)

型は隠れた答えの組み合わせで作る。下の参考の成約率はまとめの報告書の値 (該当の成約率、括弧内はそれ以外の成約率と件数)。平均は HubSpot のアポ 4.4% (17,651 件中 771)。

| 型 | 隠れた答えの組み合わせ | 参考の成約率 |
|---|---|---|
| 熱い型 | 3 か月以内に複数名・課題が具体的で早く解決したい・前向き・予算あり・決める人は本人・当日同席する・導入時期 1〜2 か月 | 導入時期 1〜2 か月以内 × 予算あり × 拠点で決裁 16.5% (それ以外 4.4%、236 件中 39)。良い答えが 4 つ 14.7% (204 件中 30) |
| 冷たい型 | 急いでいない・足りている・課題は無いか弱い・決める人が遠い (本社・別部署)・同席しない | 急いでいない・足りている (電話) 2.9% (それ以外 6.3%、629 件中 18)。決める人が遠い 3.0% (それ以外 5.6%、463 本中 14)。良い答えが 0 つ 3.3% (5,458 件中 181) |
| 予算なし→後で変わる型 | 最初は「予算はない」。月額定額と聞いて内容次第と分かると「内容次第では」に変わる。それ以外は中くらい | 電話で「無い・難しい」と言い、後で予算ありに変わった取引 9.1% (後も変わらない 1.3%、55 件中 5)。電話の「無い・難しい」全体 4.6% (予算あり 6.3%、345 件中 16) |
| 一存では決められない型 | 「私の一存では」。決める人は上の人。同席は未定 | 「自分では決められない」(電話) 2.0% (それ以外 6.5%、251 本中 5) |
| いい人がいれば型 | 採用は「いい人がいれば」。人数があいまい (2 回目の言い換えで幅が出る) | 報告書に該当の成約率は無い (台本の記録欄で冷めている印) |
| 話し好き型 | 聞かれた項目に関係する事情を 1 つ自分から添える (例: 職種を聞かれて、前任が辞めて困っていることも話す)。中身は熱い型に近い | 報告書に該当の成約率は無い (2026-10-29 ユーザー: 聞く前に事情を話す人もいる) |
| 忙しい型 | 時間を気にする。質問が 3 つを超えると「今忙しいので」。①と④だけなら答える | 報告書に該当の成約率は無い (嫌がる言葉の約 3 分の 2 が時間の言葉、30 件中約 20 件) |

- 「熱い」「冷めている」の印は、台本の「記録する欄」の熱い印・冷めている印をそのまま使う。型の熱さは、隠れた答えにある熱い印の数から規則で決める案と、型に手で付ける案がある (未決 §9-4)。
- 台本が聞くのは「採用の時期」で、報告書で一番成約率が高いのは「導入時期」。両者の重なりは未確認 (報告書の「まだ確かめていないこと」)。型には両方を持たせ、導入時期は聞かれたときと、先方から話すときだけ出す。

| `personality.talkative` / `guard` | 0〜3 (話の長さ、答えるまでの渋さ) |
| `personality.patience` | 嫌がり始めるまでの質問の数 (目安。報告書では質問の数と嫌がられ方の向きが逆だったので、型ごとに決める) |
| `reveal` | 答えが変わる条件。`after` は `monthly_fee_told` (月額定額と聞いた) / `asked_twice` (2 回目の聞き方) / `reason_asked` (理由を 1 つ確かめられた) |

`setting` の業種・規模は架空の会社の説明に使う。実在の会社名・人名・地名・電話番号は入れない。

### 4.4 言い回しの例 (ユーザーが作るデータ)

1 行 1 件の JSON Lines (`.jsonl`) を案とする。表計算で作って書き出しやすく、件数が増えても差分が読みやすい。

```json
{"slot":"budget","value":"no","tone":"丁寧","text":"今は採用に予算は取っていないんです"}
{"slot":"budget","value":"yes_depends","tone":"丁寧","text":"内容と金額次第ですね、ものによっては出せると思います"}
{"slot":"decider","value":"boss","tone":"ぶっきらぼう","text":"私の一存ではちょっと。上に上げないと"}
{"slot":"hiring_3m","value":"vague","tone":"丁寧","text":"いい人がいれば、という感じですね"}
{"slot":"busy","value":"","tone":"丁寧","text":"すみません、このあと予定があって、手短にお願いできますか"}
{"slot":"irritated","value":"","tone":"ぶっきらぼう","text":"それ、当日じゃだめですか"}
```

| 欄 | 決まり |
|---|---|
| `slot` | `hiring_3m` / `hiring_later` / `issue` / `urgency` / `consider` / `budget` / `decider` / `attend` / `intro_timing` / `price_question` / `busy` / `irritated` / `closing` / `other` |
| `value` | その項目の答えの値 (§4.3 の値と同じ。`vague` などの追加の値を許す)。`busy` などは空 |
| `tone` | `丁寧` / `ふつう` / `ぶっきらぼう` |
| `text` | 120 文字まで。実在の会社名・人名・地名・電話番号・メールアドレスを含めない |
| `persona` (任意) | 特定の型だけで使う例なら型の `id` |

受け取るときの検査 (Rust のテストで CI に入れる):

- 欄の値が上の一覧にあるか。`slot` と `value` の組が型の値と合うか。
- `text` の長さ。電話番号の形・メールアドレスの形・「株式会社」「有限会社」「様」の前の固有名詞らしい並びを見つけたら落とす (固有名詞を全部は見つけられないので、作る側で置き換えることを前提にする)。
- 日本語以外の混入 (既存の `lang.rs` の検査を使う)。
- 同じ文の重複。

置き場所 (リポジトリのファイル / 監査 Turso に管理画面から入れる / Google スプレッドシート) は未決 (§9-3)。

### 4.5 実例から作るときの決まり

- 実際の電話の文字起こしから言い回しを作るときは、言い方の型だけを残し、会社名・人名・地名・職種の細部・数字を置き換える。
- 1 件の電話を丸ごと再現する型は作らない (どの会社か特定できるため)。
- リポジトリに入れる前に、検査 (§4.4) を通す。

### 4.6 型を外れない・最初から全部言わないための決まり

1 回の呼び出しで、LLM に次の JSON を返させる。

```json
{
  "asked_slots": ["budget"],
  "is_question": true,
  "reply": "今は採用に予算は取っていないんです",
  "revealed_slots": ["budget"],
  "mood": "normal",
  "end": false
}
```

プロンプトの決まり (システム側の指示):

1. あなたは「日時に了承したばかりの採用担当者」。助言・解説・採点をしない。
2. 隠れた答えから外れたことを言わない。隠れた答えに無いことを聞かれたら、型の性格に合わせて「特にないです」「分からないです」と答える。
3. 聞かれた項目だけに答える。1 回の返事で答える項目は 1 つ (`talkative` が 2 以上なら 2 つまで)。聞かれていない項目は、`asks_price_unprompted` などの決まりがあるときだけ自分から出す。
4. あいまいに聞かれたら、あいまいに答える (例: 「人は足りていますか」には「まあ、ぼちぼちですね」)。答えの値は、具体的に聞かれたときに出す。
5. `reveal` の条件 (月額定額と聞いた、2 回目の言い換え、理由の確かめ) を満たすまで、最初の答えを変えない。
6. 質問の数が `patience` を超えたら、`irritated` / `busy` の言い回しで嫌がる。さらに 3 つ超えたら `end: true` で会話を閉じる。
7. 返事は 80 文字まで。言い回しの例の口調に合わせる。例文をそのまま使ってもよい。
8. 締めの挨拶を受けたら、挨拶を返して `end: true`。

サーバ側の確かめ (LLM の言うことだけに頼らない):

- 練習ごとに「これまで聞かれた項目」「出した答え」「質問の数」「嫌がった回数」をサーバが持つ。毎ターン、そのときに出してよい項目と答えの値をプロンプトに書き込む。
- 返ってきた `revealed_slots` が「これまで聞かれた項目 + 今回聞かれた項目 + 自分から出してよい項目」の範囲を超えたら、1 回だけ作り直す。それでも超えたら、言い回しの例から規則で選んだ短い返事に差し替える。
- 返事に隠れた答えの値 (職種名・人数など) が文字として含まれ、その項目がまだ聞かれていなければ、同じく作り直す。
- 返事の長さ・日本語以外の混入 (`lang.rs`) を確かめ、だめなら作り直す。
- 毎ターンの温度は 0.7 前後 (返事に変化をつける)。採点は 0 (§5)。

## 5. 採点の作り方

### 5.1 全体の分け方

```text
やり取り (Vec<TalkTurn>)
   │
   ▼
[共有] ヒアリングの読み取り  ← LLM 1 回 + 規則
   │   項目ごとに: 聞いたか / 答えが出たか / 答えの中身 / 発言の番号
   │   質問の数、嫌がられた場面、良い例・悪い例
   ▼
[練習だけ] 照らし合わせ  ← 規則だけ
   │   記録欄 × 隠れた答え × 読み取り → 項目ごとの区分
   │   見立て × 型の熱さ
   ▼
採点と振り返り (PracticeResult)
```

- 共有の部分は「発言の並びを受け取って、4 項目の取れ方を返す」だけにする。練習か、本物の電話かを知らない。
- 架電助言アプリでは、本物の電話の文字起こし (Zoom の文字起こし、または音声から起こした文字) を同じ入口に渡す。隠れた答えが無いので、照らし合わせは使わず、読み取りの結果をそのまま出す。

### 5.2 4 項目の「取れた」と言える条件

| 項目 | 取れた (読み取りで答えが出た) と言える条件 | 練習での照らし合わせ |
|---|---|---|
| ① 時期と人数 | 3 か月以内に採用が必要な職種と、職種ごとの人数 (または「なし」) が、先方の発言に出た。それ以外の募集を聞き、職種と大まかな時期 (または「特にない」) が出た。人数は幅 (「2〜3 名」) でもよい | 記録の職種・人数が隠れた答えと合う。人数は幅の中に入れば合うとする |
| ② 課題と意欲 | 課題が一言で出て、早く解決したいか (早く / そこまでではない / 困っていない) が出た | 課題の中身は LLM の読み取りが隠れた答えと同じ趣旨か (§5.3)。意欲は選択肢で一致 |
| ③ 検討と予算 | 営業が「月額定額」と伝え、そのうえで検討できそうかの答えが出た。予算の有無 (ある / 無い / 答えなかった) が出た。金額は聞かない | 検討・予算は選択肢で一致。`no_then_yes` の型は、最後に出た答えと一致すれば合う |
| ④ 決める人と同席 | 最終的に決める人が出た (「私でいい」なら一声かける人まで)。当日の同席 (来る / 来ない / 未定) が出た | 選択肢で一致 |

項目ごとの区分 (練習):

| 区分 | 条件 |
|---|---|
| 取れた | 答えが会話に出て、記録が隠れた答えと合う |
| 記録違い | 答えが会話に出たが、記録が隠れた答えと違う |
| 聞けていないと記録 | 答えが会話に出ず、記録に「聞けていない」 |
| 空欄 | 答えが会話に出ず、記録も空 (終えるときに「聞けていない」として扱うが、区分は分けて数える) |
| 聞かずに記入 | 答えが会話に出ていないのに、記録に値がある |

- 「聞けていないと記録」は、台本の決まり (空欄にせず「聞けていない」と書く) を守ったものとして、「空欄」「聞かずに記入」より上に置く。
- 忙しい型では、台本の「今忙しい」と言われたときの手順 (①と④だけ聞き、残りは「聞けていない」と書く) どおりなら、②③の「聞けていないと記録」を減点しない (未決 §9-12)。

### 5.3 LLM で採点する部分と規則で採点する部分

| 中身 | 方法 | 理由 |
|---|---|---|
| 営業の発言ごとに、質問か / どの項目を聞いたか | LLM (読み取りの 1 回の中で発言に印を付ける) | 「〜ですか」で数えると、確認・相づち・挨拶を拾ってしまう |
| 先方の発言ごとに、どの項目のどの答えが出たか | LLM (同上) | 言い回しが多様 |
| 「月額定額」と伝えたか | 規則 (「月額」「定額」を含む営業の発言) + LLM の印 | 規則で取れる。LLM と食い違ったら規則を正にする |
| 嫌がられた場面 | LLM (先方の発言に印) + 規則 (`irritated` / `busy` の言い回しと同じ文、練習ではお客さん役の `mood`) | どちらかで見つかれば出す |
| 良い例・悪い例の要約 | LLM | 文章を書く部分。台本の言い回しと発言の番号を必ず付けさせる |
| 質問の数 | 規則 (LLM の印を数えるだけ) | 数えるのは規則 |
| 記録と隠れた答えの照らし合わせ | 規則 | 選択肢の一致・人数の幅で決まる |
| 課題の中身が同じ趣旨か | LLM (読み取りの 1 回に含める。隠れた答えの課題と、記録の課題を渡して「同じ / 違う」を返させる) | 文の一致では決められない。練習だけで使う |
| 見立ての答え合わせ | 規則 | §5.5 |

- 読み取りは temperature 0 で 1 回。日本語以外の混入はトークの振り返りと同じく検査して、最大 2 回やり直す。
- 良い例・悪い例の文章は `frontend/src/shared/phrases.ts` と同じ禁止語の検査を通す。

### 5.4 質問の数の目安

まとめの報告書の値をそのまま出す (判定した電話、成約 / 本数)。

| 質問の数 | 1〜4 問 | 5〜7 問 | 8〜10 問 | 11 問以上 |
|---|---|---|---|---|
| 成約率 | 8.1% (31 / 382) | 6.0% (47 / 783) | 3.9% (38 / 987) | 4.0% (21 / 528) |

- 「あなたの質問は 7 問 (5〜7 問の帯)」のように帯を示す。
- 注記: 先方の様子で質問の数が決まった分も含む値。報告書では、質問が多いほど嫌がられる向きは見えなかった。
- 台本の 4 項目を聞くと、最短で 6〜8 問になる (①で 2 問、②で 2 問、③で 2 問、④で 2〜3 問)。帯の値は目安として出し、点数にはしない (未決 §9-9)。

### 5.5 見立ての答え合わせ

- 営業は終えるときに、熱い / どちらとも言えない / 冷めている を選ぶ (段階の数は未決 §9-4)。
- 正解は型の熱さ。結果には次の 3 つを並べる。
  - 隠れた答えにあった熱い印の数 (台本の記録欄の熱い印: 合計が複数名、具体的で早く解決したい、前向き・内容と金額次第、予算ある、本人か社長・役員・決める人が来る)
  - そのうち会話で聞き出せた数
  - 見立ての当たり外れ
- 聞き出せた印だけを見れば当たる見立てと、隠れた答えまで見ないと当たらない見立ては、表示を分ける (例: 「聞き出せた答えからは『どちらとも言えない』が妥当。本当の型は熱い型。②の課題を聞けていれば分かった」)。

### 5.6 架電助言アプリと共有する部分

| 部品 | 置き場所 (案) | 練習 | 助言アプリ |
|---|---|---|---|
| 発言の形 `TalkTurn` | 既存 `src/crm/talk_review/types.rs` | 使う | 使う |
| 4 項目の定義 (聞き方・取れた条件・熱い印・冷めている印) | 新しい `src/hearing/hearing_checks.json` (トークの振り返りの `checks.json` と同じ作り) | 使う | 使う |
| 読み取り `analyze(turns) -> HearingAnalysis` | 新しい `src/hearing/analyze.rs`。LLM は既存の `Completer` を通す | 使う | 使う |
| 結果の表示部品 `HearingResultView` | `frontend/src/components/` か `frontend/src/screens/hearing/` | 使う | 使う |
| 隠れた答え・照らし合わせ・見立て | `src/call_practice/` | 使う | 使わない |

- 4 項目の定義は台本 v1 に合わせる。台本が v2 になったら、この JSON だけを直す。
- 将来、商談にも広げる (2026-10-22 ユーザー) ので、読み取りの中に電話に固有の前提 (電話番号・通話記録の形) を入れない。

## 6. API とデータの形

### 6.1 エンドポイント (案)

すべて `rbac::authorize` (Google ログイン・会社ドメイン・許可リスト・無効化の確認) を通す。POST は `X-Requested-With: fetch` を必須にする (既存の CSRF の確認)。

| メソッドとパス | 中身 | 応答 |
|---|---|---|
| `GET /api/call-practice/config` | 4 項目の定義、記録欄の選択肢、往復の上限、使えるか (鍵が無いなら `enabled: false`) | `PracticeConfig` |
| `POST /api/call-practice/sessions` | 練習を始める。型はサーバが伏せて選ぶ。`persona_id` の指定は §9-6 で決める | `PracticeStartResponse` (練習の番号・最初の一言) |
| `GET /api/call-practice/sessions/{id}` | 再読み込みのとき、やり取りと状態を取り直す (本人の練習だけ) | `PracticeSessionView` |
| `POST /api/call-practice/sessions/{id}/turns` | 自分の発言を送る | `PracticeTurnResponse` (お客さん役の返事・会話が閉じたか) |
| `POST /api/call-practice/sessions/{id}/finish` | 記録欄と見立てを送り、採点を受け取る | `PracticeResult` |
| `POST /api/hearing/analyze` (第 2 段以降、助言アプリ用) | 発言の並びを渡し、読み取りの結果を受け取る | `HearingAnalysis` |

- 練習の状態 (型・やり取り・聞かれた項目・質問の数) は、サーバのメモリに持つ (1 練習 = 数 KB。最後の操作から 2 時間で消す。全体で 500 件まで)。単一インスタンス前提 (`record_lock` などと同じ)。再起動で消えたら「練習が途切れました。もう一度始めてください」を出す。
- 発言の送信には、画面が付ける `client_turn_id` を持たせる。同じ番号の再送には、前に返した返事をそのまま返す (通信が切れて送り直したときに、LLM を 2 回呼ばず、会話が二重にならない)。
- 同じ練習への発言は 1 本ずつ (前の返事が返るまで次を受けない。受けたら 409 `turn_in_progress`)。
- エラー: LLM の鍵が無い 503 `practice_unavailable`、LLM の混雑・失敗 503 `llm_busy` (画面は「お客さん役が返事できませんでした。もう一度送ってください」。発言は入力欄に残す)、練習が無い 404 `session_not_found`、終えた練習への発言 409 `session_finished`。

### 6.2 型 (Rust、ts-rs で書き出す)

```rust

pub struct HearingItemAnalysis {
    pub item: String,            // "hiring" | "issue" | "cost" | "decider" (4 項目)

}

pub struct IrritationScene { pub turn: u32, pub customer_text: String, pub prev_rep_turn: Option<u32> }

pub struct HearingAnalysis {
    pub items: Vec<HearingItemAnalysis>,  // 4 項目の順
    pub question_count: u32,
    pub question_turns: Vec<u32>,
    pub monthly_fee_told: bool,
    pub irritations: Vec<IrritationScene>,
    pub good_examples: Vec<TurnExample>,
    pub bad_examples: Vec<TurnExample>,
}

// 練習 (src/call_practice/types.rs)
pub struct PracticeStartResponse { pub session_id: String, pub opening: TalkTurn, pub max_turns: u32 }

pub struct PracticeTurnRequest { pub client_turn_id: String, pub text: String, pub source: TurnSource } // TurnSource: Text | Voice (第 1 段は Text だけ)
pub struct PracticeTurnResponse { pub rep_turn: TalkTurn, pub customer_turn: TalkTurn, pub ended: bool }

pub struct HearingRecord {             // 記録欄 (台本の「記録する欄」)
    pub hiring_3m: RecordValue<Vec<JobCount>>,
    pub hiring_later: RecordValue<Vec<JobWhen>>,
    pub issue: RecordValue<IssueRecord>,
    pub consider: RecordValue<String>,  // positive | depends | difficult | cannot_decide
    pub budget: RecordValue<String>,    // yes | no | refused
    pub decider: RecordValue<String>,   // self | self_plus_one | boss | hq
    pub attend: RecordValue<String>,    // yes | no | undecided
    pub price_asked_by_customer: bool,
}
pub enum RecordValue<T> { Value(T), NotHeard, Empty } // 「聞けていない」と空欄を分ける

pub struct PracticeFinishRequest { pub record: HearingRecord, pub heat_guess: String }

pub struct PracticeItemResult {
    pub item: String,
    pub status: String,          // got | wrong_record | not_heard | empty | recorded_without_answer
    pub your_record: String,
    pub truth: String,
    pub turns: Vec<u32>,
}

pub struct PracticeResult {
    pub items: Vec<PracticeItemResult>,
    pub not_heard_left: u32,
    pub analysis: HearingAnalysis,
    pub question_band: String,   // "1-4" | "5-7" | "8-10" | "11+"
    pub heat: HeatResult,        // guess / truth / hot_marks_hidden / hot_marks_heard
    pub persona: PersonaReveal,  // 型の名前・参考の成約率の文・隠れた答えの一覧
    pub transcript: Vec<TalkTurn>,
}
```

- 型の名前・項目の名前は第 1 段の実装で詰める。決めるのは形 (発言の並び、4 項目の読み取り、練習だけの照らし合わせが分かれていること)。
- 新しく作る JSON API には、既存の決まりどおり contract test (具体値で確かめる) を付け、ts-rs の書き出しの差分が 0 であることを CI で確かめる。

- JSON を `include_str!` で埋め込む場合は、Dockerfile の COPY と `docker-context-check` (CLAUDE.md の絶対ルール、2026-10-11 の事故) に含まれることを確かめる。
- LLM は既存の `MiniMaxJudge` の作りを使い回す (`Completer` トレイト・`extract_json`・`lang.rs`)。お客さん役は温度と `max_tokens` を変えたいので、要求の本文を作る関数だけ別にする。

### 6.4 LLM の選び方

| 案 | 利点 | 欠点 |
|---|---|---|
| MiniMax-M3 (既存の鍵 `MINIMAX_API_KEY`) | 月額の枠で追加費用が無い。判定の部品 (`Completer`・`extract_json`・`lang.rs`) をそのまま使える。2026-10-19 のユーザー指示 (判定に Gemini を使わない) と合う | 本番のトークの振り返り・アポの自動判定と枠を分け合う (2026-10-26 に枠を使い切って本番が止まった)。返事を流しながら出せば最初の文字まで 0.7〜2.0 秒 (2026-10-29 計測)。日本語に別の言語が混ざる返事がある |
| MiniMax の軽いモデル (同じ鍵、モデル名だけ変える) | 今の契約で MiniMax-M3.1-Flash・MiniMax-M2.7-highspeed が使える。速さは M3 とほぼ同じ (2026-10-29 計測) | M3.1-Flash は混ざりと考え中の文の漏れが多かった。型を外れる率は未計測 |

決定 (2026-10-29 ユーザー): お客さん役と採点を分ける。お客さん役は即答できないと電話の練習にならない。お客さん役の LLM は、最初は MiniMax で検討する。

- お客さん役: まず MiniMax で作る。返事の目安は 1〜2 秒、最大 3 秒。MiniMax で目安に届かない、または型を外れる・言語が混ざる返事が多すぎるときだけ、Claude Haiku 5.5 を検討する (本番で使うには会社の契約の鍵が要る。今の鍵は 11/6 期限のプロモーションクレジットで、試作と計測だけに使う)。
- 第 0 段の最初の計測 (2026-10-29、型 1 つ・質問 3 回、返事を流しながら出す。最初の文字が出るまで / 全文):

  | モデル | 最初の文字 | 全文 | 言語が混ざった返事 |
  |---|---|---|---|
  | MiniMax-M3 | 0.7〜2.0 秒 | 0.8〜2.0 秒 | 12 回中 3 回 |
  | MiniMax-M3.1-Flash | 0.9〜1.6 秒 | 1.0〜1.8 秒 | 6 回中 3 回 (考え中の文の漏れ 1 回) |
  | MiniMax-M2.7-highspeed | 0.9〜1.7 秒 | 1.0〜1.8 秒 | 12 回中 2 回 |
  | Claude Haiku 5.5 (effort low) | 0.5〜0.7 秒 | 0.8〜0.9 秒 | 3 回中 0 回 |
  | Claude Sonnet 5.5 (考えを使わない設定・effort low) | 0.9〜1.5 秒 | 1.3〜2.1 秒 | 3 回中 0 回 |

  MiniMax の 3 つとも速さは目安に収まった。混ざった返事は、ほとんどが最初の短い返事 (「はい、どうぞ」の場面)。温度を 0.7 から 0.2 に下げても減らなかった。
- MiniMax で使うときの手当て: 返事を 1 文ずつためて、既存の `lang.rs` で日本語以外の混入を調べてから画面に出す。混ざっていたら、その文だけ作り直す (1 回まで、約 1 秒増える)。考え中の文 (`<think>`) は `extract_json` と同じやり方で外す。第 0 段で、作り直した後に混ざりが残る率と、返事全体の秒数を測る。
- お客さん役のモデルは M3 を最初の案にする (混ざる率が他と大差なく、採点と同じモデルで済む)。第 0 段で M2.7-highspeed と比べて決める。
- 第 0 段の試作 (2026-10-29、`scripts/call_practice/proto.py`、架空の型 2 つ × 聞き方 2 通り × 4 回 = 返事 96 回、温度 0.2):

  | 方式 | 最初の返事が崩れた | 画面に出た崩れ | 全文が 3 秒を超えた | 最長 |
  |---|---|---|---|---|
  | M2.7-highspeed、崩れたら 2 回まで作り直す | 96 回中 31 回 | 6 回 | 24 回 | 10.9 秒 |
  | M2.7-highspeed、崩れたら Claude Haiku に作らせる | 96 回中 28 回 | 0 回 | 18 回 | 22.7 秒 |

  崩れは英単語・中国語の混ざりと、考え中の文がそのまま出るもの (例: 「Need 1-2 sentences」)。作り直しでは消えきらない。Haiku に回すと崩れは出ないが、MiniMax の返事を待ってから回すので遅れる。MiniMax 自体の返事が 20 秒を超えることもあった。
  演じ方は MiniMax でも問題なかった: 聞かれていない設定を先に言う返事 2 回、設定と食い違う返事 0 回。予算を「予算ってありますか」と聞くと「特に取っていない」、月額定額を伝えてから聞くと「いくらか聞いてから」「その金額なら上と相談できる」と、聞き方で答えが分かれた。
- 同じ 96 回で Claude だけの場合 (2026-10-29):

  | モデル | 最初の文字 (中央 / 最大) | 全文 (中央 / 最大) | 崩れ | 3 秒超 | 聞かれていない設定を先に言った |
  |---|---|---|---|---|---|
  | Claude Haiku 5.5 (effort low) | 0.6 / 1.8 秒 | 0.8 / 2.0 秒 | 0 | 0 | 11 回 |
  | Claude Sonnet 5.5 (考えを使わない設定・effort low) | 0.9 / 4.3 秒 | 1.5 / 4.9 秒 | 0 | 2 回 | 3 回 |

  Haiku は速いが、職種を聞かれただけで困っていることまで話す・検討を聞かれて決める人まで話す返事が多く、練習する人が聞かなくても情報が取れてしまう。Sonnet は答えを小出しにする。
- 決定 (2026-10-29 ユーザー): Claude API の今の鍵をそのまま使ってよい。お客さん役は Claude Sonnet 5.5 (`thinking: between_tools`、effort low、返事を流しながら出す、人物設定と決まりの部分はプロンプトキャッシュ)。MiniMax は採点だけに使う。鍵は環境変数 `ANTHROPIC_API_KEY` (Render に設定するのはユーザー)。
- 採点: 練習を終えた後に 1 回だけ呼ぶので、遅くてよい。MiniMax-M3 を使う (月額の枠、既存の部品を使い回せる)。
- モデルは環境変数 `CALL_PRACTICE_MODEL` (お客さん役) と `CALL_PRACTICE_SCORE_MODEL` (採点) で変えられるようにする。

本番の判定を止めないための決まり (案):

- 練習で同時に呼ぶ LLM は 2 本まで (プロセス内のセマフォ)。超えたら待たせず 503 `llm_busy`。
- 1 人 1 日の練習は 20 回まで (未決 §9-10)。
- MiniMax が `Token Plan usage limit reached` を返したら、その日の練習を止め、画面に「今日はお客さん役が使えません」と出す (本番の判定より先に練習を止める)。

### 6.5 1 回の練習あたりの量と費用の見積もり

前提: 営業の発言 12 回 (4 項目で質問 8 問前後 + 前置き・相づち・締め)。数字は見積もり (未計測)。

| 呼び出し | 回数 | 入力 (1 回) | 出力 (1 回) | 合計 |
|---|---|---|---|---|
| お客さん役 | 12 回 (作り直しを 1 割見込んで 13 回) | 決まり 800 + 型 600 + 言い回しの例 30 件 900 + やり取り 平均 700 = 約 3,000 トークン | 返事の JSON 150 + 考え中の文 300〜1,500 = 約 500〜1,700 | 入力 約 4 万 / 出力 約 0.7〜2.2 万 |
| 採点 (読み取り) | 1 回 (やり直しを含め最大 3 回) | 4 項目の定義 1,500 + やり取り 1,500 + 隠れた答え・記録 500 = 約 3,500 | 結果の JSON 1,500 + 考え中の文 1,000〜3,000 | 入力 約 0.4〜1 万 / 出力 約 0.3〜1.4 万 |
| 1 回の練習の合計 | | | | 入力 約 4.5〜5 万、出力 約 1〜3.5 万 トークン |

- MiniMax: 追加の費用は出ない (月額の枠)。1 日 100 回の練習で約 600 万トークン。2026-10-26 に上限に届いたときの分析の使用量 (1 日 3〜5 億トークン) の 1〜2% にあたる。枠の残りは MiniMax の Plan Usage で確かめる。
- 従量課金の LLM を使う場合は、上の入力・出力のトークン数に、採るモデルのその時点の公式の価格を掛けて出す (この設計では価格の数字を置かない。着手時に公式の価格表で確かめる)。
- 返事の速さ: 目安は 3 秒以内。考え中の文を出すモデルでは超える見込みがあり、第 0 段で測る。超える場合は、軽いモデルにする、考え中の文を短くする指定を入れる、返事を流しながら出す (ストリーミング) の順で検討する。

## 9. 決めてほしいこと

### 9-1. 練習の記録を残すか、残すならどこか

| 案 | 利点 | 欠点 |
|---|---|---|
| A. 残さない (サーバのメモリに 2 時間だけ) | 新しい表も書き込みも無い。ADR も不要。第 1 段はこれで出せる | 終えた後に見返せない。管理者が練習の回数・取りこぼしを見られない。型の失敗例を集められない |
| B. 既存の監査 Turso に表 `call_practice_sessions` を足す | 本人の見返し・管理者の集計・型の改善に使える。既存の鍵・接続・1 年の掃除 (既存の purge) を使える。書き込みは終えたときの 1 回 (INSERT 1 行)。1 日数十〜100 行の見込み | 書き込みが増える (2026-01 の請求超過のため回数の見積もりが要る)。ADR-037 として理由を残す必要がある。監査 DB の障害時は保存できない (練習と採点はできる) |
| C. ブラウザの localStorage | サーバの保存先が増えない | 端末ごとに閉じ、消去で消える。管理者が見られない。トークの振り返りでも採らなかった方式 (ADR-034) |
| D. Google スプレッドシートに 1 行ずつ足す | 管理者が表で見られる | 書き込みの API の割り当て・鍵の管理が増える。やり取りの JSON が表に向かない |

決定 (2026-10-29 ユーザー): 残す。最終的に、練習ごとにスコアを付けて本人に返す。案 B (監査 Turso に表を足す) を採り、ADR-037 に理由を残す。書き込みは練習を終えたときの 1 回 (やり取り・記録欄・採点の結果を 1 行)。

### 9-2. お客さん役と採点の LLM

決定 (2026-10-29 ユーザー): お客さん役は即答できるモデルで、最初は MiniMax で検討する。採点は MiniMax-M3。詳しくは §6.4。お客さん役のモデルは第 0 段の計測で決める (M3 と M2.7-highspeed を比べる)。

### 9-3. 型と言い回しの例の置き場所

| 案 | 利点 | 欠点 |
|---|---|---|
| A. リポジトリのファイル (`src/call_practice/data/`、JSON / JSONL) | PR でレビューでき、検査を CI で必ず通せる。版が残る。新しい表が要らない | 足すたびに PR とデプロイが要る。件数が数万になるとリポジトリと起動時の読み込みが重くなる (数千件なら数 MB 以下の見込み) |
| B. 管理画面から上げて既存の監査 Turso に置く | デプロイ無しで足せる。ユーザーが直接入れられる | 表・取り込みの画面・検査の画面が要る。読み込みのキャッシュが要る。ADR が要る。誤ったデータが本番にすぐ出る |
| C. Google スプレッドシートを起動時・定期に読む | ユーザーが表で編集できる | 鍵と読み込みの失敗時の扱いが要る。表の列の崩れに弱い。版が残りにくい |

案: A。ユーザーがファイルを作り、Claude が検査を通して PR にする。件数や頻度で困ったら B を考える。

### 9-4. 熱さの段階と正解の決め方

| 案 | 利点 | 欠点 |
|---|---|---|
| 段階: 熱い / 冷めている の 2 つ | 当たり外れがはっきりする | 中くらいの型 (予算なし→変わる型など) で正解が決めにくい |
| 段階: 熱い / どちらとも言えない / 冷めている の 3 つ | 中くらいの型を扱える | 「どちらとも言えない」に逃げやすい |
| 正解: 隠れた答えの熱い印の数から規則で決める (例: 0〜1 冷めている、2 どちらとも、3 以上 熱い) | 型を足しても正解が自動で決まる。報告書の「良い答えは重なるほど成約率が上がる」と合う | しきい値を決める必要がある (報告書は 0 つ 3.3% → 4 つ 14.7% の連続した変化) |
| 正解: 型ごとに手で付ける | 作る人の意図どおり | 型が増えると付け方がぶれる |

案: 3 段階 + 規則で決める。しきい値は第 1 段で型を作りながら決める。

### 9-5. 誰が使えるか・ナビに出すか

| 案 | 利点 | 欠点 |
|---|---|---|
| CRM を開ける人全員 (トークの振り返りと同じ。役割は問わない) | 既存の関門をそのまま使える。BPO と新規営業が自分で練習できる | MiniMax の枠を使う人が増える |
| 役割で絞る (BPO・新規営業・管理者) | 対象を絞れる | 役割の付け方が未決のまま (ADR-017) |
| 最初は管理者だけ、ナビでは隠す (`hidden`) | 型と採点を確かめてから広げられる | 現場の声が遅れる |

案: 第 1 段は管理者だけ・ナビで隠す。型と採点を確かめてから、CRM を開ける人全員に広げる。

### 9-6. 型を選べるようにするか

| 案 | 利点 | 欠点 |
|---|---|---|
| おまかせだけ (いつも伏せる) | 本番に近い。見立ての練習になる | 苦手な型を狙って練習できない |
| 終えた後に「同じ型でもう一度」だけ許す | 見立ての練習を壊さずに復習できる | 2 回目は型が分かっている |
| 誰でも型を指定できる | 苦手を狙える | 見立ての採点が意味を持たない練習が増える |

案: おまかせ + 終えた後の「同じ型でもう一度」。管理者は型を指定できる (確認用)。

### 9-7. 練習中に台本を見せるか

| 案 | 利点 | 欠点 |
|---|---|---|
| 見せる・見せないを本人が選ぶ | 慣れるまでは見ながら、慣れたら見ないで練習できる | 採点を比べるとき、見たかどうかで分けて見る必要がある (結果に記録する) |
| いつも見せない | 本番に近い | 最初の数回が難しい |

案: 本人が選び、結果に「台本を見た」を残す。

### 9-8. 台本の細かい注意を採点に入れるか

台本には 4 項目の他に「金額は聞かない」「『差し支えなければ』は付けない」「前置きで 2〜3 分と伝える」がある。

| 案 | 利点 | 欠点 |
|---|---|---|
| 入れない (ユーザーが挙げた 5 つだけ) | 採点が単純で、直す点が絞れる | 金額を聞く癖が残っても気づけない |
| 「良い例・悪い例」の中でだけ触れる | 点にせず気づける | LLM 任せで、毎回は触れない |
| 規則で印を付ける | 毎回確かめられる | 項目が増え、何を直すかがぼやける |

案: 「金額を聞いた」だけ規則で印を付け、他は良い例・悪い例の中で触れる。

### 9-9. 質問の数の出し方

| 案 | 利点 | 欠点 |
|---|---|---|
| 数と、報告書の帯ごとの成約率を出す | 根拠が見える | 成約率を「質問を減らせば上がる」と読まれやすい (相関の値) |
| 数だけ出す | 誤読が無い | 少ないほうがよい理由が伝わらない |
| 数と「4 項目を聞く最短は 6〜8 問」の目安を出す | 目標が分かる | 目安の根拠は台本の作りで、成約率の根拠は無い |

案: 数 + 最短の目安。帯ごとの成約率は押すと開く。

### 9-10. 1 人 1 日の練習の上限

| 案 | 利点 | 欠点 |
|---|---|---|
| 上限なし | 練習したいだけできる | MiniMax の枠を使い切ると本番の判定が止まる |
| 1 人 1 日 20 回 | 枠を守れる (100 人が上限まで使っても約 1.2 億トークン/日の見込み) | 集中して練習したい日に足りない可能性 |
| 全体で 1 日 N 回 | 枠を直接守れる | 先に使った人が多く使う |

案: 1 人 1 日 20 回 + MiniMax の上限エラーで練習を先に止める。

### 9-11. 1 回の練習の長さの上限

案: 営業の発言 30 回まで、または 15 分まで。台本の目安は 2〜3 分で、上限は暴走を止めるためのもの。

### 9-12. 忙しい型の正解

台本は「今忙しい」と言われたら①と④だけ聞いて終え、残りを「聞けていない」と書くとしている。

| 案 | 利点 | 欠点 |
|---|---|---|
| 忙しい型では②③の「聞けていないと記録」を正解として扱う | 台本の手順の練習になる | 型ごとに採点の決まりが変わる |
| どの型でも同じ採点 | 単純 | 台本どおりに引いた人が損をする |

案: 忙しい型だけ②③を正解として扱い、結果に「台本の手順どおり」と出す。

## 10. 作る順番
