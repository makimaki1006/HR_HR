# 求人文面管理の初期表示改善

2026-10-06。Rust/Axum、既存 React 画面、HubSpot を正本とする構成を維持する。

## 調査

初期 MOC 応答は固定 SHA の Drive スナップショットを検証した後、対象求人すべての画像リンクを解決している。28 求人の場合、通常約112回の外部 GET を最大並列4で待つ。これはコードから確認した処理数であり、実測時間ではない。

## 実装計画

1. 固定 file ID/SHA の検証済みスナップショットだけをプロセス内で共有する。同時取得を一本化し、失敗を保存しない。ローカルファイルは従来どおり読み直す。永続ストアは増やさない。
2. 初期 MOC は本文・応募集計・画像ハッシュ等をそのまま返し、クラウド対象画像の埋め込み URL を認証付き同一オリジンの遅延解決 URL に置換する。画像の欠落や削除として扱わない。
3. 新しい画像解決ルートは、毎回ログイン・有効アカウント・対象求人を確認し、検証済みスナップショットの該当版・画像だけを選ぶ。既存の顧客関連確認、manifest 検証を通して、既存原本画像ルートへ no-store リダイレクトする。原本ルートでの SHA/MIME/サイズ・履歴チェーンの検証を維持する。
4. 保存されていない過去画像を補完しない。既存の比較ハッシュ、応募の帰属、観測日時、求人と応募の件数を変えない。
   遅延 URL に画像ハッシュを含め、保存データの切り替え後も古い画面に異なる画像を表示しない。一致しなければ取得エラーとする。
5. React の画像 URL パーサーに厳密な新ルートを追加する。遅延画像の取得中・失敗・再試行を区別し、本文と分析の利用を妨げない。

## 検証

認証失敗、未知の版/slot/求人、画像解決の失敗、同時取得、取得失敗後の再試行、初期応答で全件画像解決しないことを Rust で検証する。Frontend の型・lint・単体テストと、本文先行表示/画像失敗時の E2E を行う。実データ読み取りで応答時間と36求人・320応募・画像参照の保持を確認する。テスト用 OIDC セッションと本番 Google ログインは区別して報告する。

## 外部取得経路の実測

2026-10-06、設定済みサービスの資格情報をメモリ上だけで利用し、Drive/HubSpot の GET を Python で再現した（書き込み0）。固定 SHA のスナップショット取得・ハッシュ照合・JSON解析は1,734ms、28求人の画像リンク解決は16,426ms（HubSpot84 GET・Drive manifest28 GET）。全件解決を初期応答から外すと、初期の外部待ちは画像解決分が不要になる。これは外部API経路の再現測定であり、本番ログイン後のブラウザ表示時間やRustハンドラの実測ではない。

同じ36求人・320応募・45画像参照を保持し、応答の画像URLを置換したデータは615,386bytes（元スナップショット3,403,848bytes）。原本画像の転送時間はこの測定に含まない。
