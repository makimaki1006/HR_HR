| 例: 次回架電日時 | 実運用で確認 | 未確認 | timezone含め確認 | 再架電約束などを確認 | 未決定 | Taskとの関係を確認 | 未決定 | 未確認 |

## 3. 現在の入力欄をどう扱うか

| 現在の画面 | 計画上の扱い |
|---|---|
| 会社名・担当者名・役職・メール・電話・業種・市区町村・従業員数 | 実定義を照合し、BPOが閲覧・更新できる項目だけを許可リスト化。会社電話と担当者電話を区別 |
| 担当オーナー・リード状態 | 当初は参照。画面から自由に変更させない |
| 会話相手・関心度・次のアクション | 仮の項目。既存プロパティまたはCall本文への対応を決めるまで実保存しない |
| 採用職種・予定人数・開始時期・課題 | Deal `bpo_24` / `bpo_49` / `bpo_25`が実在し、Companyの採用予定人数も併存。Deal項目はDeal IDへ分離する。開始時期の保存先と併存項目の使い分けは未確定 |
| 架電結果 | 仮の6択を、実際の結果・選択肢内部値へ対応。アポや停止に必要な追加項目も確定 |
| メモ・次回日時 | 次回架電はDeal `bpo_13`（日付）/ `bpo_14`（時間選択）へ対応。メモはDealの補足・タスクメモとCall本文を区別する。Workflowと必須条件は確認し、NoteやTaskを重複作成しない |

初期実装は「全プロパティを自動で編集可能」にしない。画面は定義に応じた文字・数値・選択・日付の入力部品を使うが、表示と更新の許可はRustが決める。アーカイブ項目、未知の選択肢、取得失敗を空欄と混同しない。

入力ルールは、未確認・空文字・既存値のクリアを区別する。人数の未定と0人、日付だけと日時も区別する。デモの自由入力をそのまま実プロパティへ送信しない。

| B 認可とReact入口 | CRM専用OIDC・RBAC、ページ/APIの保護、既存ナビへの入口、既存シェルと接続 | OIDCで認証した許可ユーザーだけがCRMへ到達。共有・外部パスワードからCRM実データは取得不可 | role保持先・レコード範囲の決定 |
| C 実読み取り | Rust HubSpotアダプタ、型付きAPI、一覧/詳細/関連/活動、React fixture差し替え | Contact・Company・Dealと活動の値、関連、時刻を実画面と照合。ページング・取得失敗を扱える | A、B、最小scope・資格情報 |

Bの画面入口とAPIのモック検証はAと独立して進められる。実データの公開はBとCの条件を満たしてから行う。共通App Shellの完成を待つ場合も、React CRMをHTMXで作り直さない。

## 5. RustとReactの契約案

`GET /api/crm/metadata` のみ実装済みで、返すのは定義と計測値。以下は後続の実顧客・保存APIの提案であり、実装済みエンドポイントではない。

| API案 | 用途 |
|---|---|
| `GET /api/crm/context` | 操作者・許可操作・画面に出す項目定義・機能の有効状態 |
| `GET /api/crm/call-queue` | 権限と対象条件を適用した一覧。cursor、並び順、検索・絞り込み |
| `GET /api/crm/{objectType}/{id}` | 開いたレコードの許可プロパティ、関連ID、deep link |
| `GET /api/crm/{objectType}/{id}/activities` | 活動のページングと取得状態 |
| `POST /api/crm/operations` | operation IDを持つ、許可した更新・架電記録の要求 |
| `GET /api/crm/operations/{operationId}` | 当該操作者が確認できる保存・同期状態 |

一覧の初回は有限件数を読み、スクロールで次ページを追加する。検索条件が変わればcursorをリセットし、古い応答を適用しない。全件数が不明なら「読み込み済み件数」と「全件数」を混同しない。主たる会社・担当者の表示はまとめて取得し、詳細・履歴は展開時に取得して、各行で無制限にAPIを呼ばない。

Rust DTOからts-rsで型生成する。動的なプロパティ値は型生成だけで保証せず、RustとReactで定義に照らして検証する。`loading / empty / partial / error` を区別し、404・403・429・timeoutなどを「顧客なし」として表示しない。

書き込みは共有APIクライアントを拡張し、同一オリジンのセッション・CSRF方針を適用する。CRM APIは未認証をJSON 401、ログイン方式や操作権限の不足を403として扱う。ページのログイン誘導とAPIエラーを分ける。ブラウザーから渡されたrole・owner・object名・property名を権限根拠にしない。

静的ファイルは公開配信なので、bundleに資格情報や実顧客fixtureを含めない。実アプリ用エントリとローカルデモを明示的に分け、障害時に架空データへ黙って切り替えない。

## 6. 下書きと保存の境界

折り畳み・絞り込み・読み込み追加で下書きを失わない。キーは実際の所属object IDと内部プロパティ名にする。同じ会社の複数担当者が表示されても、会社の更新要求を重複生成しない。

保存時は「変更した項目」だけを送る。取得時点の値と保存直前の値の差を確認し、別操作者による変更を黙って上書きしない。HubSpot側の利用可能な競合制御を接続設計で確認し、原子的更新が保証されない場合の限界と再確認手順を定める。

Contact更新・Company更新・Call作成は単一の原子的トランザクションとは扱わない。operation内の各処理の成功を保持し、部分失敗時は未成功分だけを再実行する。CREATEは耐久な重複防止と、応答消失時の再照合を設計する。「検索してから作る」だけでは同時実行の二重作成を防げない。

保存状態は `下書き / 保存中 / HubSpot保存済み / 耐久保存済み・同期待ち / 保存失敗` を区別する。ブラウザーメモリだけで「一時保存済み」と表示しない。耐久キューが受け付けた後に次の架電へ進めるかは運用で決め、保存先がない状態では完了扱いにしない。未保存でのページ離脱にも対応する。

Durable Retryの保存先は未決定。既存audit Tursoへの表追加を候補に含め、既存基盤の利用可否・再起動耐性・保持期限・費用・運用を比較してADRに残す。新種の永続ストアを一般論で導入しない。業務履歴はHubSpot、システム障害はアプリログへ残す。

## 7. PRの分割案と検証

| PR単位 | 変更範囲 | 主な検証 |
|---|---|---|
| 1 定義と契約 | 対応表・権限表・必要な決定、CRM DTOとモック | 実定義との照合、未知値・null・クリアの区別 |
| 2 認可と入口 | CRMミドルウェア・APIエラー・シェル/ナビ接続 | 未ログイン、各ログイン方式、各role、他部署、URL直接アクセス |
| 3 読み取り | HubSpotアダプタ・一覧・詳細・活動・React実データ表示 | 欠落/部分失敗、429、cursor、応答逆転、実レコード一致 |
| 4 入力UI | 定義に応じたフォーム・変更差分・離脱確認 | 開閉/絞り込み/ページ追加後の保持、会社共有、必須条件、誤クリア |
| 5 耐久同期 | 決定済み保存先・operation・再送・CREATE冪等性 | 再起動、二重送信、応答消失、部分成功、キュー保存失敗 |
| 6 書き込み | 許可プロパティ更新・Call履歴・同期UI | 許可外property拒否、本人記録、Workflow、停止条件、更新競合 |
| 7 通話と限定公開 | Zoom常駐状態・イベント・対象ユーザー限定 | 通話状態、複数タブ/操作者の重複架電、純正ログとの二重記録、手動運用への切り戻し |

変更ごとに対象Rustテスト、frontend typecheck・lint・テスト・build、必要なfmt/clippyを行う。配信確認はViteプレビューだけでなく、ビルドしたRustアプリの `/app/crm` で実施する。PRごとのCRM E2Eを用意し、夜間の既存分析画面E2Eだけに依存しない。

実書き込みの検証は指定のテストレコードと限定ユーザーから始める。架電停止・番号違い・アポ・再架電約束の保存とWorkflowを確認し、読み取り版へ戻せる公開手順を用意する。書き込み・通話を止めても既存の業務履歴を削除しない。

## 8. 最初に決めること

1. 定義の参照元は確認済み。次に実運用のHubSpotリスト/ビューとWorkflowを確認する。
2. 架電対象の範囲・優先順位・禁止条件と、BPOが閲覧/更新できる項目。
3. roleの保持先。ADR-017の候補から選び、他部署・無効ユーザーも扱う。
4. 架電結果・採用ヒアリング項目の所属object、保存先、必須条件、既存Workflowとの関係。
5. HubSpotは既存Service Keyで定義GETが成功。HR_HRで必要な最小scope・管理方法と、Zoom純正連携との役割分担を確定する。
6. 耐久同期の保存先・成功判定・「次へ」の条件。

最初の着手範囲はプロパティ対応表と権限表の確定、その後の認可付き読み取り版。件数・既存Workflow・役割の決定が揃ってから日程と工数を見積もる。
