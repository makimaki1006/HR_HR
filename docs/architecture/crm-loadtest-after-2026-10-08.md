# CRM 架電画面 負荷試験 — AFTER (feat/hubspot-gateway, 2026-10-08)

`crm-loadtest-before-2026-10-08.md` (BEFORE、main) と同じ道具・同じシナリオで、HubSpot ゲートウェイを入れたブランチを測った結果。

- 対象: origin/feat/hubspot-gateway `67d3e8d1` (変更なし。接続先は同ブランチの `HUBSPOT_BASE_URL` で偽物へ向けた。`before-main-base-url.patch` は当てていない)。debug ビルド
- ゲートウェイの設定: 既定値 (Search 以外 8 回/秒・80 回/10 秒、Search 3 回/秒、画面の操作が待てる上限 5 秒、キュー用・レコード用の枠 各 8)
- HubSpot: 偽物 (`fake_hubspot.mjs`)。応答 400 ± 150 ms、一般 API 190 回/10 秒 かつ 19 回/秒、Search 5 回/秒 (別枠)、Deal 20,000 件 — BEFORE と同じ
- 利用者・シナリオ: BEFORE と同じ (100 人うち管理者 10 人、0〜10 秒に一斉起動 → 30〜90 秒ごとの操作、5 分、seed 42)
- 実行: BEFORE と同じく外部バッチなし 2 回 (run1, run2) と外部バッチ 5 回/秒 1 回 (bg5)。追加で、一般枠を 100 回/10 秒にした 1 回 (limit100) と、Search を 1 回/秒に戻した 1 回 (search1、`HUBSPOT_APP_SEARCH_PER_SEC=1`)

## ドライバの変更 (`scripts/loadtest/run.mjs`、最小限)

ゲートウェイは混雑時に HubSpot を呼ばずに **503 `hubspot_busy`** を返し、画面は「HubSpot が混み合っています。少し待ってから再試行してください」と出す。これに合わせて:

- 503 `hubspot_busy` を受けたら、利用者が 3〜8 秒待って「再試行」を押すとみなして同じ操作をやり直す (1 操作あたり最大 5 回)。やり直しも 1 要求として記録し、最後の 1 回に「最初の要求からの経過時間」を持たせる。
  これで「要求ごと」(503 を失敗として数える) と「操作ごと」(やり直し込みで最終的に出たか・何秒かかったか) の両方を出せる。
- キュー 1 ページ目の再試行は画面と同じく `fresh=1` (サーバの 30 秒キャッシュを使わない) を付ける。キューが出なかった人の定常の「読み直し」も同じ (BEFORE のドライバは `fresh` を付けていなかったが、BEFORE のアプリにはキャッシュが無いので差は無い)。
- `--app-env K=V,...`: アプリに渡す環境変数 (search1 の `HUBSPOT_APP_SEARCH_PER_SEC=1` 用。ドライバは親の `HUBSPOT_*` をアプリに渡さないため)。
- レポートに 503 `hubspot_busy` の件数・やり直し後の操作の成功率を追加。BEFORE の記録 (503 が無い) の読み方は変わらない。

- **limit100**: 偽 HubSpot の一般枠を 100/10 秒にしても結果は既定とほぼ同じで、429 も 0。ゲートウェイが自分で Search 以外を 80/10 秒に抑えているため (偽物の 10 秒の最大 110 には別枠の Search が約 25〜30 回含まれる)。
  ただし偽物は Search を一般枠に数えていない。本物の HubSpot が Search も 100/10 秒に数えるなら、この負荷で枠を超える (未検証。`--search-counts-general true` で測れる)。外部バッチとの同時実行 (limit100 + bg5) は測っていない: 80 + 外部バッチ 50 = 130/10 秒で、100 なら 429 が出る計算になる。
- **search1**: 一斉起動の「20 秒以内」は 36〜39 → 17 に半減し、503 は 1.4 倍、定常のキューも 3 割強が 503 になった。それでも BEFORE (10 人、504 が 99〜101) よりは良い。
  BEFORE からの改善のうち、一斉起動については半分程度が Search 3 回/秒による。残り (定常のキューの成功率、429 が 0、全員にキューが出ること) は、キューのキャッシュ・枠の分離・待ちの上限 (20 秒待たせずに 5 秒で断る) によるもので、Search 1 回/秒でも残る。案件の詳細は Search を使わないので、search1 でもほぼ同じ。

## 残っているボトルネック

1. **案件の詳細は、ゲートウェイの一般枠 (8 回/秒・80 回/10 秒) で頭打ちになる。**
   案件の詳細 1 回で HubSpot を約 8 回呼ぶ (本体+関連・関連 2 種・contact→calls・Engagement 4 種・会社・担当者) ので、アプリ全体で約 1 件/秒しか開けない。
   このシナリオの定常の需要は約 1.5 件/秒 (開き直し・通話後の `fresh=1` を含む)。定常の HubSpot 呼び出しは 10 秒ごとに 80〜87 で張り付いていた (run1 の推移)。
   その結果、レコード用の枠 (8) の待ちが 5 秒を超えて 503 になり、**要求の 32〜40% が 503**。やり直し込みならほぼ全部開けるが、p95 は 40〜51 秒で BEFORE (19〜20 秒) より長い。
   p50 は 14〜17 秒 → 10.5〜12 秒と縮んだが、利用者は 3 回に 1 回くらい「混み合っています」を見ることになる。
   打ち手の候補: 詳細の呼び出し数を減らす (メール・ミーティング等はタブを開いたときに読む)、本物の鍵の枠が分かったら上限を上げる (偽物の枠 190/10 秒に対して 80 は控えめ)、詳細のキャッシュを伸ばす。
2. **一斉起動のキューは、20 秒以内に出るのが 100 人中 36〜39 人。** 一斉起動の 2 分ほどは、Search (3/秒) と一般枠 (1 件目の案件の詳細と取り合う) の両方が詰まり、キュー 1 ページ目の要求の 7 割強が 503。
   最後の人にキューが出るのは 155〜172 秒後。503 のあと 3〜8 秒待って押し直す、という仮定の待ちもこの時間に含まれる。
   一斉起動の間の Search は平均 1.8 回/秒 (run1) で上限 3 に届いていない — キュー用の枠 (8) の待ちで 5 秒を超えて断られる分が多い (ログの「crm read waited too long for a slot」)。
3. **503 の一部は 200 の中に隠れている。** 案件の詳細・キューは、一部の取得 (notes / emails / meetings / calls / 会社 等) が `hubspot_busy` で欠けても 200 で返す。アプリのログの「partial failure」は 90 / 63 / 48 / 35 件 (run1 / run2 / bg5 / limit100)。ドライバはこれを成功として数えている。search1 ではキューの総件数の取得の失敗・打ち切りが 78 件。
4. 小さいもの: `owners?email=` (本人の owner の解決) は 113〜120 回 → 75 回に減ったが、まだ利用者ごとに呼んでいる。

## この計測の限界 (正直に)

- 各条件 1〜3 回。BEFORE と同じく回ごとの揺れがある (AFTER の 3 回でも「20 秒以内」は 36〜39、503 は 432〜527)。追加の 2 回 (limit100、search1) は 1 回ずつ。
- **503 のあとの利用者の行動は仮定** (3〜8 秒待って押し直す、最大 5 回)。押し直さない人が多ければ要求は減るが、その人は何もできない。「操作ごと」の p95 はこの仮定に強く依存する。
- **BEFORE と AFTER でドライバが少し違う**: 503 のやり直しと、キューの読み直しに `fresh=1` を付けることを足した。BEFORE には 503 もキャッシュも無いので BEFORE の数字には影響しない。ただし「要求ごとの成功率」は、AFTER では 5 秒で返る 503 を含み、BEFORE では 20 秒の 504 を含むので、同じ物差しではない。利用者に近いのは「操作ごと」と「20 秒以内にキューが出た人」。
- 偽 HubSpot は Search を一般枠に数えない。本物がどう数えるか、上限の数え方 (到着時に判定、拒否は数えない) が本物と同じかは未検証。1 秒枠 19 は仮定。
- 一部が欠けた 200 (上の 3.) を成功として数えている。
- debug ビルド。計測中のマシンの負荷平均は 3〜4 (他の作業あり)。アプリ自体の処理時間は HubSpot の待ちより十分小さいと見ているが、release とは違う。
- 書き込み (架電結果の保存) と画面の静的ファイルは含めていない (BEFORE と同じ)。
- 本物の HubSpot は呼んでいない。

## 結論

- 当初の問題 (Search の直列化で全員のキューが 20 秒で 504、HubSpot の枠が余っているのに利用者が待つ) は解消した。定常のキューはほぼ全部 4〜6 秒で出て、429 も 0 になり、5 分のうちに全員がキューを見られた。
- 代わりに、ゲートウェイの一般枠 (80/10 秒) が新しい天井になった。案件の詳細は 3 回に 1 回 503 になり、やり直し込みの p95 は 40〜51 秒と BEFORE より長い。100 人が 30〜90 秒ごとに案件を開く負荷は、今の「詳細 1 件 = HubSpot 約 8 回」では捌ききれない。
- 一斉起動の改善 (20 秒以内 10 → 36〜39 人) の約半分は Search を 3 回/秒に上げたことによる。1 回/秒に据え置くなら 17 人。定常のキューの改善と 429 が 0 になることは、Search の設定によらず得られる。
