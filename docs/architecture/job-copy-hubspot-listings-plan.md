# 求人文面管理：HubSpot 求人一覧・版の読み取り

2026-10-10。最初の PR は読み取りのみ。既存の固定一覧、Rust / Axum、React 画面、Google OIDC を維持する (閲覧は会社ドメインの Google ログイン全員。2026-10-21 以降 JOB_COPY_ALLOWED_EMAILS は読まない)。CRM のファイル・永続ストアは変更しない。

## API と呼び出し予算

- `GET /api/job-copy/listings?prefecture=大分県&title=ドライバー&media=hrh&offset=0&sort=title`
  - `media`: `hrh` / `airwork`。`title`: Indeed の分類名 / `unknown`。空なら条件なし。
  - 起動時に通常一覧を100件ずつ全ページ読み、サーバーのメモリに索引を作る。関所の Background 優先度を使い、ページ間に1秒空ける。索引から媒体・地域・分類を照合し、求人名順（`title`）または媒体順（`media`）で並べ、最大50件返す。APIではID順（`id`）も指定できる。続きは `next_offset`、条件に合う合計は `total`、索引作成日時は `index_built_at`。
  - 媒体、媒体求人ID、アカウントID、求人名、地域、分類、公開状況、最終CSV検出日、応募件数を返す。未取得・分類不明は `null`。
  - HRハッカーとAirWorkを統合しない。AirWorkの識別情報はアカウントと求人IDを両方返す。版APIのパスではHubSpotのレコードIDを使う。
  - 応募件数は0-420→0-421の関連付けを一括で1回取得。同じ関連IDを除いて数える。取得失敗・返却省略・追加ページありは `null`。応募者のプロパティは取得しない。
- `GET /api/job-copy/listings/{HubSpotレコードID}/versions`
  - 求人1件を本文・画像・仕事内容の `propertiesWithHistory` とともに1回取得。
  - HRハッカーは本文と画像を日時順に合成、AirWorkは仕事内容のみ。保存済み画像の参照がある場合は、別の観測画像として日時付きで返す（本文の過去版の画像にしない）。同じ日時の本文・画像を同時に適用し、本文・画像とも変わらない連続記録はまとめる。
  - 各版は `written_at`, `body`, `image_urls`。画像履歴未取得は `null`、画像なしは空配列。
  - 履歴に本文が無く現在の本文がある場合は、`current` に現在値と今回の取得日時を別に返す。保存済み観測画像は `current_images`。元の履歴件数は `history_counts`。いずれかの項目が20件以上のときだけ `history_may_be_incomplete` が true。各項目が20件未満なら返った履歴をすべてとして扱う。

Searchは0回。索引作成は40,282件なら約403回。一覧要求は表示ページの応募関連の batch read が1回（準備中・空ページは0回）、版は1回。429・5xxは既存規則で各読み取り最大1回再試行する。Backgroundでは長い Retry-After も待ち、関所の共通待機を守る。すべて既存HubSpot関所経由。画面APIの認可は設定・DB・外部読み取りより先に行う。

索引は6時間ごとに再作成する。初回完了前は `status: preparing` と `total: null` を返し、0件とは扱わない。更新中は前回の索引を利用し、全件取得に成功したときだけ置き換える。失敗時は古い索引・日時を残し、`refresh_failed` を返す。失敗後は10分後に再試行する。本文は職種行の抽出時だけ利用し、索引には保存しない。応募件数も索引には保存しない。

メモリ見積もり：4万件で構造体・文字列枠が約9MiB、ID・名称・地域等の文字列と割当管理を含め索引1世代約20〜35MiB（項目の実長に依存）。更新中は旧・新の2世代で約40〜70MiBに、ページ100件分の一時本文・重複確認用ID集合が加わる。本文全件を保持せず、永続ストアは追加しない。

## 画面

「HubSpot の求人」で条件を選び、求人を取得して版を開く。取得した版を既存 `JobCopyRecord` / `CopyVersion` に変換し、タイムライン・本文・変更差分で表示する。「固定一覧を表示」で元の固定ファイル一覧へ戻る（操作デモで開いた場合は元のデモ一覧）。履歴の保存日時は掲載開始日時にしない。画像URLは当時の画像バイトを保存したことを意味しない。版ごとの応募を推定しない。

## 制限・次の検討

- 一覧は索引の作成時点の内容。更新中のHubSpot変更は次の更新で反映される。初回は約403回とページ間待機が必要なので数分以上の準備時間がある。
- 分類名の完全一致、または文字を含む照合だけを採用。正規化は既存 `matchMarketTitle` と同様。複数候補は長い分類を優先する。同じ長さの場合は文字コード順にそろえ、既存のフロント側の同長候補の並べ方も同じ順にする（ブラウザのロケール依存を外す）。
- AirWorkの公開状況は `baitai_genjoukyou_airwork`（媒体原ステータス_AirWORK）を利用する。2026-10-10に関所経由のプロパティ定義GETを1回実施し、文字列項目の存在を確認した。空値は `null`（画面は「未取得」）。履歴が20件以上ある項目では、返った期間より前の本文・画像は確認できない。
- 今回は一覧の応募件数だけ。応募理由・応募日と版の対応は既存APIの別経路であり、この一覧からの接続は後続PR。

## 未連携のMTG（2026-11-05）

コンサル向けメニュー「未連携のMTG」（`/app/job-copy?view=unlinked`）。夜の更新が取引に結び付けられなかった録画を、コンサル本人が取引を選んで結び付ける。

- 一覧の元: シート「CS_MTG結び付け待ち」（既存の `pending_recordings`）。列は 録画UUID / 録画 / 開催日 / 件名 / ホスト氏名 / 候補の取引 / 理由。「理由」は日本語以外が混ざることがあるので出さない。
- API: `GET /api/job-copy/unlinked-mtg`（`owner` / `owner_field` は他の画面と同じ。`fresh=1` で選択済みの印を読み直す）。認可は案件管理の既存 API と同じ。
  - 担当者を選ぶとホスト氏名と担当者名を NFKC・空白除去で突き合わせて絞る。「全員」は全件。
  - 各行に、候補の取引（id と名前に分解）、ホストに合う担当者の終了していない取引（最大 300 件、候補が無い・合わない行のための選択肢）、選択済みの印を付ける。
- 選択済みの印: `mtg_manual_links` を持つ取引を HubSpot Search（HAS_PROPERTY、200 件ずつ最大 10 ページ）で読み、録画UUID ごとに「選んだ取引・日時・メール」にする。60 秒キャッシュ、保存・取り消しのあとは画面が `fresh=1` で読み直す。読めなくても一覧は出す（印だけ付かない）。
- 書き込み: 画面が既存の `PATCH /api/crm/deals/{id}`（競合・反映待ちは CS提案内容メモと同じ `useCrmWrite`）で、取引の `mtg_manual_links` に 1 行 `録画UUID<TAB>日時(JST, YYYY-MM-DD HH:MM)<TAB>メール` を足す。同じ録画UUID がすでにあれば足さない。取り消しはその行だけを消す。書く前に取引の今の値を読み直して base にする。書けない設定のときは見るだけにして理由を 1 行出す。夜の更新（別リポ）がこの項目を読んで結び付ける。
- HubSpot の呼び出し（見積もり）: 一覧の表示 1 回につき Search が 1 回（キャッシュ中は 0 回、通常 1 ページ）。結び付け・取り消し 1 回につき、取引の読み取り 1 回 + PATCH 1 回（`useCrmWrite` の編集項目の確認は一覧を開いたとき 1 回）。担当者・取引は既存の 5 分の読み込みを使い、追加の読み取りは無い。
- 現行を保つ利点 / 変える利点: 保つ利点は夜の更新だけで済み画面が要らないこと。変える利点は、自動で決められなかった録画をコンサルが当日中に選べて、次の夜の更新で反映されること。戻すコストは画面・API を外すだけ（HubSpot の項目の値は残り、夜の更新は読み続けても害は無い）。
