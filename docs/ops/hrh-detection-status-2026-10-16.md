# HRハッカー(HRH) 求人の差異(変更)検知 確認結果

確認日: 2026-10-16(日本時間の未明)。読み取りのみ。コード変更・HubSpotへの書き込みはしていない。

## 結論

**実装済みで、1日3回動いている。ただし「本文・画像・状態・新規・消失」までで、通知は無く、毎回のCSV欠けに弱い。**

- 実行: 直近の定期実行(Job Daily の hr)は 10/12〜10/15 の8回すべて成功。更新は 1,615〜32,885 件を書き込み、失敗(NG)は 0。
- 検知結果の実害: 本文 `hrh_kyuujinhyou_honbun` は、無作為に取った400件のうち7件(1.75%)で値が変わった記録がある。変わった日は 10/13(2件)・10/14(4件)・10/9(1件)。画像は4件。つまり「変わったら履歴に残る」は実データで動いている。
- 弱点1: 12時(JST)枠のCSVが3日連続で欠けている(1,618件→30件→1,615件。通常は約32,900件)。
- 弱点2: 差が出ても誰にも通知されない。履歴を見に行かないと分からない。

## 1. コード: 何を取得し、何を前回と比べ、どこへ書くか

流れ(`.github/workflows/job_daily.yml` の phase=hr):

1. `hr_watcher.py --actual --skip-aw` が HRH の「求人一覧CSV」(全件、約32,900行)を取得(`fetchers/hr_csv_fetcher.py`)。
2. 前回の控え(`data/job_application_sync/hr_snapshots/*.json.gz`。求人ごとに 状態・店舗ID・求人名・本文画像の指紋)と比べて `new`(新規)/`removed`(CSVから消えた)/`changed`(状態・求人名・本文画像の指紋が変わった)を出す(`detect_diff`)。控えは Actions のキャッシュで次回へ持ち越す。
3. 差があれば `hrhacker_import.py` が HubSpot の求人(0-420)へ書く。**差の有無にかかわらず毎回、CSVの全行について更新対象を組み立てる**(10/14の夜は 32,885 件更新)。

| 検知する対象 | 取得元(CSVの列) | 書き込み先(HubSpot 求人の項目) | 備考 |
|---|---|---|---|
| 本文 | 仕事内容・メリット・応募資格・給与・勤務時間・自由項目など約60列を1つに連結 | `hrh_kyuujinhyou_honbun` | 今の値と**違うときだけ**書く。HubSpotの項目履歴がそのまま版の履歴になる |
| 画像 | 画像1〜3 | `hrh_kyuujinhyou_gazou` | 同上 |
| 給与 | 本文に含まれる(給与形態・基本給与・条件付き給与・固定残業代など) | 同上(給与だけの項目は無い) | 本文が変わったことは分かるが、給与だけが変わったかは本文の差分を見ないと分からない |
| 掲載状態 | 「公開」列 | `baitai_genjoukyou_hrhakkaa`(媒体で見た状態)、`kyuujin_status`(公開前/公開中/公開終了) | 状態が変わると `changed` |
| 新規 | CSVに初めて載った求人ID | 求人を新規作成。取込理由・管理区分・初回の最終検出日を入れる | 10/14 夜 18件を作成 |
| 消失 | CSVに載らなくなった求人 | `end_vanished_listings.py`:「公開中」で最終検出日が2日以上前の求人を `kyuujin_status=公開終了` / `baitai_genjoukyou_hrhakkaa=非公開` にする | 店舗ごとに公開中の20%を超える終了予定なら見送る(欠けたCSVの誤爆防止) |
| 毎回の印 | 全行 | `saishuu_csv_kenshutsu_bi`(最終CSV検出日)、`konkai_csv_kenshutsu_flag`、`douki_moto_filename`、`doukisaishuujikoku` | 履歴上は毎回更新される |
| 勤務地 | 店舗一覧CSV | `todoufuken`、`shikuchouson`(空のときだけ補完) | |

別スクリプト: `state_sync.py` はクラウド保管(GCS)の状態同期用で、差異の検知はしていない。`hr_offers_csv.py` は取引側の店舗IDや会社名を引くためにCSVを選ぶ補助で、差異検知とは無関係。

**対象外**: 休日・休暇・福利厚生・待遇の列は本文の連結対象に入っていない(コードに該当列が無い)。これらが変わっても検知しない。

## 3. HubSpot の実データ(読み取り)

HRH求人(`id_hrhakkaa` あり)全 33,035 件。公開中 1,660、公開終了 31,375(消失ルールで終了にした印が付くもの 61 件)。

| 確認 | 結果 |

| 本文・画像の項目に値がある | 32,906 件ずつ |
| 最終CSV検出日が 10/14 以降 | 32,903 件。10/13 以降は 32,906 件 |
| 公開中なのに 10/14 以降の検出が無い | 3 件のみ |
| ID範囲を8等分して取った400件の本文履歴 | 版が2つ以上ある(=値が変わった)のは **7件**。変わった日: 10/9 が1件、10/13 が2件、10/14 が4件 |
| 同400件の画像履歴 | 版が2つ以上は **4件**(10/9 に3件、10/13 に1件) |
| 同400件の `kyuujin_status` | 258件で値が変わっている(公開前→公開中→終了などの遷移) |

注: 最新更新順で先頭100件を取ると全件が「今日更新された最終検出日」だけで、本文の変化は見えない。そのため本文の統計は上の「ID範囲を等分した400件」で出した。400件は全体(約33,000件)の約1.2%の標本で、変更率の推定にとどまる。10/15 分の本文変更は標本に出ていない(その日の07:50の実行はCSVが欠けて1,615件だけの更新のため、標本に当たらなかった可能性が高い)。

## 4. 足りない点・リスク

1. **12時(JST)枠のCSV欠け**: 10/13 は 1,618件、10/14 は 30件、10/15 は 1,615件(通常は約32,900件)。公開中の求人数(1,660)とほぼ同じ件数なので、公開中だけに絞られた可能性がある。原因はまだ特定していない。
   - 影響: その日の「変更」は1,600件ぶんしか見えない。控えが縮み、次回は3万件が「新規」「消失」に見える(10/13 17:09 に 31,183 件、10/14 15:40 に 32,855 件)。
   - 守られている点: 「消失 → 公開終了」は店舗ごとに公開中の20%上限で止まる(10/15 は予定1件を見送り)。ただし `csv_is_complete` は行数が少ないことを判定せず、「--limit なし・1行以上・IDの欠けなし」だけを見ている。
2. **変わった日の精度**: 履歴の日時は「取込がHubSpotへ書いた時刻」。実行は1日3回(JST 1時/12時/20時の予定)だが、GitHubの定期実行が数時間遅れる日がある(10/12の1時枠は6.7時間遅れ、10/15の20時枠は約4時間遅れ)。HRH側で実際に変更された時刻は分からず、精度は「前回の取込から今回の取込までの幅」。
3. **通知が無い**: `hr_watcher.py` と `hrhacker_import.py` に Slack 通知は無い。`health_check.py` にも、求人の鮮度(最終検出日が古い、CSV件数が急減した)を見る検査は無い(検査は紐付け・一次対応など)。差が出ても、CSVが欠けても、誰にも届かない。
4. **本文の対象外の項目**: 休日・福利厚生・待遇の列を連結していないので検知できない。
5. **給与だけの変化は分けて持たない**: 本文に連結されている。給与のみの履歴・集計が要るなら、別項目に切り出す必要がある。
6. **控えの置き場**: スナップショットは Actions のキャッシュ。キャッシュが消えると全件が新規扱いになる。初回の大量書き込みを防ぐ中断(`MASS_WRITE_THRESHOLD`=500)が働く設計だが、実際に10/13と10/14に3万件の「新規」が出ても書き込みは続いていた(控えが空ではなく、縮んだだけのため上の中断条件に当たらない)。
7. **履歴は10/9から**: 10/9 より前の本文・画像の版は無い。

## 5. 判定

「実装済みで毎日動いている」。ただし、(a) 12時枠のCSV欠けで3日に1回は変更を取りこぼしうる、(b) 通知が無いので異常に気づけない、(c) 休日・福利厚生は対象外、の3点が残る。
