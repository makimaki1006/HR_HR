## 1. 要約

競合調査レポートを直接PDFとしてダウンロードする機能について、意図的に壊した入力・応答・レイアウトを与えて検証した。

実際に再現した不備は次の2点。

1. 応答のContent-TypeがPDFなら、空ファイル・HTML・途中で切れたPDFもダウンロード成功として扱っていた。
2. PDF生成前の検査がページ数と高さだけだったため、左側にはみ出した文字がPDFから欠落しても検査を通過していた。

両方に検査を追加した。修正後の15ケースはWindows・Linuxとも通過した。Nodeのテスト集計は、親テスト2件を含めて各環境17件成功・0件失敗。

ただし、4ページに収める縮小によってExcel再現ページの一部が約4.84ptになることも確認した。今回の変更は、読みやすさの改善までは含んでいない。

## 2. 利用者が求めている出力と既存の実装

利用者の目的は、Excelで行っていた競合調査を独立した機能として再現し、補足情報をタブで切り替えて確認すること。

| 項目 | 既存の実装 |
| --- | --- |
| 入口 | `/competitor`でCSVと調査条件を指定 |
| Excel再現 | 給与・人気求人・訴求語などの表とグラフ |
| Google | 既存のGoogle広告APIロジックを利用した検索需要・関連キーワード |
| Indeed | 採用市場のスクレイピング済みデータを職種・地域別に表示 |

| PDF | Excel・Google・Indeed・人口の順でA3横4ページに固定 |
| 操作 | 「PDFをダウンロード」で画面遷移せず取得。「画面で確認」でHTMLを表示 |

この表は機能の構成を説明するもので、各データの数値の正しさを今回改めて保証するものではない。

## 3. 出力処理の流れ

1. ブラウザがCSV・調査条件・`output_format=pdf`を送信する。
2. Rust / Axum側で認証を通し、競合調査と補足情報のHTMLを生成する。
3. リクエストごとの一時ディレクトリにPDF用HTMLを作成する。
4. Node / PlaywrightがChromiumでHTMLを開き、4ページに収める。
5. ページ構成と各内容の位置を検査し、検査を通過した場合にPDFを生成する。
6. Rust側がPDFを添付ファイルとして返す。
7. ブラウザが応答形式とPDFの先頭・末尾を検査し、ダウンロードを開始する。

今回の変更点は手順5と7、およびその回帰テスト。

## 4. 反例と修正内容

### 4.1 不完全なファイルを成功扱いする問題

修正前はHTTP成功と`application/pdf`のContent-Typeを確認するだけだった。テストでPDFとして空ファイル・HTML・途中で切れたPDFを返したところ、3ケースともダウンロードが発生し、成功表示になった。

修正後はBlobの先頭5文字が`%PDF-`であること、末尾32バイトに`%%EOF`があることを確認する。不一致の場合はエラー表示にし、ダウンロード用URLを作らない。

これは基本的な形式・終端の検査であり、PDF全体をパーサーで解析する検査ではない。先頭と末尾だけを偽装した壊れたPDFまで排除できるとは言えない。

### 4.2 はみ出した文字の欠落を見逃す問題

修正前の検査は、`.pdf-content`が4つ存在することと、その高さが1045px以下であることだけだった。最初のページに`left:-500px`の文字を追加すると、この検査を通過した一方、生成したPDFから検証用文字が欠落した。

修正後は次を確認する。

- パネルが4つあり、IDと順序がExcel・Google・Indeed・人口に一致する。
- 各パネルにPDFページの枠があり、幅・高さが正の値である。
- パネルの矩形がページ枠内に収まる。
- テキストの描画矩形が上下左右のページ枠内に収まる。
- SVG・画像の矩形がページ枠内に収まる。
- 境界比較にはブラウザの端数計算を考慮した1pxの許容差を設ける。

検査に失敗すると`PDF page fitting failed`として処理を止める。今回の変更は、はみ出した内容を自動的に再配置する処理ではない。

## 7. 残る課題と検証の限界

### 印刷時の読みやすさ

実レポートPDFの最小フォントサイズは、1ページ目が約4.84pt、2～4ページ目が約8.98ptだった。4ページに収めるための縮小には下限がなく、データ量によって文字がさらに小さくなる可能性がある。

読みやすさを改善する場合は、最低文字サイズと、4ページ固定をどこまで維持するかを決める必要がある。候補は、注記・表の配置調整、1ページあたりの表示量の調整、ページ分割。今回の差分には含めていない。

### 位置検査で保証できないこと

ページ枠内の矩形検査だけでは、SVG内部のクリッピング、他の要素による重なり、個別要素の非表示による欠落をすべて検出できない。修正後の検査も、PDF内の全テキストを元データと照合する処理ではない。

### 数値・外部連携

今回の逆証明はPDFの出力・ダウンロード処理が対象。給与の集計式、CSVの重複排除、Google広告APIの数値、Indeedの指標、人口・最低賃金の原典との一致は、今回改めて検証していない。

### テストの適用範囲

今回の差分に対してRust全テスト、既存のアプリE2E全体、GitHub CIはまだ実行していない。前回リリース時の成功結果を、今回の差分の成功結果として扱わない。また、追加したNodeテストをCIに組み込む設定は今回追加していない。
